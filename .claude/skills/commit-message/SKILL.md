# 커밋 메시지 양식 (PBR 저장소)

이 저장소는 **커밋 메시지 자체가 기록 문서**다(`docs/기록/버전관리.md`와 짝을 이룬다 —
"무엇을 바꿨는지보다 왜 바꿨는지"). 그래서 `git log --oneline`만 읽어도 프로젝트가
겪은 시행착오가 보여야 한다. 기본 커밋 규약(하나의 논리적 변경 단위, 관련 없는
파일 섞지 않기 등)은 그대로 지키되, **메시지 문체는 아래 양식을 따른다.**

## 기본 형식

⚠️ **제목 한 줄로 끝내지 않는다.** 이 저장소의 커밋은 거의 전부(1.26.9까지 예외
없이) **제목 + 본문 여러 문단 + 트레일러** 구조다. 제목만 있는 한 줄짜리 커밋은
이 저장소 관례가 아니라 실수다 — 실제로 한 세션이 이 규칙을 놓치고 10개를
제목만으로 남겼다가 나중에 전부 본문을 채워 다시 썼다(1.26.10~1.26.19, 아래
"실제로 있었던 실수" 참고). **매 커밋마다 본문을 쓴다.**

```
{YYMMDD} {제목} ({버전})

{본문 — 여러 문단}

Co-Authored-By: {그 커밋을 실제로 작성한 모델 이름} <noreply@anthropic.com>
```

### 제목 줄

- **`{YYMMDD}`**: 커밋하는 날짜(KST) 6자리, 구분자 없음. 예: `260829`.
- **`{제목}`**: 한국어, 한 줄, 끝에 마침표 없음. 아래 "본문 문체" 참고.
- **`({버전})`**: `MAJOR.MINOR.PATCH` 형식, 여는 괄호 바로 앞에 공백 하나.
  기능·동작이 바뀌는 커밋에는 **거의 항상** 붙인다. 대부분 PATCH만 올린다
  (하루에 여러 커밋이면 `1.26.15` → `1.26.16` → `1.26.17`처럼 이어진다).
  버전 옆에 짧은 부연을 더할 수 있다: `(1.22.4, 측정)`, `(1.22.2, 조사)`,
  `(1.21.6, 기본은 꺼 둠)`.

### 본문 (제목 다음 빈 줄부터) — 분량은 보통 4~10문단

제목이 결론이라면 본문은 그 결론에 이르는 과정이다. 아래를 필요한 만큼 담는다
(전부 다 있어야 하는 건 아니지만, 실측·판단이 걸린 커밋일수록 전부 담긴다):

1. **계기·질문** — 왜 이 작업을 했는지. 사용자의 요청 문구를 그대로 인용하기도
   한다: `'계산 시간이 아니라 각 단계의 산출물 생성 방식'을 물으셔서 이어 쟀다.`,
   `ML_OPPORTUNITIES ①의 1단계.`
2. **방법·원인** — 무엇을 재거나 고쳤는지, 왜 그게 문제였는지. 재구현 없이
   기존 함수를 재사용했다면 그것도 적는다.
3. **수치** — 있는 그대로, 구체적으로. Before → After, 비교표, 회귀식,
   상관계수 등. 예: `MAE가 237.9 -> 136.9초로 42% 줄고`, `자기상관 0.79`,
   `51.91 -> 17.53초(3.0배)`.
4. **결정과 이유** — 채택/보류/기본값 여부와 그 근거. 예: `기본은 끈다 —
   근거가 아직 하루치 한 번이기 때문이다.`, `채택 기준을 통과했다.`
5. **곁다리로 고친 것** — 본 목적은 아니지만 하는 김에 고친 것들.
6. **코드 변경 요약과 테스트 개수** — 마지막 문단. `테스트 417 -> 421개 통과.`
   처럼 이전 개수 → 이후 개수를 적는다. 측정만 하고 코드를 안 바꿨으면
   `코드 변경 없음(측정만).`이라고 명시한다.

### 트레일러

본문 마지막 문단 다음에 빈 줄을 하나 두고 정확히 이 형식으로 남긴다:

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

과거 커밋은 전부 이 문구였다(당시 세션 모델). **실제로 이 커밋을 작성하는
세션의 모델 이름을 넣는다** — 문구를 고정 상수로 베끼지 말 것. 어떤 이름을
써야 할지 애매하면(예: 별칭·버전 표기가 여러 개면) 사용자에게 확인한다.

## 버전을 안 붙이는 예외

다음 성격의 커밋은 버전 번호를 붙이지 않는다 — 동작이 바뀌지 않았기 때문이다.

- 버전 이력 문서 자체를 갱신하는 커밋: `260826 버전 이력에 1.23.2~1.23.4를 넣는다`
- 순수 문서·기록 정리: `260827 두 PC 수집 구성을 문서화한다`
- "수정안 작성"류 메타 커밋(작업 계획을 문서로 남기는 것): `260825 수정안 작성`
- 날짜·오타 등 문서 사소 정정: `260812 오늘 작업분 문서 날짜 정정 (08-11 → 08-12)`

되돌림 커밋은 `git revert`가 만드는 기본 형식(`Revert "원래 메시지"`)을 그대로
쓴다 — 이 양식을 새로 적용하지 않는다.

## 본문 문체

**한국어, 구어체에 가까운 서술문.** "Update weather.py" 같은 영어·명사구 스타일이
아니라 실제로 무엇을 했는지/무엇을 알게 됐는지 문장으로 말한다.

두 가지 큰 갈래가 있다:

1. **한 일을 말한다** (기능 추가·정리·구현) — 현재형 종결(`~한다/~붙인다/~고친다/
   ~만든다/~나눈다`)을 쓴다.
   - `날씨를 읽고, 재고, 예측에 붙여 판정한다 (1.20.1)`
   - `루트의 일회성 스크립트를 치우고 experiments를 성격별로 나눈다 (1.20.7)`
   - `시간 예산을 제약으로 걸 수 있게 한다 (1.21.6, 기본은 꺼 둠)`

2. **발견/결과를 말한다** (실측·디버깅·실험) — 과거형 종결(`~였다/~았다/~없었다/
   ~틀렸다/~무너졌다`)을 쓴다. **놀라운 결과일수록 그 자체를 헤드라인으로 뽑는다**
   (프로젝트 문화: 짐작이 아니라 재서 답한다).
   - `TMAP이 9년 전 저녁 교통량으로 답하고 있었다 (1.26.5)`
   - `직선거리는 1.53배 낙관적이었다 (1.26.4)`
   - `자기상관 0.79는 '기억'이 아니었다 (1.22.7)`
   - `커서를 대도 어디인지 알 수 없었다 (1.22.3)`

**두 갈래를 한 줄에 이어 붙일 때**는 구분자로 ` - `(공백-하이픈-공백),
` — `(공백-엠대시-공백), 또는 마침표 하나를 쓴다. 셋 다 실제로 쓰인다 —
의미 단위가 뚜렷이 갈릴 때만 쓰고, 남발하지 않는다.

- `예보로 재봤다 - 강수확률·유무만으로는 부족하다 (1.26.17)`
- `OD 흐름도 쟀다 — 이웃의 세 정의가 모두 졌다 (1.23.3)`
- `결품 지도를 만든다. 수집 창이 중요한 시간대를 비워 두고 있었다 (1.23.4)`
- `이상치 제거를 계획에 옮길 뻔했다가, 재 보고 그만둔다 (1.20.8)`

**인용 부호로 검증 대상을 표시한다** — 확인해 본 주장·설정값·명칭을 작은따옴표나
큰따옴표로 감싸면 "이걸 의심해서 재 봤다"는 맥락이 산다.

- `'예산 강제'는 예산을 지키지 않고 있었다 (1.26.6)`
- `"한 달치는 너무 적다"는 맞았다. 옛 달은 답이 아니었다 (1.22.8)`
- `"오프라인 말고 이점이 있냐"는 물음에 근거 하나가 무너졌다 (1.22.5)`

**구체적인 수치를 그대로 넣는다** — "빨라졌다"가 아니라 "8.6배 빨라졌다",
"낙관적이었다"가 아니라 "1.53배 낙관적이었다". 뭉뚱그리지 않는다.

- `군집 조정이 8.6배 빨라졌다 (1.23.8)`
- `분위수 모델 채택 — warmup 피처 + 분위수 보정 0.95→0.97 (1.15.2)`

## 하지 말 것

- **제목 한 줄만 쓰고 본문을 생략하는 것.** 가장 흔하고 가장 눈에 띄는 실수다 —
  아래 "실제로 있었던 실수" 참고.
- 영어 커밋 메시지, `fix:`/`feat:` 같은 Conventional Commits 접두어 — 이 저장소는 안 쓴다.
- "버그 수정", "기능 개선" 같은 내용 없는 요약 — 무엇이 왜 문제였는지 본문에 담는다.
- 본문 끝 마침표.
- 실제로 동작이 바뀌었는데 버전 번호를 생략하는 것.
- 여러 논리적 변경(예: 이번 세션 작업 + 이전 세션의 무관한 webapp 수정)을 한 커밋에
  섞는 것 — 파일을 이름으로 콕 집어 스테이징한다(`git add -A` 금지, 이 저장소
  루트 CLAUDE 지침과도 일치).
- 과거 트레일러 문구(`Claude Opus 5 (1M context)`)를 사실과 다르게 그대로
  복사하는 것 — 실제로 그 커밋을 작성한 모델 이름을 쓴다.

## 실제로 있었던 실수 (2026-08-29)

이 스킬 파일을 처음 만든 세션이 정작 자기 세션의 커밋(1.26.10~1.26.19, 10개)에는
제목 한 줄만 쓰고 본문을 통째로 빠뜨렸다. 직전 커밋(1.26.9까지)이 전부 상세한
본문을 갖고 있었는데도 그 패턴을 못 보고 지나쳤다 — 이 스킬 문서를 쓸 때
`git log --oneline`(제목만 보임)만 훑고 `git log --format="%B"`(본문 포함)로
전체를 대조하지 않은 것이 원인이다. 사용자가 "분량이 오늘 한 거랑 완전 다르다"고
지적한 뒤에야 발견해 10개 커밋을 전부 본문을 채워 다시 썼다(`git reset` +
`cherry-pick` + `commit --amend`로 트리는 그대로 두고 메시지만 교체, 이미 푸시한
뒤라 `--force-with-lease`로 다시 올렸다).

**교훈: 이 저장소의 커밋 관례를 확인할 때는 반드시 `%B`(전체 본문)로 봐야 한다.**
`--oneline`은 제목만 보여줘서 본문이 있는지조차 판단할 수 없다.

## 버전 번호를 정할 때

`docs/기록/버전관리.md` 맨 위 항목에서 현재 버전을 확인하고, 이번 변경의 크기에
맞춰 PATCH(대부분)·MINOR(새 기능 단위)를 올린다. 버전을 올린 커밋은 보통
`docs/기록/버전관리.md`에도 같은 버전 번호로 절을 하나 추가한다(이 저장소 규약,
`.claude/skills/pbr-pipeline`의 "버전에 영향 주는 수정을 하면 기록한다" 참고) —
**커밋 메시지가 그 절 제목과 같은 문구를 쓰는 경우가 많다.**
