# 세션 효율 (PBR 저장소)

이 저장소는 문서 20여 개, 테스트 742개(~100초), 대여이력 CSV 최대 62만 행,
그리고 **여러 세션이 같은 작업 트리를 동시에 쓰는** 구조다. 셋 다 컨텍스트를
불필요하게 불리는 원인이 된다. 아래는 "어떻게 하면 덜 먹으면서 같은 일을
하는가"를 이 저장소 실제 사례에 맞춰 정리한 것이다.

## 언제 서브에이전트(Explore/general-purpose)에 위임하는가

**기준: 결과만 필요하고 과정(원문)은 다시 안 볼 파일 읽기·탐색인가.**

| 상황 | 위임 여부 | 이유 |
| --- | --- | --- |
| `docs/` 20여 개 중 어디에 뭐가 있는지 찾기 | 위임 | 후보 문서 여러 개를 열어보고 하나만 골라야 하는데, 나머지 원문은 메인 세션에 남길 필요가 없다 |
| `EXPERIMENTS.md`·`DEMAND_DISTRIBUTION.md`처럼 **이미 어느 문서인지 아는** 파라미터 근거 확인 | 직접 Read | 대상이 확정됐으면 서브에이전트 왕복(콜드스타트)이 더 비싸다 |
| `python -m pytest` 전체 실행 후 실패만 골라내기 | 위임 또는 출력 요약 | 742개 통과 로그 전체가 컨텍스트에 남을 필요는 없다 — 실패한 것과 요약 줄만 있으면 된다 |
| `git log --format="%B"`로 커밋 문체 관례 확인 (commit-message 스킬 작성 시 실제로 겪음) | 위임 | 수십~수백 개 커밋 원문을 훑고 패턴만 뽑아내는 작업. 원문이 메인 컨텍스트에 남으면 그 뒤 작업 내내 짐이 된다 |
| step0~step4 특정 파일 하나를 고쳐야 하는데 위치를 앎 | 직접 Read/Edit | 이미 대상이 확정된 단일 파일 작업에 서브에이전트는 과잉이다 |
| 실험 스크립트 48개(`experiments/`)에서 공통 패턴(`sys.path` 보일러플레이트 등) 찾기 | 위임 | 파일 수가 많고 각 파일의 전체 내용이 아니라 패턴 유무만 필요하다 |

**이 저장소에서 실제로 위임 판단을 놓쳤던 사례**: commit-message 스킬을 처음
작성한 세션이 `git log --oneline`(제목만)로만 관례를 확인하고 본문 스타일을
놓쳐 커밋 10개를 실수했다(`.claude/skills/commit-message/SKILL.md` "실제로
있었던 실수" 참고). 이건 서브에이전트 문제가 아니라 확인 범위 문제였지만,
**"본문까지 전체를 훑어야 하는 조사"는 정확히 서브에이전트에 위임할 상황**이었다
— 수백 개 커밋 본문을 메인 컨텍스트에 그대로 펼치지 않고도 패턴만 받아올 수
있었다.

## 무거운 명령은 조용히 실행하거나 격리한다

- **`python -m pytest`**: 기본 실행은 742개 결과가 전부 출력에 찍힌다. 실패
  원인만 볼 때는 `python -m pytest -q` 또는 실패 시에만
  `python -m pytest --tb=short -x`로 첫 실패에서 멈추는 편이 컨텍스트를 아낀다.
  전체가 통과하는지만 확인하면 되는 습관적 실행은 그대로 해도 되지만(짧은
  요약 줄만 출력에 남는다), 실패를 분석해야 하는 상황이면 서브에이전트에
  로그 분석을 맡기는 것이 낫다.
- **`python tools/check_consistency.py`**: 커밋 직전 습관적으로 도는 검사라
  출력이 짧다 — 이건 그대로 메인에서 실행해도 된다.
- **`python run_pipeline.py`(전체 파이프라인)**: step0~step4가 각각 로그를
  낸다. 실행 자체를 확인해야 할 때(`pbr-run` 스킬 영역)가 아니라 **코드가
  구문적으로 맞는지만** 볼 때는 `python -m py_compile <파일>`로 충분하다 —
  전체 파이프라인을 돌릴 필요 없다.
- **대여이력 CSV(최대 62만 행)**: `db.read_rental_source(period, columns=[...])`로
  **필요한 컬럼만** 지정해서 읽는다(`pbr-pipeline` 스킬에도 있는 규칙) — 이건
  실행 속도 문제이자 동시에, 결과를 그대로 터미널에 찍거나 Read로 열어보면
  컨텍스트도 그만큼 먹는다. 표 형태로 확인할 때는 `.head()`/`.describe()`처럼
  요약된 형태로만 출력한다.

## 대화 컨텍스트를 비울 시점 (`/clear`)

이 저장소는 작업 단위가 뚜렷하게 갈린다 — **구역별 검토**(F→A→E→B→D→C→G 순회한
전례처럼), **문서 정리**, **실험 하나**, **커밋 하나**. 다음 경계에서 `/clear`를
쓰면 이전 구역의 탐색 결과(수십 개 파일 원문)를 다음 작업까지 끌고 가지 않는다.

- 검토 대상 구역이 바뀔 때 (예: A 구역 검토 끝나고 E 구역으로 넘어갈 때)
- 실험 하나(`experiments/params/road_time_model.py` 재추정 등)를 끝내고
  무관한 문서 작업으로 넘어갈 때
- 커밋까지 마친 뒤 다음 요청이 방금 커밋한 내용과 무관할 때

반대로 **비우면 안 되는 경우**: 아직 검토·승인 절차 중간(검토 → 보고 →
승인 후 수정)이거나, 방금 확인한 파일 내용을 다음 편집에서 바로 참조할 때.
이 저장소는 "검토 → 보고 → 사용자 승인 → 수정"을 구역마다 반복하므로, **보고
직후 사용자 승인을 기다리는 시점**에 컨텍스트를 비우면 승인 대상이 뭐였는지
다시 불러와야 해서 오히려 손해다.

## 동시 세션 경쟁과 컨텍스트 낭비

[[concurrent-session-index-conflict]]에 기록된 대로 이 저장소는 여러 세션이
같은 git 인덱스를 공유한다. 이게 세션 효율과 만나는 지점: **스테이징 확인을
반복해서 다시 하는 것**(`git diff --cached`를 여러 번 다시 찍어보는 것)은
경쟁을 막지 못하면서 출력만 컨텍스트에 쌓는다. 대신:

- `python tools/commit_guard.py --intend <파일들>` 로 의도를 한 번 남기고
  (훅이 있으면) 커밋 시점에 자동으로 막히게 한다 — 사람이 반복 확인할 필요를
  없앤다.
- 커밋 **후** `git show --stat HEAD` **한 번**으로 결과를 확인한다 — 이게
  유일하게 의미 있는 확인이고, 그 전 단계의 반복 확인은 낭비다.

## 요약: 이 저장소에서의 체크리스트

1. 파일 위치를 모르는 탐색(문서 20여 개, 실험 48개) → Explore 서브에이전트
2. 파일 위치를 아는 단일 작업 → 직접 Read/Edit
3. 커밋 관례·과거 패턴처럼 **원문 전체를 훑어야 하는 조사** → 서브에이전트
4. `pytest`/`run_pipeline`/CSV 로드는 필요한 만큼만 조용히 (`-q`, `columns=[...]`,
   `py_compile`)
5. 구역·작업 단위가 바뀌는 경계에서 `/clear` — 단, 승인 대기 중에는 비우지 않는다
6. 동시 세션 경쟁은 반복 확인이 아니라 `commit_guard.py` + 커밋 후 단 한 번의
   `git show --stat HEAD`로 해결한다
