## 5. DB 선택 검토 → ✅ SQLite 채택

> **당시 상황**: CSV 기반인데 대규모 처리가 힘들 테니 DB로 가야 한다는 것은 정해짐.
> 그런데 **어떤 걸 왜 쓸지**를 고민해야 함. NoSQL을 말했는데, 시계열 데이터를 다룰 수
> 있는 DB를 고려해 봐야 할 것 같다고 함.

### 시계열 DBMS(TSDB) 개요

- **개요**: 시간 흐름에 따라 생성되는 데이터(센서, 로그, 거래 등)를 고속 저장·조회하는 DB
- **종류**: InfluxDB(모니터링 특화), TimescaleDB(PostgreSQL 기반 SQL 활용),
  Machbase(국내 고성능 TSDB), kdb+(금융권 초고속 DB)

### 당시 데이터 상황

(60만 행, 10개 컬럼) 규모의 CSV 파일 총 5개 — ① 대여이력(시계열) ② 대여소 정보(마스터)
③ 대여소별 작업량 ④ 대여소별 재고 이동 ⑤ 방문 순서

**추천 DB: SQLite.** 5개 CSV를 각각 다른 파일로 두지 않고 `bike_system.db` 하나 안에
5개 테이블로 통합 관리 (SQL JOIN 및 이식성 극대화).

### SQLite가 로컬 파일임에도 완전한 DB로 작동하는 이유

1. **B-Tree 구조 및 인덱스** — CSV처럼 처음부터 끝까지 읽는(Full Scan) 방식이 아니라,
   인덱스를 통해 60만 건 중 원하는 1건을 3~4번 만에 찾아낸다.
2. **페이지 단위 입출력** — 파일 전체를 메모리에 올리지 않고 데이터가 포함된 작은
   블록(보통 4KB)만 로드해 메모리 사용을 최소화한다.
3. **바이너리 인코딩** — 텍스트인 CSV와 달리 이진수로 변환·압축 저장해 디스크를 아끼고
   연산 속도를 높인다.
4. **ACID 트랜잭션 보장** — WAL(Write-Ahead Logging)로 쓰기 도중 프로그램이 꺼져도
   파일이 깨지지 않고 안전하게 복구된다.
5. **표준 SQL 지원** — 대형 서버 DB와 같은 문법이라 복잡한 JOIN 및 시계열 가공이 가능하다.

### 실제로 어떻게 됐나

✅ **SQLite로 갔고, 이 메모의 판단이 대체로 맞았습니다** — 자세한 결정 과정과 이관
단계는 [DB_PLAN.md](DB_PLAN.md), 스키마는 [DB_SCHEMA.md](DB_SCHEMA.md).

다만 **한 가지는 틀렸습니다.**

> "DB로 옮기면 빨라진다"는 전제가 조건부였습니다. 단일 기간만 다루면 **CSV가 최대
> 1.8배 빠릅니다.** 비용을 분해해 보니 데이터를 읽는 일은 전체의 1.4%뿐이고 98.6%가
> SQLite→Python 경계 비용이었습니다. DB가 이기는 건 **저장소가 필요한 양보다 클 때**
> 입니다 — [RETROSPECTIVE.md](RETROSPECTIVE.md) 4장 ①.

테이블 구조도 메모의 초안(5개)과 달라져 **15개 테이블**이 됐습니다.
초안의 컬럼명(`latitude`, `capacity`, `truck_id` 등)도 실제와 다르니
[DB_SCHEMA.md](DB_SCHEMA.md)를 정본으로 보세요.

## 7. Issue는 문제 정의 능력을 보여준다

**Background** — 왜 필요한가
(예: 현재 메인 페이지 로딩이 3초 이상 걸려 이탈률 증가. Lighthouse 측정 결과 이미지
에셋 용량이 원인으로 파악됨)

**Task** — 무엇을 할 것인가
(예: 메인 배너 이미지를 WebP 포맷으로 변환 및 압축)

**Acceptance** — 완료 기준

### 이슈에 있어야 하는 것

상황(어떤 문제가 보였는가) · 영향(사용자는 무엇을 못 하는가) · 목표(무엇을 바꾸면 되는가) ·
완료 기준(어떤 상태면 닫을 수 있는가) · 검증 방법(어떻게 확인할 것인가)

### 나쁜 이슈의 특징

- 제목만 있고 본문이 없음
- 문제와 해결책이 섞여 있음
- 완료 기준이 없어 끝을 판단하기 어려움
- 스크린샷이나 재현 절차가 없음
- 커밋/PR과 연결되지 않음

### 흐름

```text
issue → branch → commit → pull request → review → merge
```

이슈마다 브랜치를 나눠서 진행한다. **메인에서 바로 고쳐 커밋하면** 다른 오류가 생겨
전체 서비스가 멈출 수 있다.

> 좋은 저장소는 "코드를 올렸습니다"가 아니라
> **"문제를 정의하고, 분리해서 고쳤고, 검토 후 반영했습니다"** 를 보여준다.

## 9. 트러블슈팅은 면접 답변의 재료다 (STAR)

### 사례: 작업 계획의 소요시간이 비현실적으로 나온다

**Situation**
최종 작업 계획의 예상 소요시간이 현실성 없이 과하게 계산된다.
(예: 수요 예측을 다음 5시간 동안 하는데, 이전 작업이 4시간 소요된다.)

**Task**
수요 예측 시점부터 5시간 동안의 예측이므로 최대한 빨리 마쳐야 하며,
**1~2시간 이내에 재배치를 완료하는 것**이 목표다. 상황처럼 오래 걸리면
예측 시간 동안 사용될 대수를 충족하지 못한다.

**Action**
"각 작업자마다 방문 노드 수가 너무 과하게 책정되었다"고 판단.
작업자별로 부여되는 노드 수를 줄인다.

**Result**
매 작업마다 과한 작업량을 계획하는 것은 현실성이 없다는 것을 알았다.
모든 작업을 할 수 없는 경우엔 **우선순위가 높은 작업을 우선 처리**해야 한다.
