## 2. 어떻게 여기까지 왔나

작업은 다섯 덩어리였습니다.

### ① 고장 수리 (1.0.3 ~ 1.2.2)

먼저 **파이프라인이 아예 돌지 않는 상태**를 고쳤습니다.

- `now` 값이 세 갈래(실행 시각 / 하드코딩 / 미사용 설정 파일)로 갈려 단계 간
  파일명이 어긋났습니다 → `project_config`로 통일
- step0 스크립트들이 서로 import해서 **한 파일 실행 = API 호출부터 전부 재실행**
  → 실행 로직을 `main()`으로 격리
- `EDA.py`는 오타로 즉시 크래시, step4는 산출물 저장이 주석 처리된 상태
- 웹 대시보드를 만들고([WEBAPP.md](WEBAPP.md)), 코드 리뷰로 작업 ID 충돌·
  프로세스 트리 미종료 등을 수정

### ② 검증 기반 마련 (1.2.1 ~ 1.3.0)

- Python 3.14 환경에서 **의존성이 전부 깨져 있었습니다**(2023년 고정 버전).
  `scikit-learn-extra`는 아카이브돼 설치 자체가 불가능 → `kmedoids`로 교체
- 합성 데이터 생성기 + 스모크 테스트 34개 → 이후 모든 수정의 안전망

### ③ 저장소 이관 (1.4.0 ~ 1.7.0, [DB_PLAN.md](DB_PLAN.md))

CSV 파일명의 `{now}` 라벨을 **`run_label` 컬럼**으로 옮기는 작업을 4단계로 나눠
진행했습니다: 저장소 → 이중 기록 → 웹 API 전환 → 대여이력 적재.
각 단계가 되돌릴 수 있고 CSV 폴백이 있어 중간에 멈춰도 안전한 구조로 갔습니다.

### ④ 운영 모델 반영 (1.8.0 ~ 1.9.2, [FLEET.md](FLEET.md))

"보유 21대, 하루 3회차, 회차당 10대 로테이션"이라는 **실제 운용 방식**을 반영했습니다.
그전까지 차량 대수는 제약이 아니라 클러스터 수에서 따라 나오는 결과였습니다.

실데이터를 받아 처음으로 전 단계를 완주했고(step3 TMAP 지도 포함),
군집 거리 가중치를 실험으로 조정해 시간 예산 초과를 없앴습니다.

### ⑤ 성과 지표 체계 (1.9.3 ~ 1.11.0, [KPI.md](KPI.md))

지표가 콘솔·CSV·여러 테이블에 흩어져 있던 것을 `kpi_summary` 한 줄로 모으고,
**계획 달성률에서 실제 편익으로** 지표의 성격을 확장했습니다.

## 4. 측정이 뒤집은 가설 다섯 가지

이 프로젝트에서 가장 값진 부분입니다. **예상하고, 재고, 틀렸음을 확인한** 기록입니다.

### ① "DB로 옮기면 빨라진다" → 조건부

단일 기간만 다루면 **CSV가 최대 1.8배 빠릅니다.** 비용을 분해해 보니
데이터를 읽는 일은 전체의 **1.4%**뿐이고, 98.6%가 SQLite→Python 경계 비용이었습니다
(셀마다 PyObject 생성 66% + DataFrame 변환 32%).

DB가 이기는 건 **저장소가 필요한 양보다 클 때**입니다 — 3개월치에서 한 달만 읽으면
2.45배 빠릅니다. 실제 운용(1년치 적재, 한 달씩 분석)이 여기 해당해서 다행이었지만,
"DB니까 빠르다"는 전제는 틀렸습니다. → [DB_PLAN.md](DB_PLAN.md) 4단계

### ② "거리 가중치를 올리면 이동거리가 는다" → 반대였다

`_05_10` **한 회차만 보고** 총 이동거리가 301→319km로 늘었다고 보고했습니다.
3회차 전부로 다시 재니 오히려 **866→814km로 51km 줄었습니다.**

greedy 탐색이라 단일 실행 결과가 흔들립니다(γ=2000에서는 오히려 악화).
단일 실행으로 판단하면 안 된다는 걸 직접 겪었습니다. → [step1 문서](steps/step1_clustering.md)

### ③ "회수하면 그 대여소에 결품이 생긴다" → 0건

Pick 대여소에서 결품이 **한 시간도 늘지 않아** 버그를 의심했는데, 검증해 보니
타당했습니다. Pick 대여소는 회수 후에도 재고 중앙값 16대인데 그 시간대 순수요가
**−0.7대**(반납이 더 많음)라 바닥날 일이 없었습니다.

반대로 Drop 대여소는 **재고 중앙값이 0대** — 절반 이상이 완전히 비어 있었고
결품이 거의 전부 거기서 났습니다. → [KPI.md](KPI.md) 3-B

### ④ "MAE가 낮으면 예측이 좋다" → 기준선을 봐야 안다

`_10_15` 시간대의 MAE가 1.14로 **네 시간대 중 가장 낮았습니다.** 그런데
"순수요 0"이라고 찍는 기준선도 1.14였습니다 — **예측이 아무 값도 못 하고 있었습니다.**

절대 오차만 봤다면 "낮 시간대 예측이 제일 정확하다"고 정반대로 판단했을 겁니다.
→ [KPI.md](KPI.md) 3-E

### ⑤ "step1이 5분 이상 걸린다" → 42초

기존 기록(버전관리 1.0.1)에 "5분 이상"이라 적혀 있어 성능 개선을 우선 과제로 뒀는데,
실데이터에서 **42초**였습니다. 작업 대상이 87곳이라 조정 반복이 빨리 수렴했습니다.
성능 최적화 우선순위를 낮췄습니다.

## 5. 설계 결정과 근거

| 결정 | 대안 | 왜 이걸로 | 대가 |
| --- | --- | --- | --- |
| SQLite | PostgreSQL, 시계열 DB, NoSQL | 단독 개발·단일 PC. 표준 라이브러리만으로 동작, 파일 하나로 백업 | 동시 쓰기 1개 (현재 구조엔 무관) |
| 표준 `sqlite3` | SQLAlchemy | pandas 계층 코드가 동일해 이점이 없었음. 교체 지점을 `connect()` 하나로 격리 | PostgreSQL 전환 시 그 함수만 수정 |
| CSV·DB 이중 기록 | 즉시 전환 | 되돌릴 수 있고, 중간에 멈춰도 안전 | 전환기 동안 코드 중복 |
| `kmedoids` (Rust) | `scikit-learn-extra` | 후자는 아카이브돼 3.12+ 설치 불가 | 결과가 미세하게 다를 수 있음 |
| 누적 부하 기반 로테이션 | 고정 순번표 | 정비로 차량이 빠지거나 회차 수가 바뀌어도 규칙이 성립 | 다음 출동 차량을 미리 못 정함 |
| 요구사항 하한(`>=`) 고정 | 상한 고정 | 새 Python에서 휠이 없어 설치가 통째로 깨지는 걸 겪음 | 상위 버전 호환은 미보장 |
| 파이썬 단독 웹(FastAPI) | React + API | 핵심 자산이 pandas·PuLP. JSON API를 미리 분리해 나중에 교체 가능 | 지도 인터랙션 제한 |

## 6. 지금 알고 있는 한계

**모델**
- `z = 1.65`가 부족합니다 (실측 커버리지 91.7~92.8%, 필요값 ≈ 1.99)
- `_10_15` 회차의 예측은 기준선과 차이가 없습니다
- 계절 전환기(2월→3월) 커버리지 86.5% — 수요 1.8배 급증을 못 따라감
- ILP는 직선거리(Haversine), VRP는 greedy 휴리스틱
- 차량이 여러 클러스터를 순차 처리하지 못함 (회차당 1대 = 1클러스터 고정)
- 시간 예산이 **제약이 아니라 사후 점검**입니다

**측정**
- 결품 시뮬레이션은 실측이 아니라 복원입니다. 초기 재고(API 현재 스냅샷)와
  순수요(25년 11월)의 시점이 다르고, 재고를 0에서 잘라 **결품의 하한**입니다
- `improvement_rate`는 계획 달성률이지 이용자 편익이 아닙니다

**운영**
- 웹앱에 인증이 없습니다 (로컬 전용)
- `VEHICLES_PER_ROUND = 10`, 작업 시간 30초/대는 현장 확인이 필요한 가정값입니다
- 폴더명에 공백·괄호·한글이 있어 셸 인용이 필요합니다

## 7. 남은 과제 (우선순위)

1. **`z`를 1.65 → 1.99로 조정** — 근거가 실측이라 즉시 실험 가능. γ 실험과 같은 방식
2. **`_10_15` 회차 재검토** — 예측이 안 되는 시간대를 계속 돌릴 것인가
3. **계절 전환기 대응** — 최근 데이터 가중, 또는 계절별 `z`
4. **시간 예산을 실제 제약으로** — 초과 클러스터를 쪼개는 반복 루프
5. **차량의 다중 클러스터 처리** / OR-Tools 전환
6. 포화 시간·수요 충족률 지표, CSV 기록 제거, 폴더명 정리
