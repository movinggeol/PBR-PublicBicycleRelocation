## 🟡 P2-B. 의존성 폐기 예고 — **대비 완료 (1.18.7), 전환은 남음**

### `PULP_CBC_CMD`가 PuLP 4.0에서 사라진다

`pulp 3.3.2`가 실행마다 경고를 냅니다. `requirements.txt`는 **하한(`>=`) 고정**이라
PuLP 4.0이 나온 뒤 새 환경에서 설치하면 **step2가 통째로 깨집니다.** 1.2.1에서
"의존성이 전부 import 실패"를 겪은 것과 같은 종류의 사고입니다.

**한 것 (1.18.7)**

| 항목 | 조치 |
| --- | --- |
| `LpVariable.dicts` (폐기 예정) | → `prob.add_variable_dicts()`. 경고 사라짐 |
| 솔버 생성 | `ilp.build_solver()` 하나로 모음. 파이프라인·실험·테스트가 전부 이걸 쓴다 |
| 폐기 대비 | `PULP_CBC_CMD` → `COIN_CMD`(PATH) → `COIN_CMD`(cbcbox 경로) → **무엇을 설치할지 알려 주고 중단** |
| 회귀 방지 | 테스트 3개 (폐기 후 폴백, 없을 때 안내, main이 직접 만들지 않는지) |

**순서에 뜻이 있습니다** — `PULP_CBC_CMD`를 **먼저** 봅니다. 문서의 모든 수치가
그 솔버로 나왔으므로, 있는 동안에는 그대로 써서 재현성을 지킵니다.

**남은 것 — 확인해 본 결과**

- `pip install pulp[cbc]`는 **`cbcbox` 패키지(약 149MB)** 를 설치합니다. 설치하면
  `COIN_CMD(path=cbcbox.cbc_bin_path())`로 정상 동작합니다(실측 확인).
- 다만 **PuLP 3.3.2의 `COIN_CMD`는 cbcbox를 자동으로 찾지 못합니다** — 경로를 직접
  넘겨야 합니다. `build_solver()`가 그 처리를 이미 해 둡니다.
- **149MB를 모두에게 강요하지 않으려고 `requirements.txt`에는 넣지 않았습니다.**

- **PuLP 4.0이 실제로 나오면**: (a) 4.0이 여전히 CBC를 동봉하는지 확인 →
  아니라면 (b) `requirements.txt`를 `pulp[cbc]>=…`로 바꾸고 README의 "별도 solver
  설치가 필요 없습니다" 문구를 정정. 상한(`pulp<4`)은 규약 위반이라 쓰지 않습니다.

        `stops`에 실으면 된다. 표시는 `36.3504, 127.3845` 형태면 카카오맵·
        네이버지도·구글지도 어디에나 붙는다.
      - **주소는 새로 얻어야 한다.** 좌표를 주소로 바꾸려면 역지오코딩이 필요하고
        (TMAP에 있다), 대여소는 잘 안 바뀌므로 **한 번 받아 테이블에 저장해
        두는 것**이 맞다 — 지시서를 열 때마다 부르면 안 된다. 비용·한도가 드는
        외부 호출이니 **좌표부터 넣고 주소는 그다음**으로 나누는 편이 낫다.

      복사 수단은 `navigator.clipboard`가 표준이지만 **HTTPS 또는 localhost에서만
      동작한다** — 기사가 다른 PC의 IP로 접속하면 조용히 실패한다. 폴백
      (`document.execCommand('copy')` 또는 텍스트 선택)을 함께 두고, 복사됐다는
      **눈에 보이는 확인**을 준다. 인쇄에는 필요 없으므로 `no-print`다.

      이 항목이 여기 붙은 이유는 **현장 = 휴대폰**이기 때문이다. 폰에서 좌표를
      복사해 지도 앱으로 넘어가는 흐름이라, 위의 모바일 작업과 같은 화면
      (`/orders`)을 건드린다. 다만 **좌표 복사는 데스크톱에서도 되어야 한다** —
      모바일 모드에서만 나타나게 만들지 말 것.

    - **모드 자체는 1.26.47에서 끝났다** (설계 근거는
      [DESIGN.md](../구현/DESIGN.md) "모바일 모드", 이력은
      [버전관리.md](버전관리.md) 1.26.47).

      착수 전(390px) → 후:

      | 화면 | 전 | 후 |
      | --- | --- | --- |
      | `/orders` 첫 지시서 | **1546px 아래**(칩 39개가 1029px) | **558px** |
      | `/orders` 7열 표 | 14개가 71~89px씩 넘침 | 카드로 누움 |
      | `/kpi` 15열 표 | **1367px**(화면의 3.5배) | 카드로 누움 |
      | 전 화면 가로 넘침 | `/orders`·`/data` | **0** |

      **설계의 핵심은 "폭 판정을 CSS가 하지 않는다"**이다. `@media`는 버튼으로
      끌 수 없어서 규칙을 두 벌 적게 되고, 그러면 한쪽만 고치게 된다. 스크립트가
      폭과 버튼을 함께 보고 `<html data-narrow>`를 붙였다 뗀다.

      처음 남겼던 제약 둘도 같은 버전에서 채웠다:

      - **카드 모드 정렬** — 표 앞에 단추 줄(`.m-sortbar`)을 세웠다. 정렬은
        머리글의 `th.__pbrSort`를 그대로 부른다(규칙을 두 벌 만들면 데스크톱과
        결과가 갈린다). 방향은 화살표로도 말한다.
      - **터치 타깃 44px** — 화면당 42~53개였던 것이 **전 화면 0개**가 됐다.
        표 안 링크가 16~21px이었는데, 글자를 키우면 표가 길어지므로 누를 면만
        키웠다(`inline-block` + 세로 여백 + 음수 마진, 겹침 0 확인).

      그 과정에서 **인쇄 결함 둘**을 잡았다 — 정렬 줄이 종이에 나온 것
      (`.no-print`가 `orders.html`에만 있었다)과, 인쇄에서 첫 칸만 `block`으로
      남은 것(`td[data-label=""]`의 가중치가 더 높다). 둘 다 테스트로 고정했다.

> (`ortools_gap.py`가 `bc.ilp_mod.build_solver()`를 부른다). ILP는
> **수송문제라 제약행렬이 완전 단모듈**이고 군집 하나가 0.05~0.2초에 풀리므로
> ([DECISIONS.md](../분석/DECISIONS.md) 4장) 바꿔서 얻을 시간이 없다.
> CP-SAT 검토는 하지 않는다.

### 🔴 대기-0B. 1차 군집화 효율화 — **예산 초과의 진짜 원인이다** (2026-08-31 예약)

> 📌 **[대기-0A](#대기-0a-vrp를-or-tools로-교체--얻는-것과-잃는-것을-끝까지-재고-결정한다-2026-08-31-예약)와
> 짝이다.** 경로를 아무리 잘 풀어도 **흩어진 군집은 못 고친다.** 손댈 곳은 여기다.

**진단은 이미 섰다.** 소요시간의 **60~75%가 이동**이고, 예산을 넘긴 군집은
작업량이 많아서가 아니라 **거리가 길어서** 넘었다(상관 **r=0.966**). 초과 군집은
45~56km로, 정상(30km)보다 흩어져 있다.

```text
클러스터 6  총 121.0분 = 이동 88.0분 + 작업 33.0분   (이동 73%, 43.99km)  ⚠ 초과
클러스터 9  총 107.6분 = 이동 74.6분 + 작업 33.0분   (이동 69%, 37.29km)
클러스터 0  총  60.3분 = 이동 35.3분 + 작업 25.0분   (이동 59%, 17.65km)
```

작업량은 25~34대로 고른데 **거리만 벌어졌다.**

🔴 **근본 원인 — 목적함수에 시간 항이 없다.**

```text
J = α·(군집별 수급 불균형)² + β·(군집 크기 편차)² + γ·(군집 내 거리)
```

`γ·거리합`은 **메도이드까지의 거리 합**이지 **차량이 실제로 도는 시간**이 아니다.
그래서 "대여소는 6곳뿐인데 서로 멀리 떨어진" 군집이 만들어질 수 있고, step1은
그것이 예산을 넘길지 **알지 못한 채** 넘긴다.

**현재 실측 준수율은 78~85%**이고 `_05_10`에는 **196분**짜리 회차도 있었다
(예산 120분). `_05_10` 5개월 평균은 **154분**이다.

### ✅ 대기-4. 군집 산정식에 실제 거리 (P4-10) — **닫는다. 현행이 낫다** (2026-08-31)

재현: `python experiments/diagnostic/tour_length_estimate.py`
([EXPERIMENTS.md](../분석/EXPERIMENTS.md) 13장)

**K를 바꾸기 전에 어림 자체를 먼저 쟀다.** 5-H는 곧바로 K를 바꿔 전체를 돌렸는데,
그러면 결과가 나빠도 *어림이 나빠서인지 K 결정 방식이 나빠서인지* 갈리지 않는다.
이번에는 어림값과 **실제 군집 안 이동거리**를 직접 견줬다(차고지 왕복은 어림식이
따로 더하는 항이라 뺐다). **현행 식을 같은 자에 대조군으로 올린 것이 핵심이다** —
새 어림끼리만 견주면 셋 다 못해도 하나가 이긴다.

| 어림 | 보정계수 | MAPE | 최악 | CV |
| --- | ---: | ---: | ---: | ---: |
| **현행 (대여소 수)** | 0.375 | **7.5%** | **14.1%** | **8.0%** |
| BHH (면적) | 1.863 | 9.4% | 26.8% | 11.3% |
| NN 순회 | 1.822 | 8.2% | 23.6% | 10.2% |
| MST | 2.942 | 8.8% | 32.1% | 11.2% |

**거리를 보는 셋이 모두 현행보다 못하다.** 실제 좌표를 쓰는 NN·MST도 마찬가지라
5-H의 진단(*"균일분포 가정이 문제"*)은 지지되지 않는다.

**원인은 비교 대상이 다르다는 것.** 어림은 *모든 후보를 한 번씩 도는 최단 순회*를
재는데, 실제 경로는 적재 10대 제약 때문에 pick↔drop을 오가며 되돌아 다니는 K개의
분리된 경로다. 되돌아 다니는 양은 **기하가 아니라 물량과 적재 용량**이 정하므로
좌표를 정확히 볼수록 나아지는 문제가 아니다.

⚠️ **1.21.6("거리가 시간을 지배한다", r=0.966)과 모순이 아니다.** 군집이 *정해진 뒤*
그 군집의 시간을 거리가 설명하는 것과, 군집을 *정하기 전* 거리를 잘 어림할 수
있는가는 별개다. `wanted_vehicles()`는 후자의 자리에 있다.

📌 **8장 향후과제 1번의 남은 후보를 모두 소진했다** — 그 항목을 "아직 안 해 본
개선안"이 아니라 **"재 봤고 현행이 낫다"**로 다시 썼다. 굳이 다음을 적자면 기하가
아니라 물량 항(`bikes / VEHICLE_CAPACITY`)이지만, 현행이 이미 오차 7.5%라 이길
여지가 크지 않다.

⚠️ 씨앗 42 하나로 쟀다. 네 어림이 **같은 경로를 상대로** 겨루므로 순위는 유효하나
절대값은 흔들릴 수 있다.

곁다리 둘:
- `total_tour_km(frame, method)`를 step1에 두었다(`bhh`/`nn`/`mst`). BHH 경로는
  값이 소수점 이하까지 같음을 테스트로 고정했다 — 바뀌면 5-H 수치가 무효가 된다.
- **척도가 다른 어림끼리 표준편차로 견주면 안 된다.** 처음에 그렇게 봐서 MST가
  이기는 것으로 나왔는데, MST는 값 자체가 작아 표준편차도 자동으로 작아질 뿐이다.
  변동계수로 봐야 한다. 판정 로직을 고쳤다.
