## 2. 어떻게 여기까지 왔나

작업은 열한 덩어리였습니다.

### ① 고장 수리 (1.0.3 ~ 1.2.2)

먼저 **파이프라인이 아예 돌지 않는 상태**를 고쳤습니다.

- `now` 값이 세 갈래(실행 시각 / 하드코딩 / 미사용 설정 파일)로 갈려 단계 간
  파일명이 어긋났습니다 → `project_config`로 통일
- step0 스크립트들이 서로 import해서 **한 파일 실행 = API 호출부터 전부 재실행**
  → 실행 로직을 `main()`으로 격리
- `EDA.py`는 오타로 즉시 크래시, step4는 산출물 저장이 주석 처리된 상태
- 웹 대시보드를 만들고([WEBAPP.md](../구현/WEBAPP.md)), 코드 리뷰로 작업 ID 충돌·
  프로세스 트리 미종료 등을 수정

### ② 검증 기반 마련 (1.2.1 ~ 1.3.0)

- Python 3.14 환경에서 **의존성이 전부 깨져 있었습니다**(2023년 고정 버전).
  `scikit-learn-extra`는 아카이브돼 설치 자체가 불가능 → `kmedoids`로 교체
- 합성 데이터 생성기 + 스모크 테스트 34개 → 이후 모든 수정의 안전망
  (지금은 245개, 무엇을 지키는지는 [TESTING.md](../구현/TESTING.md))

### ③ 저장소 이관 (1.4.0 ~ 1.7.0, [DB_PLAN.md](../구현/DB_PLAN.md))

CSV 파일명의 `{now}` 라벨을 **`run_label` 컬럼**으로 옮기는 작업을 4단계로 나눠
진행했습니다: 저장소 → 이중 기록 → 웹 API 전환 → 대여이력 적재.
각 단계가 되돌릴 수 있고 CSV 폴백이 있어 중간에 멈춰도 안전한 구조로 갔습니다.

### ④ 운영 모델 반영 (1.8.0 ~ 1.9.2, [FLEET.md](../구현/FLEET.md))

"보유 21대, 하루 3회차, 회차당 10대 로테이션"이라는 **실제 운용 방식**을 반영했습니다.
그전까지 차량 대수는 제약이 아니라 클러스터 수에서 따라 나오는 결과였습니다.

> 회차당 10대는 1.19.1에서 다시 **작업량이 정하도록** 바뀌었습니다. 상한 10이
> 실데이터에서 늘 걸려 사실상 고정이었기 때문입니다 ([FLEET.md](../구현/FLEET.md)).

실데이터를 받아 처음으로 전 단계를 완주했고(step3 TMAP 지도 포함),
군집 거리 가중치를 실험으로 조정해 시간 예산 초과를 없앴습니다.

### ⑤ 성과 지표 체계 (1.9.3 ~ 1.11.0, [KPI.md](../분석/KPI.md))

지표가 콘솔·CSV·여러 테이블에 흩어져 있던 것을 `kpi_summary` 한 줄로 모으고,
**계획 달성률에서 실제 편익으로** 지표의 성격을 확장했습니다.

### ⑥ 파라미터 검증 (1.12.0, [EXPERIMENTS.md](../분석/EXPERIMENTS.md))

지표 체계가 갖춰지자 비로소 **"그동안 쓰던 값이 맞나"를 물을 수 있었습니다.**
목표 재고의 `z=1.65`, 예측에 쓰는 학습 창, 군집의 `γ` — 셋 다 "그럴듯해서" 정한
값이었습니다. 12개월치 순수요 위에서 각각 실험해 `z=1.99`, `γ=3000`으로 바꿨고,
계절 전환기 처방을 찾았습니다.

이 과정에서 **이전 결론 하나가 뒤집혔습니다** (4장 ⑥).

### ⑦ 계획 단위를 쪼개고, 도구로 다듬기 (1.13.0 ~ 1.17.3)

여기서부터는 "돌아간다"를 넘어 **누가 무엇을 언제 계획하느냐**를 다뤘습니다.

- **차량 대수를 실행 설정으로** (1.13.0) — 정비·결원으로 차가 빠지는 날이 실제
  운용이라, 보유·회차당 대수를 웹 폼과 CLI에서 바꿀 수 있게 했습니다.
- **ILP·VRP 속도 통일** (1.13.2) — 25 vs 30km/h로 갈려 있어 ILP가 고른 조합이
  VRP에서는 최소가 아니었습니다. 25로 통일하자 시간 예산 초과가 다시 드러났는데,
  **계획이 나빠진 게 아니라 추정이 정확해진 것**입니다.
- **평일/휴일 분리** (1.14.x, [steps/step0_raw.md](../구현/steps/step0_raw.md)) — 그전까지
  주말을 통째로 버려 이용의 21~34%가 사라져 있었습니다. 재 보니 대여소의 33~37%가
  두 구분에서 **부호가 반대**였습니다. `휴일 = 주말 ∪ 공휴일`로 정의하고 계획
  대상일을 달력으로 자동 판정합니다.
- **계절 보정과 되돌린 채택** (1.15.x,
  [DEMAND_DISTRIBUTION.md](../분석/DEMAND_DISTRIBUTION.md)) — 계획 대상 달 첫 14일로 배율을
  구해 `mu`·`sigma`에 곱합니다. 같은 라운드에서 분위수 모델을 채택했다가 **1.15.3에서
  철회**했습니다. 그 '승리'가 계절 배율이 과대추정된 베이스라인과 겨룬 결과였기
  때문입니다 — 측정 코드와 운영 코드가 다른 함수를 쓰면 측정이 거짓말을 합니다.
- **화면을 도구로** (1.16.0 ~ 1.17.2, [DESIGN.md](../구현/DESIGN.md)) — 토큰 기반 색·다크
  모드에서 시작해 Apple 디자인 언어로 다시 짰고, 처음 쓰는 사람을 위한 `/guide`를
  더했습니다. 안내는 설정값을 **하드코딩하지 않고 `project_config`에서 읽습니다** —
  숫자를 박아 두면 곧 거짓말이 되기 때문입니다.
- **정합성 점검** (1.17.3) — 코드·웹·문서를 맞대어 봤습니다. 문서에만 있고 동작하지
  않던 `--warmup-*` 옵션, 결측 지표에서 500이 나던 `/kpi`, 그대로 입력하면 크래시가
  나는 시간대 예시가 나왔습니다. 셋 다 **테스트가 없던 자리**였습니다.

### ⑧ 대조군을 세우다 (1.18.0, [THESIS.md](../연구/THESIS.md))

졸업작품을 넘어 **논문**으로 만들려니 "이 방법이 단순한 방법보다 나은가"에 답하는
숫자가 하나도 없다는 것이 드러났습니다. 대조군 4종을 세우고 5개월·4씨앗으로 반복해
유의성까지 확인했습니다.

**그런데 대조군을 세우는 과정이 평가 자체의 결함 세 가지를 찾아냈습니다** — depot
복귀 누락, 계획 기준 지표, 요일 필터 불일치. 셋 다 **비교하려고 하지 않았으면
드러나지 않았을** 것들입니다. 셋 다 고쳤고(1.18.3~4, 1.19.1), 마지막 하나인 복귀
누락은 "회차당 차량을 늘리는 운영 결정이 필요하다"며 3일간 보류했다가 그 결정이
내려지면서 함께 풀렸습니다 ([TODO.md](TODO.md) 1-1).

### ⑨ 계획을 현장으로 내보내다 (1.19.0 ~ 1.19.8)

여기까지는 **계산이 맞는가**를 다뤘습니다. 이 덩어리는 **그 계산을 사람이 쓸 수 있는가**를
다뤘습니다 — 차량별 작업지시서(인쇄하면 차량마다 쪽이 나뉩니다), 출발 직전 타슈 API로
계획 대상 대여소만 다시 조회하는 실시간 재고 대조, 표 정렬, 지표 그래프 3종.

**여기서 정한 성향이 뒤에도 계속 적용됩니다** — *화면은 판정만 하고 계획을 바꾸지
않는다*. 자동 보정을 넣으면 기사가 든 종이와 화면이 어긋나기 때문입니다.

측정이 또 한 번 예상을 뒤집었습니다. "공차 이동을 줄이려면 회차당 차량을 줄여야
한다"고 보고 스윕을 돌렸는데, **회차당 대수는 맞바꿈이 아니라 작업량이 정하는 값**이라는
결론이 나왔습니다(1.19.8). 그래서 대수를 고정하지 않고 **일감이 정하게** 바꿨습니다.

### ⑩ 밖에서 정보를 들여오다 (1.20.0 ~ 1.20.5)

파이프라인이 쓰는 정보가 '지난달 대여이력 + 지금 재고 한 장'뿐이라는 한계를 그대로
두고는 더 나아갈 곳이 없었습니다. 두 가지를 들여왔습니다.

- **재고 시계열** (1.20.0) — 평일 07~22시 10분 간격 수집(1.25.1에서 09~17시에서 넓혔습니다). 결품을 계산이 아니라
  실측으로 재기 위한 재료입니다([COLLECTOR.md](../구현/COLLECTOR.md)).
- **날씨** (1.20.1~2) — 대전 ASOS 13,848시간. **비 오는 날 재배치 필요량이 평소의
  40~55%** 라는 것을 확인했고, 계획 화면이 그 사실을 알립니다([WEATHER.md](../분석/WEATHER.md)).

그리고 문서를 정리했습니다 — 기술 선택의 근거([DECISIONS.md](../분석/DECISIONS.md)),
용어집([GLOSSARY.md](../GLOSSARY.md)), 그리고 30개를 넘긴 문서를 네 폴더로 나누고
목차([README.md](../README.md))를 세웠습니다.

### ⑪ 최적화가 충분한지 캐묻다 (1.21.6 ~ 1.21.9)

사용자 질문 하나에서 시작했습니다 — **"현행 ILP·VRP만으로 최적화가 효과적인가?
충분한가?"** 대조군 비교로 '효과적'은 이미 답할 수 있었지만 '충분한가'는 아니었습니다.
그래서 남은 약점을 하나씩 재 봤고, **네 번 중 세 번은 제가 세운 가설이 틀렸습니다.**

| 의심한 것 | 재 보니 |
| --- | --- |
| 시간 예산 초과(78~85%)가 문제다 | **맞았다.** 그런데 고칠 코드가 이미 있었다 — `greedy_route()`의 `time_budget_sec`를 파이프라인이 안 넘기고 있었을 뿐. 켜니 초과 4건 → 0건, 대가는 결품 40초 |
| 공차 이동 63%가 낭비다 | **틀렸다.** 90%가 차고지 왕복이라 피할 수 없고, 줄일 수 있는 중간 공차는 **6%**뿐이었다 |
| 이동시간 추정에 거리를 넣으면 낫다 | **틀렸다.** 대용으로 쓴 '퍼짐'은 계수가 음수로 나왔다 — 대여소 수의 대리 변수일 뿐 |
| 작업 문턱(2)이 잘못 잡혔다 | **틀렸다. 그런데 문턱이 아예 작동하지 않고 있었다** — `TOP_STATION_LIMIT`(50)이 먼저 자른다 |
| pick 후보가 비어 있을 것이다 | **틀렸다.** 후보의 재고 0 비율은 **0%**. '48.8%'는 전체 평균이고 pick 후보는 '넘치는 곳'만 고른 집합이다 |

**틀린 가설도 값을 냈습니다.** 문턱을 재다가 상한이 진짜 손잡이라는 것을 알았고,
그 상한을 쓸어 보니 **50이 보유 차량 21대와 맞물린 값**임이 드러났습니다(넓히면
필요 차량이 31대가 되어 집행이 안 됩니다). 근거가 없던 게 아니라 적히지 않았을
뿐이었고, 이제 적었습니다.

**이 라운드의 결론**: 파라미터로 짜낼 것은 거의 다 짜냈습니다. 남은 개선 여지는
**운영 결정**(차량 대수·수집 창)이나 **최적화 앞쪽**(수요 예측·실측 재고)에 있습니다.

## 3. 고친 문제들

발견 경로별로 묶었습니다. **절반 이상이 "고치러 간 김에" 또는 "실데이터를 넣으니"
드러난 것**이라, 검증 없이는 알 수 없었을 문제였습니다.

| 심각도 | 문제 | 어떻게 발견 |
| --- | --- | --- |
| 🔴 | `now` 3원화로 파이프라인 실행 불가 | 코드 전수 검토 |
| 🔴 | import 부작용 체인 (한 파일 = 전체 재실행) | 코드 전수 검토 |
| 🔴 | `EDA.py` 즉시 크래시 (`pd.DateFrame` 오타) | 코드 전수 검토 |
| 🔴 | 의존성 전부 import 실패 (Python 3.14) | 실제 설치 시도 |
| 🔴 | `scikit-learn-extra` 설치 불가 (아카이브) | 실제 설치 시도 |
| 🔴 | 웹 전 페이지 500 (Starlette 시그니처 변경) | 서버 실제 기동 |
| 🔴 | 원천 CSV BOM 인코딩 (첫 컬럼명 깨짐) | 실데이터 투입 |
| 🔴 | 처리 대수 2배 계산 (pick+drop 중복) | 시간 예산 질문에 답하다 |
| 🔴 | step4에도 같은 2배 버그 | 실데이터 결과 대조 |

## 4. 측정이 뒤집은 가설 열세 가지

이 프로젝트에서 가장 값진 부분입니다. **예상하고, 재고, 틀렸음을 확인한** 기록입니다.

### ① "DB로 옮기면 빨라진다" → 조건부

단일 기간만 다루면 **CSV가 최대 1.8배 빠릅니다.** 비용을 분해해 보니
데이터를 읽는 일은 전체의 **1.4%**뿐이고, 98.6%가 SQLite→Python 경계 비용이었습니다
(셀마다 PyObject 생성 66% + DataFrame 변환 32%).

DB가 이기는 건 **저장소가 필요한 양보다 클 때**입니다 — 3개월치에서 한 달만 읽으면
2.45배 빠릅니다. 실제 운용(1년치 적재, 한 달씩 분석)이 여기 해당해서 다행이었지만,
"DB니까 빠르다"는 전제는 틀렸습니다. → [DB_PLAN.md](../구현/DB_PLAN.md) 4단계

### ② "거리 가중치를 올리면 이동거리가 는다" → 반대였다

`_05_10` **한 회차만 보고** 총 이동거리가 301→319km로 늘었다고 보고했습니다.
3회차 전부로 다시 재니 오히려 **866→814km로 51km 줄었습니다.**

greedy 탐색이라 단일 실행 결과가 흔들립니다(γ=2000에서는 오히려 악화).
단일 실행으로 판단하면 안 된다는 걸 직접 겪었습니다. → [step1 문서](../구현/steps/step1_clustering.md)

### ③ "회수하면 그 대여소에 결품이 생긴다" → 0건

Pick 대여소에서 결품이 **한 시간도 늘지 않아** 버그를 의심했는데, 검증해 보니
타당했습니다. Pick 대여소는 회수 후에도 재고 중앙값 16대인데 그 시간대 순수요가
**−0.7대**(반납이 더 많음)라 바닥날 일이 없었습니다.

반대로 Drop 대여소는 **재고 중앙값이 0대** — 절반 이상이 완전히 비어 있었고
결품이 거의 전부 거기서 났습니다. → [KPI.md](../분석/KPI.md) 3-B

### ④ "MAE가 낮으면 예측이 좋다" → 기준선을 봐야 안다

`_10_15` 시간대의 MAE가 1.14로 **네 시간대 중 가장 낮았습니다.** 그런데
"순수요 0"이라고 찍는 기준선도 1.14였습니다 — 예측이 아무 값도 못 하는 것처럼 보였습니다.

절대 오차만 봤다면 "낮 시간대 예측이 제일 정확하다"고 정반대로 판단했을 겁니다.
→ [KPI.md](../분석/KPI.md) 3-E

### ⑤ "step1이 5분 이상 걸린다" → 42초

기존 기록(버전관리 1.0.1)에 "5분 이상"이라 적혀 있어 성능 개선을 우선 과제로 뒀는데,
실데이터에서 **42초**였습니다. 작업 대상이 87곳이라 조정 반복이 빨리 수렴했습니다.
성능 최적화 우선순위를 낮췄습니다.

### ⑥ "`_10_15`의 예측은 쓸모없다" → ④번 결론 자체가 틀렸다

④번을 근거로 이 회차를 없앨지 검토하던 중, **측정 대상을 의심해 봤습니다.**
MAE는 대여소 1,369곳 전체 평균인데, 파이프라인이 실제로 손대는 곳은
`|rebal_qty| > 2`인 일부뿐입니다.

작업 대상만 놓고 다시 재니 `_10_15`의 `mu`는 오차를 **40.2%** 줄이고 있었습니다
(31곳, MAE 4.363 vs 기준선 7.300). 나머지 1,286곳은 72.8%가 `|mu| < 0.5`라
무엇으로 예측하든 결과가 같았고, 수가 압도적이라 전체 평균을 지배했던 것입니다.

바뀐 것은 데이터가 아니라 **누구를 평균에 넣었는가**뿐이었습니다.
→ [EXPERIMENTS.md](../분석/EXPERIMENTS.md) 2장

### ⑦ "`z`를 올리면 KPI가 좋아진다" → 개선률은 오히려 떨어진다

`z`를 1.65 → 1.99로 올려 전체 파이프라인을 돌리자 결품 시간은 10~27% 줄었는데
**개선률과 목표 도달률은 함께 떨어졌습니다**(예: `_10_15` 목표 도달 46.5% → 37.8%).

두 지표가 `target_qty`를 분모로 삼기 때문입니다. z를 올리면 목표 자체가 높아지니
같은 작업으로 도달하기 어려워집니다. **성능이 나빠진 게 아니라 자를 바꾼 것입니다.**

지표가 실험하려는 파라미터에 의존하면 그 실험의 판정 기준이 될 수 없습니다.
z 비교에는 목표값과 무관한 **결품 시간**을 써야 합니다. → [KPI.md](../분석/KPI.md)

### ⑧ "결품 시간은 목표값과 무관하니 무엇이든 비교할 수 있다" → 방법 비교는 못 한다

⑦에서 "z가 다른 실행은 결품 시간으로 비교하라"는 규칙을 세웠습니다. 그런데 논문용
대조군 실험(1.18.0)에서 그 결품 시간으로 네 방법을 비교하자 **전부 같은 점수(0.42h)가
나왔습니다 — 아무 것도 하지 않은 무재배치까지 포함해서입니다.**

step4가 `stock + rebal_qty`로 재배치 후 재고를 잡기 때문입니다. 즉 **계획이 100%
집행된다고 가정**한 값이라, 계획이 같고 집행만 다른 방법들은 구분되지 않습니다.
실제로 ILP는 군집 안에서 `min(총 pick, 총 drop)`만큼만 옮깁니다.

VRP가 실제로 싣고 내린 양으로 다시 재니 0.48h(제안) / 0.74h(그리디) /
1.39h(지리 균등 군집) / 2.16h(무재배치)로 벌어졌습니다
(**1.18.4 당시 값** — depot 복귀를 넣어 다시 잰 현행 수치는
[EXPERIMENTS.md](../분석/EXPERIMENTS.md) 5장에 있습니다). **같은 지표인데 무엇을
집어넣느냐로 비교 가능 여부가 갈렸습니다.** 덤으로 현행 수치가 편익을 약 13%
과대평가하고 있다는 것도 드러났습니다.

**고쳤습니다**(1.18.4) — step4가 VRP 실행 결과로 재고를 더합니다. 계획 기준 값은
`stockout_hours_plan`으로 함께 남겨 격차를 볼 수 있게 뒀습니다.
→ [EXPERIMENTS.md](../분석/EXPERIMENTS.md) 5장

### ⑨ "날씨는 이용량만 흔들고 순수요까지는 안 온다" → 온다. 단, 비 오는 날에만

날씨를 붙이기 전에 먼저 물었습니다 — 비가 오면 대여와 반납이 **함께** 줄어드니
순수요(반납 − 대여)는 그대로일 수 있지 않은가? 그러면 날씨를 넣어도 계획은 안 바뀝니다.

측정해 보니 전달됐습니다. 비 온 날 이용량은 -58~-78%이고, 재배치 필요량도
**-45~-61%** 였습니다. 도시 총량 기준 표본 밖 설명력이 0.344 → 0.756으로 올랐습니다.

**그런데 대여소 단위로 보면 평균 개선은 +4.3%뿐입니다.** 이 숫자만 인용하면 "별것
아니다"가 됩니다. 갈라 보면 완전히 다른 그림이 나옵니다 — **비 오는 날(전체의 10%)에
+40%, 나머지 90%의 날에는 +0.4%.** 날씨는 매일 조금씩 좋아지는 개선이 아니라, **비
오는 날 크게 빗나가던 것을 고치는 처방**입니다. 평균이 성격을 감춘 사례가 하나 더
늘었습니다(⑥과 같은 함정).

### ⑩ "커버리지로 예측 개선을 잴 수 있다" → 비 오는 날의 손실은 거기 안 나타난다

날씨를 피처로 넣어 분위수 모델을 다시 판정했더니 커버리지 기준으로는 여전히 맞바꿈
(커버리지↑, 과잉↑)이었습니다. 그래서 채택하지 않았는데, **왜 커버리지가 날씨의 이득을
못 잡는지**를 따져 보니 이유가 분명했습니다.

**비가 오면 필요량이 절반으로 주는데 계획은 그대로입니다.** 그러면 계획은 수요를
**덮기는 덮되 과하게 덮습니다.** 결품(커버리지)은 멀쩡해 보이고 낭비만 늘어납니다.
갈라 보니 두 검증 달 모두에서 비 온 날 과잉이 7.71 → 6.45대, 8.34 → 5.55대로 줄고
맑은 날은 오히려 늘었습니다.

지표 하나로는 못 봅니다. ⑦(z를 올리면 개선률이 떨어진다)·⑧과 같은 뿌리입니다 —
**효과와 비용을 함께 재야 하고, 무엇을 재는 지표인지 알아야 합니다.**

### ⑪ "공차 이동 63%는 낭비다" → 90%가 피할 수 없는 차고지 왕복이었다

지표 이름(`empty_distance_ratio`)만 보고 "이동의 63%가 빈 차라니 크다"고 읽었습니다.
분해해 보니 이렇습니다.

| 구성 | 비중 | 성격 |
| --- | ---: | --- |
| depot → 첫 대여소 | 31.6% | 피할 수 없음 |
| 마지막 → depot | 25.0% | 피할 수 없음 |
| **중간에 빈 차** | **6.1%** | 줄일 수 있는 부분 |

세 회차 모두 같은 모양입니다. 최적화로 줄일 수 있는 것은 **총 이동의 6%**뿐이고,
여기서 절반을 아껴도 전체의 3%입니다. **사안 목록에서 뺐습니다.**

코드 주석에 *"차고지에서 첫 대여소로 가는 구간과 복귀 구간이 기본으로 여기 들어간다"*
라고 적혀 있었는데, 읽고도 비중을 따지지 않았습니다. ⑧과 같은 종류의 실수입니다 —
**지표가 무엇을 입력으로 받는지 보지 않고 인용한 것.**

### ⑫ "작업 문턱을 조정해야 한다" → 문턱이 아예 작동하지 않고 있었다

`REBAL_MIN_QTY = 2`를 1~5로 바꿔 봤는데 후보 100곳·작업량 335대·결품이 **전부
같았습니다.** 원인은 `TOP_STATION_LIMIT`(pick·drop 각 50곳)이 **먼저 자르는** 것이었습니다.
문턱 2의 자격자가 pick 76~89곳·drop 208~298곳이니 어차피 상위 50곳만 갑니다.

**계획 규모를 정하는 손잡이가 문턱이 아니라 상한이었습니다.** 그래서 상한을 쓸어
보니 또 하나가 나왔습니다 — **50은 보유 차량 21대와 맞물린 값**입니다. 100으로
넓히면 결품은 5% 줄지만 필요 차량이 31.5대가 되어 21대로 잘리고, 그러면 군집당
일감이 5.1 → 8.3곳으로 늘어 **예산 초과 조건**이 됩니다.

> 근거가 없던 것이 아니라 **적히지 않았을 뿐**이었습니다. 파라미터가 이상해 보일 때
> "왜 이 값인가"보다 **"이 값이 실제로 쓰이고는 있는가"** 를 먼저 물어야 합니다.

### ⑬ "pick 대여소가 비어 있을 것이다" → 후보의 재고 0 비율은 0%였다

수집 재고에서 **관측의 48.8%가 재고 0**인 것을 보고, ILP의 '총 pick = 총 drop'이
종이 위에서만 성립하는 것 아닌지 의심했습니다.

재 보니 pick 후보의 **재고 0 비율은 0%**이고, 계획한 양을 못 채우는 것은 934대 중
33대(3.5%)였습니다. 당연합니다 — `pick` 후보는 `rebal_qty < 0`, 즉 **"여기 자전거가
넘친다"로 골라낸 집합**입니다. 그중에 빈 대여소가 있을 리 없습니다.

**전체 평균을 부분집합에 그대로 적용한 오독**이었습니다. ⑥에서 똑같은 함정을 겪고
문서로 남겨 뒀는데도 다시 밟았습니다.

## 4-보론. 실험이 남긴 규칙

일곱 번의 뒤집힘에서 반복되는 것이 있습니다.

1. **"필요한 값"을 계산했으면 그 값을 다시 적용해 확인한다.** 백테스트가 내놓은
   "필요 z ≈ 1.99"는 월별 필요값의 평균이었고, 실제로 z=1.99를 적용하면 94.9%로
   95%에 못 미쳤습니다.
2. **평균을 낼 때 누구를 넣었는지 확인한다.** ⑥이 여기서 나왔습니다.
3. **편익만 재면 언제나 "더 크게"가 답이 된다.** z도 γ도 편익 곡선만 보면
   올릴수록 좋습니다. 비용을 같이 재야 멈출 곳이 보입니다.
4. **파라미터 곡선이 매끄러울 것이라고 가정하지 않는다.** γ=2000이 γ=1000보다
   나빴습니다(두 번의 실험 모두에서). 두 점을 재고 사이를 추측하면 못 찾습니다.
5. **한 회차·한 실행으로 판단하지 않는다.** ②에서 한 번 겪고, γ=3000 결정 때
   같은 실수를 반복하지 않으려 3회차 전부로 재확인했습니다.
6. **대조군 없이 "좋다"고 말하지 않는다.** 자기 전후 비교로는 65%든 78%든 자기
   계획을 자기 자로 잰 것입니다. ⑧이 여기서 나왔습니다.
7. **지표가 무엇을 입력으로 받는지 본다.** 같은 '결품 시간'이라도 계획량을 넣으면
   방법 비교가 불가능하고, 집행량을 넣으면 가능합니다.
8. **비율을 인용하기 전에 분해한다.** '공차 63%'는 90%가 차고지 왕복이라 실제로
   줄일 수 있는 것은 6%였습니다(⑪). 큰 비율일수록 무엇으로 이뤄졌는지 먼저 봅니다.
9. **파라미터를 조정하기 전에 그것이 쓰이고 있는지 확인한다.** 작업 문턱을 다섯 값으로
   재는 동안 결과가 한 번도 안 바뀌었는데, 상한이 먼저 자르고 있었습니다(⑫).
10. **부분집합에 전체 평균을 적용하지 않는다.** ⑥에서 겪고 문서로 남겼는데 ⑬에서
   다시 밟았습니다. 규칙을 아는 것과 그 순간에 떠올리는 것은 다릅니다.

| 표준 `sqlite3` | SQLAlchemy | pandas 계층 코드가 동일해 이점이 없었음. 교체 지점을 `connect()` 하나로 격리 | PostgreSQL 전환 시 그 함수만 수정 |
| CSV·DB 이중 기록 | 즉시 전환 | 되돌릴 수 있고, 중간에 멈춰도 안전 | 전환기 동안 코드 중복 |
| `kmedoids` (Rust) | `scikit-learn-extra` | 후자는 아카이브돼 3.12+ 설치 불가 | 결과가 미세하게 다를 수 있음 |
| 누적 부하 기반 로테이션 | 고정 순번표 | 정비로 차량이 빠지거나 회차 수가 바뀌어도 규칙이 성립 | 다음 출동 차량을 미리 못 정함 |
| 요구사항 하한(`>=`) 고정 | 상한 고정 | 새 Python에서 휠이 없어 설치가 통째로 깨지는 걸 겪음 | 상위 버전 호환은 미보장 |
| 파이썬 단독 웹(FastAPI) | React + API | 핵심 자산이 pandas·PuLP. JSON API를 미리 분리해 나중에 교체 가능 | 지도 인터랙션 제한 |
| 날씨는 **알림만**, 계획은 그대로 | `target_qty`에 자동 반영 | 예보가 빗나가면 결품이 난다. 작업지시서와 같은 성향 — 판정만 하고 계획을 바꾸지 않는다 | 측정된 이득(비 오는 날 -40% 오차)을 자동으로는 못 얻는다 |
| 과거 날씨는 **포털 CSV**, 실시간만 API | 전부 API로 | 1년치가 8,760시간인데 API는 한 시각씩 준다 | 자료 갱신이 수동이다 |
| 문서를 **읽는 사람 기준**으로 분류 | 파이프라인 단계 기준 | 문서 절반이 여러 단계에 걸쳐 있어 단계로는 못 나눈다 | 코드에서 문서를 찾을 때 한 번 더 생각해야 한다 |

## 6. 지금 알고 있는 한계

**모델**
- ~~`z = 1.65`가 부족합니다~~ → `z = 1.99`로 조정 (커버리지 94.9%)
- ~~`_10_15` 회차의 예측은 기준선과 차이가 없습니다~~ → 측정 오류였습니다 (4장 ⑥)
- ~~**계절 전환기(2월→3월) 커버리지 86.5%**~~ → **계절 보정(warmup) 구현으로 완화
  (1.15.1)**. 계획 대상 달 첫 14일 실적으로 도시 전체 배율을 구해 `mu`·`sigma`에
  곱합니다(26년 2→3월 `_05_10` 커버리지 88.7% → 94.7%). 다만 배율은 **도시 전체 하나**라
  대여소별 계절 반응 차이는 여전히 못 따라갑니다
- z=1.99에서도 커버리지는 94.9%로, 설계 의도 95%에 여전히 조금 못 미칩니다
- ILP는 직선거리(Haversine), VRP는 greedy 휴리스틱
- 차량이 여러 클러스터를 순차 처리하지 못함 (회차당 1대 = 1클러스터 고정)
- 시간 예산이 **제약이 아니라 사후 점검**입니다

**측정**
- 결품 시뮬레이션은 실측이 아니라 복원입니다. 초기 재고(API 현재 스냅샷)와
  순수요(25년 11월)의 시점이 다르고, 재고를 0에서 잘라 **결품의 하한**입니다.
  → **1.21.0에서 처음 숫자로 확인했습니다** — 수집한 재고로 직접 세니 `_10_15`
  작업 대상 기준 복원 1.73h vs 실측 **1.97h(+13%)** 입니다. 방향은 예상대로였고,
  크기는 **수집 하루치로 낸 잠정값**입니다([KPI.md](../분석/KPI.md) 부록)
- `improvement_rate`는 계획 달성률이지 이용자 편익이 아닙니다

**운영**

- 작업 시간 30초/대는 현장 확인이 필요한 가정값입니다. 회차당 투입 상한은 1.19.1에서
  10 → 보유 대수로 열었고 **실제 대수는 작업량이 정합니다**([FLEET.md](../구현/FLEET.md))
