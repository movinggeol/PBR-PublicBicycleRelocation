# 실도로 소요시간 수집 — 고정 패널 반복 관측

TMAP에서 **매일 같은 구간**의 실도로 소요시간을 받아 쌓습니다.
운영 문서입니다 — **왜 이 값이 필요한가**와 실험 결과는
[EXPERIMENTS.md 9장](../분석/EXPERIMENTS.md)이 정본입니다.

- 수집기: [`tools/collect_road_time.py`](../../tools/collect_road_time.py)
- 스케줄러: [`scripts/road_collector.ps1`](../../scripts/road_collector.ps1)
- 패널: [`tools/road_panel.json`](../../tools/road_panel.json) (git으로 나릅니다)
- 재고 수집기는 [COLLECTOR.md](COLLECTOR.md) — **다른 수집기입니다.** 성격이 많이 다릅니다(7장).

> **어느 환경이 이걸 돌리고 있나**는 [두_PC_작업.md 0장](두_PC_작업.md)이 정본입니다.
> 2026-09-03 기준 **집환경(B)만** 돕니다.

---

## 1. 왜 모으는가

묻는 것은 하나입니다 — **이동시간 모형의 계수가 날마다 안정적인가.**

5-F장에서 `이동시간 = 275초 + 직선km × 3600/27.3`이 상수 속도(25km/h)보다
표본 밖 오차를 42% 줄인다는 것을 쟀지만 **하루치 한 번**이었습니다. 그래서
`USE_ROAD_MODEL`을 켜지 않고 남겨 두었습니다. 이 수집기는 그 "하루치"를
여러 날로 늘리는 장치입니다.

### 파이프라인 실행분으로는 답할 수 없다

`road_leg`에는 step3이 지도를 그리며 받은 실측이 **이미** 쌓입니다.
그런데 그것으로 계수의 안정성을 물으면 답이 나오지 않습니다.

**계획이 매일 바뀌면 잰 구간도 매일 바뀌기** 때문입니다. 계수가 흔들렸을 때

    ① 교통 상황이 달라져서인지   ← 알고 싶은 것
    ② 잰 구간이 달라져서인지     ← 잡음

를 가를 방법이 없습니다. 그래서 **고정 패널**을 씁니다 — 한 번 정한 구간
목록을 매일 그대로 다시 잽니다. 그러면 날짜 사이의 차이는 오직 교통 차이입니다.

## 2. 확정 사양

| 항목 | 값 | 왜 |
| --- | --- | --- |
| 패널 크기 | 사슬 **5개** × 지점 21 = **회차당 100구간** | `CHAIN_COUNT` · `HOPS_PER_CHAIN` |
| 회차 | `_05_10` `_10_15` `_15_20` `_20_05` **4개** | `project_config.DURATIONS` |
| 하루 호출 | **20건** (사슬 5 × 회차 4) | 사슬 1개 = TMAP 1호출 |
| 저장 테이블 | `road_leg` | 파이프라인 실행분과 **같은 표**에 쌓입니다 |
| 라벨 | `roadprobe-YYYY-MM-DD` | `PROBE_PREFIX` — 실행분과 가르는 유일한 표식 |
| 패널 씨앗 | `42` (`PANEL_SEED`) | 결정적으로 만들기 위해 |
| 패널 지문 | `0bd56c9eec4d` | **환경 사이에 이 값이 같아야** 함께 분석할 수 있습니다 |

### 왜 사슬로 끊는가

**한 사슬 = TMAP 호출 1회.** 경유지 30개 상한 안에 들도록 끊으면
`routeSequential30`으로 처리되는데, 이 엔드포인트는 **100짜리와 한도가 따로
잡힙니다.** 지점을 한 줄로 길게 늘어놓는 것보다 쿼터를 아낍니다.

## 3. 패널 설계 — 무엇을 재는 구간으로 골랐나

`build_panel()`이 `PANEL_SEED`로 결정적으로 만듭니다.

**① 차고지에서 시작해 차고지로 돌아옵니다.**
실제 경로에서 차고지 왕복이 총 이동거리의 61~65%를 차지하므로
(EXPERIMENTS 8장), 차고지 구간이 빠진 패널은 실제를 대표하지 못합니다.

**② 거리 구간을 골고루 채웁니다.**
배율이 거리에 크게 의존하기 때문입니다 — 5-F장 실측으로 0.5km 미만은 유효
5.6km/h, 10km 이상은 23.1km/h입니다. 짧은 구간만 모이면 **고정비 계수**가,
긴 구간만 모이면 **속도 계수**가 잡히지 않습니다.

목표 거리 `TARGET_KM_CYCLE = (0.3, 0.75, 1.5, 3.5, 7.5, 15.0)`을 순환시키며
**그 거리에 가장 가까운 대여소**를 다음 지점으로 고릅니다.

현재 패널의 거리 분포:

| 구간 | 0~0.5 | 0.5~1 | 1~2 | 2~5 | 5~10 | 10~20 | 20+ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 구간 수 | 14 | 15 | 16 | 18 | 15 | 19 | 3 |

**③ 한 번 만들면 다시 만들지 않습니다.** 수집 도중에 패널이 바뀌면 그때까지
쌓은 것이 비교 불가능해집니다. `--rebuild-panel`은 그래서 경고를 답니다.

> ⚠️ **패널은 `tools/`에 둡니다** — `data/`는 `.gitignore`라 환경마다 **다른
> 패널**이 생깁니다. 실제로 그렇게 어긋났고(9-1장), 그래서 git으로 나르게
> 바꿨습니다(1.26.52). `test_panel_lives_where_git_carries_it`이 고정합니다.

## 4. 시각 처리 — `startTime`이 전부다

`start_time_for(duration, day_type=...)`가 **다음 `day_type` + 회차 첫
시각**을 만듭니다(`_05_10` → 05시). TMAP은 이 값으로 **그 시각의 교통량**을
정합니다.

여기서 몇 가지가 따라 나옵니다.

**① 하루 중 아무 때나 돌려도 됩니다.** 09시에 부르든 21시에 부르든 받는 값은
같습니다 — 재고 수집기와 달리 **창 가드가 없는** 이유입니다. 그래서
"몇 시에 도느냐"가 아니라 **"그날 받았느냐"**만 중요합니다.

**② 같은 `day_type`끼리만 받아야 합니다.** `weekday`면 다음 평일, `holiday`면
다음 토·일·공휴일을 가리킵니다 — 토요일에 받은 `weekday` 값은 존재하지
않고(다음 평일로 밀립니다), 반대로 `holiday`로 평일에 받아도 다음 휴일로
밀립니다. **다른 `day_type`끼리 섞으면 표본이 부풀어 오릅니다** — 평일
월~금이 화·수·목·금·**월**을 가리켜 다섯 요일을 고르게 덮는 것과 같은
이치로, 토·일·공휴일도 서로 다른 날을 고르게 가리켜야 합니다.

> ✅ **휴일 수집을 시작했습니다 (2026-09-08, 1.26.158).** 예전에는 `day_type`
> 인자가 없어 **언제나 다음 평일**만 만들었고, `--if-needed`가 주말이면
> 통째로 건너뛰었습니다. 이제는 `--day-type`을 안 주면 **그 날짜의 실제
> 요일**로 자동 판정합니다 — 평일이면 weekday, 주말·공휴일이면 holiday
> 계수를 잽니다. 스케줄 트리거도 월~금에서 전요일로 넓혔습니다
> ([road_collector.ps1](../../scripts/road_collector.ps1)).
>
> **평일과 휴일은 `run_label`이 아니라 `runs.day_type`으로 갈립니다.**
> 휴일분 라벨은 `roadprobe-holiday-YYYY-MM-DD`로 접두어가 붙어 사람이 봐도
> 구분되지만, 회귀 스크립트는 반드시 `road_time_model.py --day-type`으로
> 걸러야 합니다 — 이 저장소 전체가 지키는 "평일과 휴일은 절대 섞지 마라"
> 규약이 이동시간에도 적용됩니다(EXPERIMENTS.md 9장 참고).

## 5. 스케줄 — 켜져 있을 때 알아서 한 번 (1.26.105)

### 예전 방식과 무엇이 달랐나

원래는 **평일 03:30 한 번**이었습니다. 새벽에 TMAP 한도를 파이프라인보다 먼저
조금 떼어 두려는 것이었는데, **새벽에 PC를 켜 두지 않는 환경에서는 그날을
통째로 잃었습니다.** `StartWhenAvailable`이 아침에 뒤늦게 깨우지만 그마저
끊기면 끝입니다 — 2026-09-03이 실제로 그렇게 비었습니다(08:29에 깨어났다가
`0x40010004`로 중도 종료).

### 지금 방식

**하루에 여러 번 깨우되, 필요할 때만 부릅니다.**

| 트리거 | 언제 |
| --- | --- |
| 시각 슬롯 | **매일(휴일 포함) 09:00 · 12:00 · 15:00 · 18:00 · 21:00** (`-Slots`로 바꿉니다) |
| 로그온 | 켠 지 **3분 뒤** (슬롯을 다 놓친 날의 안전망) |

> ✅ **전요일로 넓혔습니다 (2026-09-08, 1.26.159).** 예전에는 트리거가
> 월~금이었고 `--if-needed`가 주말을 스스로 걸렀습니다. 이제
> `start_time_for()`가 `day_type`을 받아 휴일이면 '다음 토·일·공휴일'을
> 만들 수 있으므로, 주말·공휴일도 **휴일 계수로** 잽니다(4장 ②).

작업은 수집기를 `--if-needed`로 부릅니다. 이 옵션이 셋을 봅니다.

1. **`--day-type`을 안 주면 그날의 실제 요일로 자동 판정합니다.** 평일이면
   평일 계수, 주말·공휴일이면 휴일 계수를 잽니다(4장 ②).
2. **이미 채운 회차는 건너뜁니다.** 회차마다 100구간이 다 있으면 다시 부르지
   않습니다. 네 회차가 다 차 있으면 **TMAP을 한 번도 부르지 않고** 끝납니다.
3. **모자란 회차만 채웁니다.** 한도 소진·네트워크 실패로 잘린 회차가 있으면
   그것만 다시 부릅니다 — 다 받은 회차를 지우고 새로 받으면 호출을 두 배로
   쓰게 됩니다.

> 📌 **그래서 슬롯을 늘려도 비용이 없습니다.** 같은 날 몇 번을 깨워도 호출은
> 하루 20건을 넘지 않습니다. 그날 처음 성공한 실행만 호출을 쓰고, 나머지는
> 즉시 끝납니다.

**사람이 손으로 돌릴 때(옵션 없이)는 예전처럼 전부 다시 받습니다** — 일부러
새로 재려는 의도로 봅니다.

## 6. 운영 명령

```powershell
.\scripts\road_collector.ps1 install                    # 등록 (관리자 권한 필요)
.\scripts\road_collector.ps1 install -Slots 10:00,16:00 # 시각을 직접 정한다
.\scripts\road_collector.ps1 status                     # 스케줄 + 쌓인 현황
.\scripts\road_collector.ps1 now                        # 지금 모자란 회차만
.\scripts\road_collector.ps1 now -Full                  # 그날 것을 전부 다시
.\scripts\road_collector.ps1 pause                      # 일시정지 (데이터는 남는다)
.\scripts\road_collector.ps1 resume
.\scripts\road_collector.ps1 uninstall                  # 작업 삭제 (데이터는 남는다)
```

수집기를 직접 부를 수도 있습니다.

```bash
python tools/collect_road_time.py --status          # 쌓인 현황
python tools/collect_road_time.py --dry-run         # 호출 계획만
python tools/collect_road_time.py --if-needed       # 모자란 회차만
python tools/collect_road_time.py --durations _05_10,_10_15
python tools/collect_road_time.py --date 2026-09-04 # 라벨 날짜를 직접
```

> ℹ️ **권한** — 이미 등록된 작업을 다시 걸거나(`install` 재실행) 켜고 끄는 것은
> 일반 권한으로 됩니다(2026-09-03 실측). **작업을 처음 만들 때**는
> `Access is denied`가 날 수 있는데, 그때만 관리자 권한 PowerShell로 한 번
> 돌리면 됩니다.

**데이터를 지우는 명령은 없습니다.** `pause`·`uninstall` 모두 스케줄만 건드립니다.

## 7. 재고 수집기와 무엇이 다른가

같은 "수집기"라는 이름이지만 성격이 반대인 곳이 많습니다.
[COLLECTOR.md](COLLECTOR.md)의 규칙을 그대로 옮겨 오면 안 됩니다.

| | **재고** (`collect_stock.py`) | **도로** (이 문서) |
| --- | --- | --- |
| 무엇이 값을 정하나 | **부른 시각** — 그때의 재고 | **`startTime`** — 부른 시각과 무관 |
| 창 가드 | 있음 (07:00–22:00) | **없음** — 아무 때나 |
| 놓친 틱 | 10분 뒤 다음 틱이 온다 | **하루치가 통째로 걸린다** |
| `StartWhenAvailable` | 끔 | **켬** |
| 비용 | 무료 API | **유료 TMAP · 일일 한도** |
| 하루 호출 | 90틱 × 대여소 | **20건** |
| 두 환경이 겹치면 | **안전** — 병합 때 `INSERT OR IGNORE`로 걸러진다 | **낭비** — 표본은 안 늘고 한도만 두 배 |
| 분담 | **안 나눈다** — 둘 다 매일 07:00–23:00, 켜져 있는 만큼 | **한 환경만** 돌린다 |

> 🔴 **도로 수집기는 두 환경에서 동시에 돌리지 마십시오.** 패널이 git으로
> 공유되고 `startTime`도 같아서 **두 환경이 사실상 같은 값을 받습니다.**
> 표본은 안 늘고 한도만 두 배로 씁니다. 키를 공유한다면 그만큼 잘립니다.

## 8. 한도가 소진되면 — 잘리는 자리를 돌린다 (1.26.104)

한도가 소진되면 `collect()`가 **그 자리에서 멈춥니다**(`return saved`).
회차 순서가 늘 같으면 **잘리는 자리도 늘 같아서**, 마지막 회차만 관측이 계속
모자랍니다. 실제로 `roadprobe-2026-09-01`이 앞의 셋만 100구간씩 받고 `_20_05`를
통째로 잃었습니다(300 / 400구간).

그래서 `rotate_durations()`가 **날짜로 순서를 돌립니다.**

- 날짜 기준이라 **같은 날 다시 돌리면 같은 순서**입니다(멱등).
- 평일만 도는 스케줄에서도 네 회차가 고르게 마지막에 섭니다(평일 20회 기준 5·5·5·5).
- `--durations`로 직접 고른 경우에는 **돌리지 않습니다** — 사람이 정한 순서가 의도입니다.

열흘을 채워도 특정 창만 표본이 적으면 **사전 등록 기준(회차별 변동계수)을
회차별로 견줄 수 없습니다.** 이것이 순서를 돌리는 이유입니다.

### 9-1. 첫날은 다른 패널로 모았다 (2026-09-01)

| 날짜 | 구간 | 지금 패널과 일치 | 회차 |
| --- | ---: | ---: | --- |
| 09-01 | 300 | **69** (사슬 1~4 어긋남) | 3개 (`_20_05` 없음) |
| 09-02 | 400 | **100** ✅ | 4개 |
| 09-03 | — | — | **없음** (중도 종료) |

패널을 git으로 나르게 한 것이 08-31 18:24(1.26.52)인데, 회사환경의 수집은
**09-01 03:30**에 돌았습니다. 그 시각에는 아직 그 커밋을 받지 않아 **로컬에서
만든 패널**로 쟀습니다.

**69구간은 겹치므로 통째로 버릴 필요는 없습니다** — 다만 *"같은 구간을 매일
다시 잰다"* 는 전제가 09-01에만 부분적으로 깨져 있으니 **회귀에 넣기 전에
`--status`로 확인**하십시오. `warn_if_panel_drifted()`가 스스로 알립니다.

📌 **판정에 쓸 10일은 09-02부터 셉니다.**

### 9-2. 판정 기준은 미리 박아 두었다

**10일 이상(가급적 서로 다른 요일)**이 쌓여야 둘 다 잴 수 있습니다.

### 9-2-A. 이 데이터가 실제로 계획에 반영되는 경로 (2026-09-08 정리)

🔴 **지금 이 순간, 쌓인 도로 데이터는 계획 계산에 전혀 쓰이지 않습니다.**
ILP·VRP 모든 단계가 거리를 시간으로 바꿀 때 부르는 함수는
`project_config.travel_seconds()` 하나뿐인데, 안에 스위치가 있습니다.

```python
def travel_seconds(km, speed_kmph=None):
    if USE_ROAD_MODEL:                                    # 기본 꺼짐
        return ROAD_FIXED_SEC + km * 3600.0 / ROAD_SPEED_KMPH  # 실측 계수
    return km / speed_kmph * 3600.0        # 지금 실제로 쓰는 식(직선÷25km/h)
```

`USE_ROAD_MODEL`은 **기본값이 꺼짐**이고, `.env`에 `PBR_USE_ROAD_MODEL=1`을
사람이 명시적으로 넣어야 켜집니다. 즉 흐름은 이렇습니다.

```text
collect_road_time.py  →  road_leg에 실측 쌓기
        ↓
road_time_model.py     →  9-2 기준으로 판정 (사람이 결과를 읽는다)
        ↓ 통과 + 10일 이상이면
사람이 .env에 PBR_USE_ROAD_MODEL=1 · PBR_ROAD_FIXED_SEC=... ·
       PBR_ROAD_SPEED_KMPH=... 를 직접 씀
        ↓
travel_seconds()가 그때부터 실측 계수를 씀 → ILP·VRP 계산이 바뀐다
```

**자동으로 켜지지 않습니다.** 이유는 지금까지의 모든 대조군 비교·`z`·`γ`
실험이 전부 "직선÷25km/h" 위에서 나온 값이기 때문입니다 — 상수를 자동으로
갈아치우면 그 실험들의 재현성이 조용히 깨집니다. 판정이 통과해도 **사람이
결정하고 손으로 켜는 것**이 지금 설계입니다.

✅ **구조는 나눠 두었습니다 (2026-09-08, 1.26.160).** `travel_seconds()`가
`day_type`을 받아 `ROAD_FIXED_SEC_WEEKDAY/HOLIDAY`·
`ROAD_SPEED_KMPH_WEEKDAY/HOLIDAY` 두 쌍 중 하나를 고릅니다. ILP·VRP·
군집 K 추정 셋 다 `config.day_type`(그 실행이 평일 계획인지 휴일 계획인지)을
그대로 넘깁니다. 🔴 **다만 지금은 휴일 쌍이 실질적으로 아무 값도 아닙니다**
— `PBR_ROAD_FIXED_SEC_HOLIDAY`·`PBR_ROAD_SPEED_KMPH_HOLIDAY`를 사람이
채우기 전까지는 평일 계수로 조용히 폴백합니다. 채택 판정에 쓸 휴일 표본이
아직 없어서입니다(위 9-2-A). 옛 이름 `PBR_ROAD_FIXED_SEC`·
`PBR_ROAD_SPEED_KMPH`(접미사 없음)는 평일 값의 폴백으로 계속 읽습니다 —
기존 `.env`가 조용히 무시되지 않습니다.

### 11-1. 실제 스케줄러 등록이 문서와 어긋나 있었다 (2026-09-08 발견)

🔴 **코드를 고쳐도 스케줄러가 옛 설정 그대로면 반영되지 않습니다.** 1.26.159
직후 이 PC의 `PBR도로시간수집`을 직접 조회해 보니 **5장의 "지금 방식"이
아니라 그 이전(1.26.105 이전) 상태**로 등록돼 있었습니다.

```text
등록된 트리거: 월~금 03:30 딱 한 번
등록된 인자:   collect_road_time.py   (--if-needed 없음)
```

그런데도 지금까지 매일 정상적으로 수집돼 온 것처럼 보인 이유는
`StartWhenAvailable=True`입니다 — 03:30에 PC가 꺼져 있으면 **켜지자마자
그 놓친 실행을 대신 돌립니다.** 실제 `road_leg.observed_at`을 보면 매일
07:05~08:30 사이 한 번, 그날 몫(400구간·20호출)을 통째로 받아 왔습니다.
`--if-needed`가 없으니 이미 채웠는지 안 보고 **매번 전부 다시 받습니다** —
지금까지는 하루 한 번뿐이라 20호출 한도 안에 있었지만, 문서가 설명하는
"여러 번 깨워도 안전하다"는 안전망은 이 PC에 없었던 것입니다.

**일반 권한 셸에서 `.\scripts\road_collector.ps1 install`을 돌리면 실패합니다**
— `Register-ScheduledTask`가 기존 작업을 덮어쓸 때 `Access is denied`
(`CimException`)를 냅니다. 🔴 **처음엔 스크립트가 이 실패를 숨겼습니다** —
스크립트 전역에 `$ErrorActionPreference = 'Stop'`이 있었지만
`Register-ScheduledTask` 호출 자체에는 `-ErrorAction`을 안 줬습니다. **CIM
기반 cmdlet은 자기 호출에 `-ErrorAction`이 없으면 전역 설정 대신 자신의
기본값(Continue)을 따릅니다** — 그래서 오류 텍스트가 화면에 찍힌 뒤 바로
다음 줄부터 계속 실행돼 "[등록] ..." 안내가 그대로 떴습니다(재현해서
`CimException`이 `-ErrorAction Stop`을 명시했을 때는 정상적으로 잡히는
것을 확인했습니다 — 즉 전역 설정이 무력화된 게 아니라 애초에 그 호출에
적용된 적이 없었습니다). **`Register-ScheduledTask` 호출에 `-ErrorAction
Stop`을 명시해 고쳤습니다(1.26.160)** — CIM 기반 cmdlet을 부를 때는
전역 `$ErrorActionPreference`에 기대지 말고 그 호출에 직접
`-ErrorAction`을 주어야 합니다.

**관리자 권한 PowerShell에서(반드시 프로젝트 폴더로 `cd`한 뒤) 실행하면
성공합니다.** 2026-09-08에 실제로 확인했습니다.

```powershell

.\scripts\road_collector.ps1 install
```

```text

```

> 1.26.160부터는 그 실패가 안내 문구를 찍기 전에 스크립트를 **멈춥니다.**

### 11-2. 새 필터가 옛 표본을 조용히 버렸다 (2026-09-09, 1.26.161)

🔴 **`--status`는 7일이라 하는데 모형은 1일이라고 했습니다.** 1.26.160에서
`road_time_model.py`에 평일·휴일 필터(`runs.day_type`)를 넣었는데, 그 컬럼은
**1.26.159에서 처음 기록하기 시작**한 것이었습니다. 그 전 6일(08-31~09-08)은
전부 NULL이고, SQL에서 `NULL == 'weekday'`는 참이 아니므로 **판정용 표본이
5일에서 1일로 줄었습니다.**

```text
고친 뒤: [weekday] 구간 2607개 · 날짜 7일 (2026-08-31 ~ 2026-09-09)
고치기 전: [weekday] 구간 400개 · 날짜 1일 (2026-09-09 ~ 2026-09-09)
```

**라벨이 사실을 알고 있었습니다** — 휴일분만 `roadprobe-holiday-`를 달므로,
접두어가 없으면 평일분입니다. 그래서 **기록이 있으면 기록을, 없으면 라벨을**
쓰도록 고쳤습니다.

📌 **컬럼을 새로 만들면 그 이전 자료는 전부 NULL이라는 것**을 잊기 쉽습니다.
특히 이번처럼 **판정을 코앞에 둔 자리**에서는, 필터 하나가 표본을 조용히
지워도 스크립트는 아무 경고 없이 계수를 내놓습니다. 두 도구(`--status`와
모형)가 **다른 날짜 수를 말하면 그 자체가 신호**입니다.
