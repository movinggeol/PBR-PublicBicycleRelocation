# 두 PC로 번갈아 작업하기 — 무엇을 옮기고 무엇을 옮기지 않는가

> 2026-08-31 정리. 회사 노트북과 개인 노트북 두 곳에서 같은 저장소를 번갈아
> 쓸 때, `.gitignore`에 걸린 것들을 어떻게 다룰지 정합니다.

**결론부터: 매번 동기화할 것은 없습니다.** 초기 1회 세팅만 하면 이후는 git
`push`/`pull`로 충분합니다. `.gitignore`에 걸린 것들은 성격이 네 가지로 갈리고,
**그중 손으로 옮겨야 하는 것은 원본 데이터와 `.env` 둘뿐입니다.**

> 이 문서는 **개발을 번갈아 하는** 경우를 다룹니다. **지금 어느 환경이 무엇을
> 수집하는지는 아래 0장이 정본입니다.** 겹쳐도 안전한 이유와 병합 명령은
> [COLLECTOR.md 11장](COLLECTOR.md#11-두-번째-pc가-휴일을-맡는다-2026-08-27-1250·1254)에
> 있습니다(그 장의 *A=평일 / B=휴일* 분담은 2026-09-03에 폐기됐습니다).

## 0. 지금 어느 환경이 무엇을 맡고 있나 (2026-09-03)

**이 절이 수집 분담의 정본입니다.** 수집기를 켜고 끌 때 여기를 먼저 고치십시오 —
어느 환경이 도는지 모르면 **같은 값을 두 번 받거나, 아무도 안 받습니다.**

| | **회사환경 (A)** | **집환경 (B)** |
| --- | --- | --- |
| 부르는 이름 | 회사 노트북 · 지금까지 "A PC" | 개인 노트북 · 지금까지 "B PC" |
| **재고 수집** | ✅ **활성** — 매일(휴일 포함) **07:00–23:00** · 10분 | ✅ **활성** — **같은 설정** |
| **도로 수집** | ⏸ **일시정지** (2026-09-03) | ✅ **활성** — 평일 슬롯 + 로그온 |
| 실제 켜져 있는 때 | 대략 **08:30–17:30** | 대략 **18:00–23:00** |
| 작업 이름 | `PBR재고수집` · `PBR도로시간수집` | 같음 |

등록 명령은 양쪽 모두 같습니다.

```powershell
.\scripts\collector.ps1 install -Window 07:00-23:00 -IncludeHolidays
```

### 왜 재고는 둘 다 같은 창인가

**요일이나 시간으로 나누지 않습니다** (2026-09-03 사용자 결정). 양쪽 모두
매일 07:00–23:00으로 걸어 두고, **실제로 켜져 있는 동안 모이는 것이 곧 이득**입니다.

- 회사환경은 낮(08:30–17:30), 집환경은 저녁(18:00–23:00)에 켜져 있어
  **자연스럽게 하루를 나눠 덮습니다.** 창을 손으로 자를 필요가 없습니다.
- **겹쳐도 안전합니다.** `tick_of()`가 같은 격자로 반올림하므로 두 환경의 09:10은
  같은 키가 되고, `merge_stock.py`가 `INSERT OR IGNORE`로 합칩니다 —
  중복은 병합 때 걸러집니다(COLLECTOR.md 11-1장).
- 창을 좁게 자르면 **가동 시간이 바뀔 때마다 다시 등록**해야 하고, 그 사이가
  구멍으로 남습니다. 넓게 걸어 두면 켜져 있는 만큼 저절로 채워집니다.

> ⚠️ **이것은 관측을 남기는 범위지 분석의 `--day-type`이 아닙니다.** 평일과 휴일을
> 섞어 통계를 내지 말라는 규약은 그대로입니다(COLLECTOR.md 3장).

> 🔴 **한쪽 PC에서는 `--status`가 영원히 "결측"이라고 말합니다.** 창이 07:00–23:00
> (하루 97틱)인데 회사환경은 낮만, 집환경은 저녁만 켜져 있기 때문입니다 —
> 2026-09-03 기준 회사환경은 하루 49~61틱이고 **온전한 날이 0일**입니다.
> **고장이 아닙니다.** 온전함은 `merge_stock.py`로 **합친 뒤에야** 판정할 수
> 있습니다. 한쪽 숫자만 보고 창을 다시 좁히지 마십시오.

### 왜 도로는 한 환경만인가

패널이 git으로 공유되고 `startTime`도 같아서 **두 환경이 사실상 같은 값을
받습니다.** 재고와 달리 **표본이 늘지 않는데** TMAP 유료 한도만 두 배로 씁니다 —
키를 공유한다면 그만큼 잘립니다.

집환경이 맡는 이유는 **가동 시간**입니다. 도로 수집은 재고와 달리 **하루치가
통째로 걸려 있어**(놓치면 그날이 빕니다) 늦게까지 켜져 있는 쪽이 유리합니다.

> 📌 **2026-09-03에 회사환경의 도로 수집을 껐습니다.** 그날 집환경에 등록(1.26.103)하면서
> 두 곳이 동시에 도는 상태가 됐기 때문입니다. 데이터는 지우지 않았고, 작업도
> `pause`라 되살릴 수 있습니다(`road_collector.ps1 resume`).

### 이미 모은 것은 어디에 있나

**도로 관측 2일치(09-01·09-02)는 회사환경 DB에만 있습니다.** 집환경으로
분석을 옮기려면 [DB_이관.md](DB_이관.md)의 `tools/transfer_run.py`로 날라야
합니다. 아직 옮기지 않았습니다.

**재고는 양쪽에 따로 쌓이므로 `tools/merge_stock.py`로 합쳐야 합니다.**
2026-09-03 기준 회사환경 DB에는 **평일 08-25~09-03치만** 있고 휴일이 한 건도
없습니다 — 집환경분을 아직 합치지 않았기 때문입니다.

### 바꿀 때 할 일

1. 수집기를 켜거나 끕니다(`road_collector.ps1` · `collector.ps1`).
2. **위 표를 고칩니다.**
3. 도로 수집을 옮겼다면 **양쪽의 패널 지문이 같은지** 확인합니다 —
   `python tools/collect_road_time.py --status`의 `지문` 줄.

## 2. 옮기면 안 되는 것 — 가상환경과 캐시

`.venv/`를 복사하면 **깨집니다.** 안의 스크립트에 파이썬 실행 파일 경로가
절대경로로 박히기 때문입니다. 사용자 이름이 다른 PC로 옮기면 그 경로가 없습니다.

각 PC에서 새로 만드는 것이 정답이고, 그 방법은 이미 [README.md 설치](../../README.md#설치)에
있습니다. `requirements.txt`가 커밋되어 있으므로 **이것이 사실상의 동기화 장치**입니다.

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -r requirements-dev.txt   # 테스트까지 돌리려면
```

> ⚠️ **버전을 맞추세요.** 두 PC의 파이썬이 다르면 한쪽에서만 나는 버그를 쫓게
> 됩니다. 검증된 조합은 [README.md 검증된 환경](../../README.md#검증된-환경-2026-08-10-전체-파이프라인-e2e-확인)에
> 표로 있습니다(Python 3.14.7 기준). `requirements.txt`는 하한(`>=`)만 걸므로
> **설치 시점이 다르면 버전이 갈릴 수 있습니다** — 한쪽에서 이상하면 먼저
> `pip freeze`로 양쪽을 대조하세요.

`__pycache__/`는 두면 오히려 해롭습니다 — 파이썬 버전이 다르면 무시되고, 같으면
낡은 바이트코드가 새 소스를 가릴 여지가 있습니다. 지우면 다음 실행에서 다시 만듭니다.

## 3. `.env` — 키 이름은 git이, 키 값은 손이 나른다

**`.env`는 절대 커밋하지 않습니다.** API 키가 들어 있고, 한 번 올라가면 이력에
남아 지워도 남습니다.

대신 [.env.example](../../.env.example)이 **키 이름과 설명을 나릅니다.** 이 파일은
커밋되므로 새 PC에서는 이것을 복사해 값만 채우면 됩니다.

```powershell
copy .env.example .env
```

### 무엇을 채워야 하나

| 키 | 필수 | 쓰는 곳 |
| --- | --- | --- |
| `TASHU_API_KEY` | **필수** | step0 재고 수집 · 웹 실시간 대조 |
| `API_KEY` (TMAP) | **필수** | step3 경로 지도 |
| `APIHUN_KMA_TYPE01_KEY` | 선택 | 실시간 날씨 — **없어도 파이프라인은 돕니다** |

기상청 키가 선택인 이유는 [.env.example](../../.env.example) 주석에 적힌 그대로입니다 —
과거 날씨 자료는 키 없이 CSV로 받고([WEATHER.md](../분석/WEATHER.md) 1장), 키는
실시간 관측·예보에만 씁니다.

### 기상청 활용신청은 옮길 것이 없다 (2026-08-31 실측)

기상청 API 허브는 **키 하나로 엔드포인트 여러 개**를 쓰는데, 각각 **따로
활용신청**해야 열립니다. 그런데 **승인은 키 문자열이 아니라 계정에 붙습니다** —
같은 키를 쓰는 두 PC는 한쪽에서 신청이 승인되면 **양쪽이 동시에 열립니다.**
**동기화할 것이 없다는 뜻입니다.** 키를 새로 발급받지 않았다면 `.env`도 그대로 둡니다.

2026-08-31 기준 실제 응답으로 확인한 상태입니다.

| 엔드포인트 | 쓰는 곳 | 상태 |
| --- | --- | --- |
| `kma_sfctm2` | 실시간 관측 (`fetch_current`) | ✅ 열림 |
| `fct_afs_dl` | 문장 예보 (`fetch_forecast`) | ✅ 열림 |
| `nph-dfs_shrt_grd` | 격자 예보 · 강수량 mm (`fetch_grid`) | ✅ 열림 |
| `kma_sfctm3` | **기간 관측** (여러 시각 한 번에) | ❌ **403 — 미신청** |

`kma_sfctm3`만 아직 막혀 있습니다. **막혀 있어도 지장은 없습니다** —
[weather.py](../../weather.py)가 이 경우를 예상하고 시각별 조회로 우회하며,
긴 기간은 기상자료개방포털 CSV로 받습니다. 다만 **한쪽 PC에서 403이 났다고 해서
그 PC만의 문제로 보지 마세요** — 계정 단위라 양쪽이 똑같이 막혀 있습니다.

**키 값 자체는 git이 아닌 경로로 나릅니다.** 세 개뿐이므로 비밀번호 관리자나
본인에게 보내는 메시지면 충분합니다. 클라우드 드라이브에 `.env`를 두고 양쪽에서
링크하는 방법도 있지만, **그 드라이브가 동기화 중 충돌을 내면 키가 반쪽이 됩니다** —
파일이 작으므로 손으로 두 번 만드는 편이 안전합니다.

> 💡 **키를 새로 발급받았다면 양쪽을 함께 고치세요.** 한쪽만 고치면 다른 PC에서
> 인증 실패가 나는데, 원인이 코드가 아니라 `.env`라는 것을 알아채기까지 시간이
> 걸립니다.

## 4. `data/` — 원본만 옮기고 나머지는 다시 만든다

`data/`는 약 2.8GB로 **git으로는 옮길 수 없습니다.** GitHub 파일 상한이 100MB인데
DB 하나가 1.3GB입니다. 그런데 **전부 옮길 필요도 없습니다** — 안이 두 종류로 갈립니다.

### 4-1. 원본 — 반드시 옮긴다 (약 1.5GB)

받아 온 자료라 **다시 만들 수 없습니다.**

| 경로 | 크기 | 무엇 |
| --- | --- | --- |
| `data/raw_data/타슈 대여이력(25.04~26.03)/` | **1.5GB** | 1년치 대여이력 원본 |
| `data/raw_data/날씨/` | 550KB | 기상자료개방포털 ASOS CSV (2025·2026) |
| `data/raw_data/재고이력/` | 8.2MB | 수집기가 쌓은 일별 재고 — 4-3장 |

USB나 클라우드 드라이브로 한 번 복사하면 됩니다. **대여이력이 사실상 전부**이므로
날씨·재고이력은 부담이 없습니다.

### 4-2. 산출물 — 옮기지 않아도 된다 (약 1.35GB)

| 경로 | 크기 | 만드는 것 |
| --- | --- | --- |
| `data/bike_system.db` | 1.3GB | [db.py](../../db.py) — "파이프라인 산출물을 한 파일에 모아 관리한다" |
| `data/pp_data/` | 56MB | step0~step4 (ILP·VRP·성능 지표·순수요 등) |

원본만 있으면 `python run_pipeline.py`로 다시 만들어집니다.

> 🔴 **예외가 하나 있습니다 — 실행 라벨은 다시 만들어지지 않습니다.**
> `station_info.stock`은 [tashu.py](../../tashu.py)가 **실행하는 순간 라이브
> API에서 받은 재고**입니다(`parking_count` → `stock`). 2026-08-11에 돌린 실행의
> 재고는 그날로 끝났고, 오늘 다시 돌리면 **오늘 재고**가 들어옵니다.
>
> 그런데 [DECISIONS.md](../분석/DECISIONS.md) 6-B가 실험의 **정본 스냅샷**을
> 특정 실행 라벨(`2026-08-11 real`)로 못박았습니다. 그 라벨이 없는 PC는
> [TODO.md](../기록/TODO.md)의 `P4-실행대기` 명령을 **하나도 돌릴 수 없습니다.**
> 실제로 2026-08-31에 그 상태가 됐습니다 — 한쪽 PC에는 그 라벨이 있고 다른
> 쪽에는 없었는데, 양쪽 문서가 각자의 DB를 보고 서로 반대되는 사실을 적었습니다.
>
> **DB 1.3GB를 통째로 옮길 필요는 없습니다.** 라벨 하나만 떼어 나르는 도구가
> 있습니다(약 6천 행, 수백 KB).
>
> ```powershell
> # 라벨을 가진 PC에서
> python tools/transfer_run.py --list
> python tools/transfer_run.py --export "2026-08-11 real" --out run_20260811.db
>
> # 받는 PC에서
> python tools/transfer_run.py --import run_20260811.db --dry-run
> python tools/transfer_run.py --import run_20260811.db
> ```
>
> **이미 있는 라벨은 말없이 덮지 않습니다**(`--overwrite`가 있어야 덮습니다) —
> 실험 결과가 붙어 있는 실행을 덮으면 어느 쪽 숫자를 본 것인지 알 수 없게
> 되기 때문입니다. `road_leg`(TMAP 실측)는 **따라가지 않습니다.** 양쪽이 각자
> 쌓는 관측치라, 섞으면 '어느 PC에서 잰 것인가'가 사라집니다 — 재고이력과
> 같은 성격이라 4-3장처럼 각자 쌓는 쪽이 맞습니다.

> #### 왜 git으로 나르지 않는가 — **재고 확인 (2026-09-01)**
>
> *"`.gitignore`에서 `*.db`를 빼면 되지 않나"* 를 실측으로 따져 보고 **현행 유지로
> 결정했습니다**(사용자 결정).
>
> **먼저 `*.db`를 빼도 아무것도 달라지지 않습니다.** 1.3GB DB를 막는 것은
> `.gitignore`의 **`data/`**(19행)이지 `*.db`(33행)가 아닙니다
> (`git check-ignore -v data/bike_system.db`로 확인). `data/` 밖에는 `.db`가
> 하나도 없으므로, 실제로 커밋하려면 **`data/`를 풀어야** 하고 그때 아래가
> 전부 현실이 됩니다.
>
> | 잃는 것 | 실측 |
> | --- | --- |
> | 저장소 폭발 | 압축률 31% → **커밋 1회당 약 404MB.** 현재 `.git`은 **6.6MB**다 |
> | GitHub 상한 | 100MB 초과라 **푸시가 거부된다.** LFS를 써도 무료 1GB를 두세 번에 소진 |
> | 되돌릴 수 없음 | 한 번 커밋하면 이력에 영원히 남는다 — 빼려면 `filter-repo` + 강제 푸시 |
> | 델타가 안 먹힘 | SQLite는 **3바이트만 바뀌어도 블롭을 통째로** 새로 저장한다(실측) |
> | 병합 불가 | 바이너리라 양쪽이 파이프라인을 돌리면 **매번 한쪽을 버려야** 한다 |
> | 규약 충돌 | `merge_stock.py`는 *"먼저 수집한 것이 이긴다"*로 관측을 지키는데 git 병합은 **한쪽을 덮는다** |
>
> 📌 **1.3GB 중 실제로 못 나르는 것은 1.4MB뿐**이고, 그것을 위한 도구가
> `transfer_run.py`입니다. 나머지는 파이프라인이 다시 만듭니다.
>
> #### 그래서 정한 방식 — **파일로 내보내 손으로 옮긴다**
>
> 내보낸 파일은 **`data/transfer/`**에 둡니다(`data/`가 이미 무시되므로 git에
> 딸려 가지 않습니다). USB·클라우드 드라이브 등으로 옮기십시오.
>
> ```powershell
> # 내보내는 PC
> python tools/transfer_run.py --export "2026-08-11 real" --out data/transfer/run_20260811_real.db
>
> # 받는 PC (같은 경로에 둔 뒤)
> python tools/transfer_run.py --import data/transfer/run_20260811_real.db --dry-run
> python tools/transfer_run.py --import data/transfer/run_20260811_real.db
> ```
>
> **왕복이 손실 없음을 확인했습니다**(2026-09-01) — 빈 DB에 import해 대여소
> 1,368곳·총재고 3,235로 원본과 일치했습니다. 12개 테이블 9,124행, 파일 1.4MB.
>
> ⚠️ **`road_leg`(TMAP 고정 패널)는 따라가지 않습니다** — 양쪽이 각자 쌓는
> 관측치라 섞으면 '어느 PC에서 잰 것인가'가 사라집니다(4-3장의 재고이력과 같은
> 성격). 2026-09-01부터 양쪽에서 각자 쌓입니다.

> ⚠️ **DB 전체는 다만 시간이 듭니다.** 1년치 대여이력을 다시 훑어야 하므로, **재생성 시간이
> 복사 시간보다 길면 DB째 복사하는 편이 빠릅니다.** 1.3GB 파일 하나이므로 판단
> 기준은 단순합니다 — 새 PC를 자주 세팅하지 않는다면 **한 번은 DB를 통째로 옮기고**
> 이후 갱신만 파이프라인에 맡기는 것이 현실적입니다.

### 4-3. 재고이력은 성격이 다르다 — 합쳐야 한다

`data/raw_data/재고이력/`은 **양쪽 PC가 각자 쌓습니다.** 복사가 아니라 **병합**이
필요한 유일한 자료입니다. 덮어쓰면 한쪽 관측이 사라집니다.

병합기가 따로 있습니다 — `INSERT OR IGNORE`라 **이미 있는 틱은 건드리지 않습니다.**

```powershell
python tools\merge_stock.py D:\다른PC\재고이력\ --dry-run   # 무엇이 들어올지 먼저
python tools\merge_stock.py D:\다른PC\재고이력\
```

자세한 규칙(겹칠 때 무엇이 이기는지, 마스터가 왜 CSV에 없는지)은
[COLLECTOR.md 11-4장](COLLECTOR.md#11-4-합치기-toolsmerge_stockpy)이 정본입니다.

## 6. 정리 — 새 PC 세팅 순서

```powershell
# 1. 코드 — git이 나른다
git clone https://github.com/movinggeol/PBR-PublicBicycleRelocation-.git
cd PBR-PublicBicycleRelocation-

# 2. 가상환경 — 각 PC에서 새로 만든다 (2장)
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt -r requirements-dev.txt

# 3. 키 — 이름은 git이, 값은 손이 (3장)
copy .env.example .env
#    → TASHU_API_KEY · API_KEY 채우기

# 4. 원본 데이터 — 한 번 복사 (4-1장)
#    data/raw_data/ 를 USB·클라우드로

# 5. 산출물 — 다시 만든다 (4-2장)
python run_pipeline.py

# 6. 확인
python -m pytest
```

## 7. 자동 동기화를 넣지 않은 이유

두 PC가 **같은 DB 파일을 동시에 쓰면 SQLite 잠금이 걸리고, 어느 쪽이 정본인지
흐려집니다.** 클라우드 드라이브에 `data/`를 통째로 올려 양쪽에서 여는 구성이
특히 위험합니다 — 1.3GB 파일을 백그라운드에서 동기화하는 도중에 쓰기가 들어가면
**파일이 깨질 수 있습니다.**

같은 판단이 재고 병합에도 적용되어 있습니다 — 자동이 아니라 **분석 직전에 손으로
한 번 부르는 명령**입니다([COLLECTOR.md 11-5장](COLLECTOR.md#11-5-남는-일)).
