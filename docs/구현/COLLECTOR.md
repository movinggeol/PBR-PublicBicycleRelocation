# 재고 시계열 수집 — 평일 09–17시 운영 예시 시나리오

> 2026-08-24 도입(1.20.0). 타슈 API로 대여소별 재고를 **평일 09:00–17:00, 10분
> 간격**으로 모아 실험용 시계열로 남깁니다. [TODO.md](../기록/TODO.md) 1-4(요일 구분별
> 재고 스냅샷)의 착수입니다.

## 1. 왜 모으는가

지금 파이프라인이 쓰는 초기 재고는 `tashu_api.py`가 **실행하는 순간 받아 온 스냅샷
한 장**입니다. 여기서 두 가지 문제가 나옵니다.

- **요일 구분과 무관합니다.** 평일 낮에 돌려 휴일 계획을 세우면 평일 재고 분포로
  휴일 결품을 시뮬레이션합니다 ([TODO.md](../기록/TODO.md) 1-4).
- **결품이 실측이 아닙니다.** step4는 "초기 재고 + 과거 순수요"로 결품 시간을
  *계산*합니다. 실제로 재고가 0이었던 시간을 잰 적은 없습니다
  ([THESIS.md](../연구/THESIS.md) 4장 한계).

재고 시계열이 쌓이면 둘 다 정면으로 다룰 수 있습니다.

## 2. 확정 사양

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 수집 창 | **평일 09:00–17:00** | 휴일 = 주말 ∪ 공휴일 제외 |
| 간격 | **10분** | 하루 49틱 (09:00 · 09:10 · … · 17:00) |
| 실행 | **Windows 작업 스케줄러** | `--once`를 10분마다 호출 |
| 대상 | 대여소 **1,372곳** (2026-08-24 실측) | 신설·폐지로 변합니다 — 그래서 마스터를 하루 한 번 남깁니다 |
| 정본 | `stock_history` 테이블 (SQLite) | 일별 CSV 백업 병행 |

**데이터 양**

| 구간 | 틱 | 행 수 | 누적 크기 |
| --- | --- | --- | --- |
| 하루 | 49 | 67,228 | ~2.7 MB |
| 주 (평일 5일) | 245 | 336,140 | ~14 MB |
| 4주 (평일 20일) | 980 | 1,344,560 | ~55 MB |

**시간대(duration) 커버리지** — 09–17시 창에서 온전히 분석 가능한 회차는 하나입니다.

| duration | 커버리지 |
| --- | --- |
| `_05_10` | 09:00~10:00만 (부분) |

> 그대로 살아 있으므로** 창 확장은 언제든 가능합니다 — 되돌릴 수 없는 선택이
> 아닙니다. `install -Window 08:00-20:00`으로 다시 등록하면 됩니다.

## 3. 저장 구조

테이블 두 개입니다. 컬럼 표는 [DB_SCHEMA.md](DB_SCHEMA.md#4-7-재고-시계열--실측-관측-1200)에
있고, 여기서는 **왜 그렇게 나눴는지**만 적습니다.

```text
stock_history         (observed_at, station_id) → stock      ← 틱마다
stock_station_master  (observed_on, station_id) → 이름·좌표   ← 하루 한 번
```

1. **기존 `station_stock`을 쓰지 않습니다.** PK가 `(run_label, station_id)`라
   실행 1건당 스냅샷 1장입니다. `run_label`에 시각을 우겨넣으면 `runs` 이력이
   하루 49건씩 오염되고, `db.latest_label()`이 파이프라인 실행 대신 수집 틱을
   최신으로 집습니다.
2. **이름·좌표를 틱마다 반복하지 않습니다.** 1,372행 × 49틱마다 같은 문자열을
   넣으면 용량이 몇 배가 됩니다.
3. **마스터도 `station_stock`에 얹지 않고 별도 테이블로 뺐습니다**(설계 단계에서
   바꾼 판단). `latest_label()`은 `run_label`의 **사전순** MAX인데, `collect-…`는
   숫자로 시작하는 실행 라벨보다 항상 커서 파이프라인 실행을 밀어냅니다.
   회귀 테스트가 이걸 고정합니다 — `test_수집은_station_stock과_runs를_건드리지_않는다`.
4. **`day_type`·`duration` 컬럼을 두지 않습니다.** 둘 다 `observed_at`에서
   파생되고, 요일 판정은 `project_config.holiday_mask()` 하나가 독점해야 합니다.
   거를 때는 `db.load_stock_history(day_type="weekday")`를 쓰세요.
5. **`db.TABLES`에 등록하지 않습니다.** 그 규약은 `run_label` 스코프 산출물용이라
   `demand_backtest`처럼 전용 함수를 씁니다.
6. **PK가 `(observed_at, station_id)`라 `INSERT OR REPLACE`가 멱등**합니다.

> **정본을 DB로 두는 것은 의도한 예외입니다.** "CSV가 아직 정본" 규약은
> 파이프라인 산출물에 대한 것이고, 시계열은 `rental_history` 선례를 따릅니다.
> 대신 `data/raw_data/재고이력/stock_YYYY-MM-DD.csv` 일별 백업을 병행합니다.

## 4. 수집기 — `tools/collect_stock.py`

**한 번 실행 = 한 틱.**

```text
창 가드 → 유휴 타이머 리셋 → tashu.fetch_stations() → 틱 격자 반올림
        → db.save_stock_snapshot() → CSV append → 로그 기록
```

**창 가드가 핵심입니다.** 스케줄러가 잘못 깨워도 스크립트가 스스로 판단합니다.

- `project_config.is_holiday(오늘)`이면 아무 것도 하지 않고 종료.
  **Windows 작업 스케줄러는 요일만 알고 공휴일을 모르므로, 이 가드가 실질적
  방어선입니다.** 이게 없으면 어린이날(화요일) 재고가 평일 데이터에 섞입니다.
- 반올림한 틱이 09:00~17:00 밖이면 종료.

**틱 격자 반올림**: 스케줄러는 09:00:03처럼 몇 초 늦게 깨우고, 부하가 걸리면
09:09:58에 깨우기도 합니다. 격자에 맞춰 두지 않으면 **날짜가 다른 같은 시각끼리
대조가 어긋납니다** — 시간대별 프로파일이 목적이므로 이 정렬이 데이터의 값어치를
정합니다.

| 옵션 | 뜻 | 기본값 |
| --- | --- | --- |
| `--once` | 한 틱만 수집하고 종료 (스케줄러용) | 기본 동작 |
| `--loop` | 창이 끝날 때까지 상주하며 반복 | 꺼짐 |
| `--window 09:00-17:00` | 수집 창 | `09:00-17:00` |
| `--interval 10` | 틱 간격(분) | `10` |
| `--force` | 창 밖·휴일에도 수집 | 꺼짐 |
| `--status` | 수집 현황만 출력 (API 호출 안 함) | — |
| `--dry-run` | 호출만 하고 저장하지 않음 | 꺼짐 |

**결측을 반드시 기록합니다** — `data/raw_data/재고이력/collect_log.csv`에
시각·성공여부·사유·행 수를 남깁니다. 나중에 *"이 시각은 API가 죽어서 없다"* 와
*"재고가 정말 0이었다"* 를 구분하지 못하면 실험이 거짓말을 합니다.
**빠진 틱은 보간하지 않습니다 — 결측 자체가 데이터입니다.**

종료 코드는 **0(성공·건너뜀) / 1(수집 실패)** 입니다. 작업 스케줄러의 '마지막 실행
결과'에 그대로 나타납니다.

## 5. 스케줄 등록

`schtasks.exe` 대신 PowerShell `Register-ScheduledTask`를 씁니다 — 아래 설정 중
절반은 schtasks 플래그로 표현할 수 없습니다. **등록에 관리자 권한은 필요 없습니다**
(현재 사용자 작업).

| 설정 | 등록된 값 | 이유 |
| --- | --- | --- |
| 요일 | `DaysOfWeek = 62` (월–금) | 주말은 트리거 자체가 없음 |
| 트리거 | `09:00` 시작 · `PT10M` 간격 · `PT8H` 지속 | 09:00~17:00 = 49틱 |
| 실행 파일 | **`.venv\Scripts\pythonw.exe`** | `python.exe`로 걸면 **10분마다 콘솔 창이 깜빡입니다** (하루 49번) |
| 동시 실행 | `IgnoreNew` | 한 틱이 매달려도 다음 틱이 겹쳐 쌓이지 않게 |
| 실행 시간 제한 | `PT5M` | 매달린 호출은 다음 틱 전에 강제 종료 |
| 놓친 작업 따라잡기 | `StartWhenAvailable = False` | 뒤늦게 실행하면 이미 값이 있는 격자 슬롯을 낡은 값으로 덮어씁니다. 10분 뒤 다음 틱이 오므로 따라잡을 이유가 없습니다 |
| 배터리 | 배터리에서도 시작·계속 | 노트북에서 조용히 멈추지 않게 |

> 주간 트리거에는 반복 설정이 노출되지 않습니다. `New-ScheduledTaskTrigger -Once`로
> 만든 트리거에서 `.Repetition`만 떼어 옮기는 것이 PS 5.1에서 통하는 방법입니다.

## 6. 운영 — 시작·일시정지·중지

**저장소 루트에서, VS Code의 PowerShell 터미널에 칩니다.** 관리자 권한은 필요
없고, 실행 정책이 `RemoteSigned`라 서명 없이 돕니다. Git Bash 터미널이라면
`powershell -File scripts/collector.ps1 install` 형태로 칩니다.

```powershell
.\scripts\collector.ps1 install     # 수집 시작 (최초 1회 등록)
.\scripts\collector.ps1 pause       # 일시정지 — 작업은 남기고 안 깨움
.\scripts\collector.ps1 resume      # 재개
.\scripts\collector.ps1 uninstall   # 완전 중지 — 작업 삭제
.\scripts\collector.ps1 status      # 스케줄 상태 + 수집 현황
.\scripts\collector.ps1 now         # 지금 한 틱 즉시 수집 (창 밖이어도)
```

`install` 한 번이면 그 뒤로는 **평일 09:00에 저절로 시작해 17:00에 저절로
멈춥니다.** 매일 켜고 끌 필요가 없고, 주말·공휴일도 알아서 건너뜁니다.
**VS Code도 터미널도 열어 둘 필요가 없습니다** — 작업 스케줄러가 OS 수준에서
돌리고, `pythonw.exe`라 창도 뜨지 않습니다. 필요한 것은 PC가 켜져 있고
**로그인되어 있는 것**뿐입니다.

> **아침에 PC를 켜는 시각이 그날 데이터의 완전성을 정합니다.** 따라잡기를 껐으므로
> 꺼져 있던 시간의 틱은 그냥 없습니다 — 09:35에 로그인하면 09:40 틱부터 들어오고
> 그날은 `44/49`가 되어 "온전한 날"에서 빠집니다. 온전한 하루가 필요하면 09:00
> 전에 로그인해 두세요.

**각 명령이 데이터에 하는 일**

| 명령 | 스케줄 | 이미 모은 데이터 | 되돌리기 |
| --- | --- | --- | --- |
| `install` | 등록 + 활성 | 그대로 | `uninstall` |
| `pause` | 유지, 비활성 | **손대지 않음** | `resume` |
| `resume` | 다시 활성 | 그대로 | `pause` |
| `uninstall` | 삭제 | **손대지 않음** | `install` |
| `now` | 무관 | 한 틱 추가 | 해당 틱 삭제 |

**데이터를 지우는 명령은 없습니다.** 일시정지·중지 모두 스케줄만 건드립니다.
쌓인 시계열을 지우려면 DB에서 직접 지워야 합니다 — 실수로 날릴 일이 없습니다.

창·간격을 바꾸려면 인자를 주고 다시 등록합니다(같은 이름이라 덮어씁니다):

```powershell
.\scripts\collector.ps1 install -Window 08:00-20:00 -Interval 15
```

**`status` 출력**

```text
  스케줄   : 활성 · 다음 실행 2026-08-25 09:00
  마지막   : 2026-08-24 16:50 · 성공
PBR 재고 수집 현황 (창 09:00~17:00 · 간격 10분 · 하루 49틱)
  누적     : 3일 · 147틱
  기간     : 2026-08-22 ~ 2026-08-24
  온전한 날: 2일 (최근 2026-08-22, 2026-08-23)
             ↳ 실험에 쓸 수 있는 날입니다.

      날짜  틱  기대  결측    상태
2026-08-22  49    49     0    온전
2026-08-23  49    49     0    온전
2026-08-24  49    49     0    온전

  최근 로그: 2026-08-24 16:50 · 성공 · 1372곳
```

등록 직후에는 `마지막 : 아직 실행 전 — 첫 수집은 다음 실행 시각입니다`가 나옵니다.
작업 스케줄러는 '한 번도 안 돎'을 `1999-11-30` / `코드 267011`
(`SCHED_S_TASK_HAS_NOT_RUN`)로 돌려주는데, **오류가 아니라 정상 상태**라
사람이 읽는 문구로 바꿔 둡니다.

**"온전한 날"이 실험에 쓸 수 있는 날입니다.** 며칠 일시정지해 구멍이 나도,
이 줄이 어느 날이 온전한지 알려주므로 실험에서 골라 쓰면 됩니다.

## 7. 사람이 알아야 할 전제

### 실행 환경 (2026-08-24 실측)

| 항목 | 값 | 수집에 미치는 영향 |
| --- | --- | --- |
| 기기 | 노트북 (배터리 있음) | 뚜껑을 닫으면 절전 |
| **AC 절전 대기** | **안 함 (0)** | **전원을 꽂아두면 09–17시 내내 안 잠 — 그대로 수집됨** |
| 배터리 절전 대기 | 10분 | 배터리로 쓰면 10분 방치에 끊김 |
| 절전 방식 | 모던 대기(S0), 최대 절전 꺼짐 | 아래 참고 |
| 실행 정책 | `CurrentUser = RemoteSigned` | 로컬 `.ps1`을 서명 없이 실행 가능 |

### 상태별 동작

| 상태 | 수집 | 비고 |
| --- | --- | --- |
| 화면만 꺼짐 | ✅ | 디스플레이 절전은 무관 |
| 잠금 화면 (Win+L) | ✅ | **잠금은 로그오프가 아닙니다** |
| 재부팅 후 로그인 | ✅ | 작업이 남아 있어 자동 재개 |
| 절전 · 뚜껑 닫기 | ❌ | 그 시간 데이터 없음 |
| 로그오프 · 사용자 전환 | ❌ | 사용자 계정 작업이라 |
| 배터리로 10분 방치 | ❌ | 위 표 참고 |

### 절전은 "깨우지" 말고 "안 자게" 한다

이 PC는 **모던 대기(S0)** 라 절전 중 데스크톱 앱이 억제됩니다. 작업에 "깨우기"를
켜도 10분마다 확실히 도는지 보장할 수 없습니다. 그래서 두 가지로 대응합니다.

1. **`install`이 전원 설정을 점검해 경고합니다** — 지금 배터리로 돌고 있거나
   AC 절전 시간이 창(8시간)보다 짧으면 등록하면서 알려줍니다. **설정을 말없이
   바꾸지는 않습니다** — 사용자 시스템 설정이라 경고까지가 선입니다.
2. **매 틱이 시스템 유휴 타이머를 리셋합니다**(`SetThreadExecutionState`,
   `ES_SYSTEM_REQUIRED`). 10분마다 리셋되므로 절전 임계값이 10분보다 크면 창 동안
   잠들지 않습니다. **배터리 기본값 10분은 간격과 같아 이것만으로는 못 막습니다.**

> **실사용 한 줄: 평일 09–17시에는 전원 어댑터를 꽂고 뚜껑을 열어두면 됩니다.**
> 화면이 꺼지거나 잠기는 것은 상관없습니다.

### 그 밖에

- **로그인 상태여야 합니다.** 사용자 계정 작업이라 로그오프 상태에서는 돌지
  않습니다. 필요하면 `install -RunWhenLoggedOff`로 넓힙니다(비밀번호를 묻습니다).
- **절전으로 놓친 틱은 결측 로그에도 안 남습니다** (스크립트 자체가 안 돌아서).
  그래서 `status`는 로그가 아니라 **DB의 기대 격자와 대조해** 결측을 셉니다.
- 공휴일 제외는 스케줄러가 아니라 **스크립트 가드**가 합니다(4장).

## 8. 모은 데이터로 무엇을 하는가

   **평일 09:00 실측 중앙값**으로 바꿉니다.

   같은 날 실측 추이와 대조합니다.

## 10. 한계

- **타슈 API 응답에는 자체 타임스탬프가 없습니다.** `observed_at`은 "우리가 받아 온
  시각"이지 "타슈가 그 값을 갱신한 시각"이 아닙니다. 10분 간격에서 실질적 문제는
  없지만 논문에 쓸 때는 명시해야 합니다.
- **09–17시 창에서는 `_10_15` 회차만 온전합니다**(2장).
- **`Δstock`에는 재배치 차량의 이동이 섞입니다** — 순수요와 동일시할 수 없습니다.
- 수집 기간이 특정 계절에 몰리면 계절 효과와 분리되지 않습니다. 최소 2주(평일
  10일), 가능하면 4주를 권합니다.
- **PC가 깨어 있어야만 모입니다**(7장). 시스템 가용성이 곧 데이터 가용성입니다.
