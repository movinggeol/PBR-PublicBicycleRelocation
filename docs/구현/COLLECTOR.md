# 재고 시계열 수집 — 평일 07–22시 운영 예시 시나리오

> 2026-08-24 도입(1.20.0). 타슈 API로 대여소별 재고를 **평일 07:00–22:00, 10분
> 간격**으로 모아 실험용 시계열로 남깁니다. **창은 2026-08-27에 09–17시에서
> 넓혔습니다**(1.25.1) — 그 전에 모은 3일치는 09–17시 창으로 모은 것입니다(2-B장). [TODO.md](../기록/TODO.md) 1-4(요일 구분별
> 재고 스냅샷)의 착수입니다.

## 1. 왜 모으는가

지금 파이프라인이 쓰는 초기 재고는 `tashu_api.py`가 **실행하는 순간 받아 온 스냅샷
한 장**입니다. 여기서 두 가지 문제가 나옵니다.

- **요일 구분과 무관합니다.** 평일 낮에 돌려 휴일 계획을 세우면 평일 재고 분포로
  휴일 결품을 시뮬레이션합니다 ([TODO.md](../기록/TODO.md) 1-4).
- **결품이 실측이 아닙니다.** step4는 "초기 재고 + 과거 순수요"로 결품 시간을
  *계산*합니다. 실제로 재고가 0이었던 시간을 잰 적은 없습니다
  ([THESIS.md](../연구/THESIS.md) 4장 한계).

재고 시계열이 쌓이면 둘 다 정면으로 다룰 수 있습니다.

## 2. 확정 사양

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 수집 창 | **평일 07:00–22:00** | 휴일 = 주말 ∪ 공휴일 제외. 2026-08-27에 09–17시에서 넓혔습니다 |
| 간격 | **10분** | 하루 91틱 (07:00 · 07:10 · … · 22:00) |
| 실행 | **Windows 작업 스케줄러** | `--once`를 10분마다 호출 |
| 대상 | 대여소 **1,372곳** (2026-08-24 실측) | 신설·폐지로 변합니다 — 그래서 마스터를 하루 한 번 남깁니다 |
| 정본 | `stock_history` 테이블 (SQLite) | 일별 CSV 백업 병행 |

**데이터 양**

| 구간 | 틱 | 행 수 | CSV 크기 |
| --- | --- | --- | --- |
| 하루 | 91 | 124,852 | ~3.4 MB |
| 주 (평일 5일) | 455 | 624,260 | ~16.9 MB |
| 4주 (평일 20일) | 1,820 | 2,497,040 | ~67.6 MB |

> 행당 **27.1 B** 실측입니다(`stock_2026-08-26.csv` 1,817,668 B / 67,186행).
> 도입 때 적었던 40 B는 추정치였습니다 — 실제로 더 작습니다.

**시간대(duration) 커버리지** — 07–22시 창에서 온전히 분석 가능한 회차는 **둘**입니다.

| duration | 07–22시 (지금) | 09–17시 (2026-08-27 이전) |
| --- | --- | --- |
| `_05_10` | 07:00~10:00 (3/5시간) — 끝 경계만 | 09:00~10:00 (1/5시간) |
| `_10_15` | **완전** — 경계 둘 다 관측 | **완전** |
| `_15_20` | **완전** — 경계 둘 다 관측 | 15:00~17:00 (3/5시간) |
| `_20_05` | 20:00~22:00 (2/9시간) — 시작 경계만 | 없음 |

**창을 넓혀 얻은 것은 `_15_20`의 완전 관측입니다.** 9-B 실측에서 물량이
`_10_15`의 3.6배이고 실제 재배치를 가장 많이 돌린 회차인데, 09–17시 창에서는
3/5만 보였습니다.

> **이미 모은 데이터는 그대로 살아 있습니다.** 창 변경은 되돌릴 수 없는 선택이
> 아닙니다 — `install -Window …`로 다시 등록하면 됩니다.

### 2-B. 창을 넓힌 날 경계 (2026-08-27)

**2026-08-25 · 08-26 · 08-27은 09:00–17:00 창으로 모았습니다.** 이후는 07:00–22:00
입니다. 데이터는 그대로 살아 있고 그 3일의 09~17시 구간에는 **빠진 틱이 없습니다.**

다만 `--status`는 **지금 등록된 창을 기준으로** 결측을 세므로(6장), 이 3일이
`49/91 · 결측 42 · 결측`으로 나오고 **"온전한 날 0일"** 이 됩니다.

| 날짜 | 실제로 모은 것 | 새 창 기준 표시 |
| --- | --- | --- |
| 2026-08-25 ~ 08-27 | 09–17시 49틱 (당시 기준 온전) | `결측` — 07–09시·17–22시가 없어서 |
| 2026-08-28 ~ | 07–22시 91틱 | `온전` |

**이 3일을 버릴 필요는 없습니다.** `_10_15`는 09–17시 창에서도 완전하므로
(2장) 그 회차 분석에는 그대로 씁니다. `_15_20`·`_05_10`을 볼 때만 08-28
이후를 쓰면 됩니다.

> 옛 창 기준으로 보려면 인자를 주면 됩니다 — 등록된 스케줄은 건드리지 않습니다.
>
> ```powershell
> python tools\collect_stock.py --status --window 09:00-17:00
> ```

## 3. 저장 구조

테이블 두 개입니다. 컬럼 표는 [DB_SCHEMA.md](DB_SCHEMA.md#4-7-재고-시계열--실측-관측-1200)에
있고, 여기서는 **왜 그렇게 나눴는지**만 적습니다.

```text
stock_history         (observed_at, station_id) → stock      ← 틱마다
stock_station_master  (observed_on, station_id) → 이름·좌표   ← 하루 한 번
```

1. **기존 `station_stock`을 쓰지 않습니다.** PK가 `(run_label, station_id)`라
   실행 1건당 스냅샷 1장입니다. `run_label`에 시각을 우겨넣으면 `runs` 이력이
   하루 49건씩 오염되고, `db.latest_label()`이 파이프라인 실행 대신 수집 틱을
   최신으로 집습니다.
2. **이름·좌표를 틱마다 반복하지 않습니다.** 1,372행 × 91틱마다 같은 문자열을
   넣으면 용량이 몇 배가 됩니다.
3. **마스터도 `station_stock`에 얹지 않고 별도 테이블로 뺐습니다**(설계 단계에서
   바꾼 판단). `latest_label()`은 `run_label`의 **사전순** MAX인데, `collect-…`는
   숫자로 시작하는 실행 라벨보다 항상 커서 파이프라인 실행을 밀어냅니다.
   회귀 테스트가 이걸 고정합니다 — `test_수집은_station_stock과_runs를_건드리지_않는다`.
4. **`day_type`·`duration` 컬럼을 두지 않습니다.** 둘 다 `observed_at`에서
   파생되고, 요일 판정은 `project_config.holiday_mask()` 하나가 독점해야 합니다.
   거를 때는 `db.load_stock_history(day_type="weekday")`를 쓰세요.
5. **`db.TABLES`에 등록하지 않습니다.** 그 규약은 `run_label` 스코프 산출물용이라
   `demand_backtest`처럼 전용 함수를 씁니다.
6. **PK가 `(observed_at, station_id)`라 `INSERT OR REPLACE`가 멱등**합니다.

> **정본을 DB로 두는 것은 의도한 예외입니다.** "CSV가 아직 정본" 규약은
> 파이프라인 산출물에 대한 것이고, 시계열은 `rental_history` 선례를 따릅니다.
> 대신 `data/raw_data/재고이력/stock_YYYY-MM-DD.csv` 일별 백업을 병행합니다.

## 4. 수집기 — `tools/collect_stock.py`

**한 번 실행 = 한 틱.**

```text
창 가드 → 유휴 타이머 리셋 → tashu.fetch_stations() → 틱 격자 반올림
        → db.save_stock_snapshot() → CSV append → 로그 기록
```

**창 가드가 핵심입니다.** 스케줄러가 잘못 깨워도 스크립트가 스스로 판단합니다.

- `project_config.is_holiday(오늘)`이면 아무 것도 하지 않고 종료.
  **Windows 작업 스케줄러는 요일만 알고 공휴일을 모르므로, 이 가드가 실질적
  방어선입니다.** 이게 없으면 어린이날(화요일) 재고가 평일 데이터에 섞입니다.
- 반올림한 틱이 07:00~22:00 밖이면 종료.

**틱 격자 반올림**: 스케줄러는 09:00:03처럼 몇 초 늦게 깨우고, 부하가 걸리면
09:09:58에 깨우기도 합니다. 격자에 맞춰 두지 않으면 **날짜가 다른 같은 시각끼리
대조가 어긋납니다** — 시간대별 프로파일이 목적이므로 이 정렬이 데이터의 값어치를
정합니다.

| 옵션 | 뜻 | 기본값 |
| --- | --- | --- |
| `--once` | 한 틱만 수집하고 종료 (스케줄러용) | 기본 동작 |
| `--loop` | 창이 끝날 때까지 상주하며 반복 | 꺼짐 |
| `--window 07:00-22:00` | 수집 창 | `09:00-17:00` (**기본값은 그대로**) |
| `--interval 10` | 틱 간격(분) | `10` |
| `--force` | 창 밖·휴일에도 수집 | 꺼짐 |
| `--include-holidays` | 평일 + 휴일 (**창은 지킴**) — 11장 | 꺼짐 |
| `--holidays-only` | **휴일만** (평일은 건너뜀) — 11장 | 꺼짐 |
| `--status` | 수집 현황만 출력 (API 호출 안 함) | — |
| `--dry-run` | 호출만 하고 저장하지 않음 | 꺼짐 |

**결측을 반드시 기록합니다** — `data/raw_data/재고이력/collect_log.csv`에
시각·성공여부·사유·행 수를 남깁니다. 나중에 *"이 시각은 API가 죽어서 없다"* 와
*"재고가 정말 0이었다"* 를 구분하지 못하면 실험이 거짓말을 합니다.
**빠진 틱은 보간하지 않습니다 — 결측 자체가 데이터입니다.**

종료 코드는 **0(성공·건너뜀) / 1(수집 실패)** 입니다. 작업 스케줄러의 '마지막 실행
결과'에 그대로 나타납니다.

## 5. 스케줄 등록

`schtasks.exe` 대신 PowerShell `Register-ScheduledTask`를 씁니다 — 아래 설정 중
절반은 schtasks 플래그로 표현할 수 없습니다. **등록에 관리자 권한은 필요 없습니다**
(현재 사용자 작업).

| 설정 | 등록된 값 | 이유 |
| --- | --- | --- |
| 요일 | `DaysOfWeek = 62` (월–금) | 주말은 트리거 자체가 없음. `-IncludeHolidays`·`-HolidaysOnly`면 `127`(7일) — 11장 |
| 트리거 | `07:00` 시작 · `PT10M` 간격 · `PT15H` 지속 | 07:00~22:00 = 91틱 |
| 실행 파일 | **`.venv\Scripts\pythonw.exe`** | `python.exe`로 걸면 **10분마다 콘솔 창이 깜빡입니다** (하루 49번) |
| 동시 실행 | `IgnoreNew` | 한 틱이 매달려도 다음 틱이 겹쳐 쌓이지 않게 |
| 실행 시간 제한 | `PT5M` | 매달린 호출은 다음 틱 전에 강제 종료 |
| 놓친 작업 따라잡기 | `StartWhenAvailable = False` | 뒤늦게 실행하면 이미 값이 있는 격자 슬롯을 낡은 값으로 덮어씁니다. 10분 뒤 다음 틱이 오므로 따라잡을 이유가 없습니다 |
| 배터리 | 배터리에서도 시작·계속 | 노트북에서 조용히 멈추지 않게 |

> 주간 트리거에는 반복 설정이 노출되지 않습니다. `New-ScheduledTaskTrigger -Once`로
> 만든 트리거에서 `.Repetition`만 떼어 옮기는 것이 PS 5.1에서 통하는 방법입니다.

## 6. 운영 — 시작·일시정지·중지

**저장소 루트에서, VS Code의 PowerShell 터미널에 칩니다.** 관리자 권한은 필요
없고, 실행 정책이 `RemoteSigned`라 서명 없이 돕니다. Git Bash 터미널이라면
`powershell -File scripts/collector.ps1 install` 형태로 칩니다.

```powershell
.\scripts\collector.ps1 install     # 수집 시작 (최초 1회 등록)
.\scripts\collector.ps1 pause       # 일시정지 — 작업은 남기고 안 깨움
.\scripts\collector.ps1 resume      # 재개
.\scripts\collector.ps1 uninstall   # 완전 중지 — 작업 삭제
.\scripts\collector.ps1 status      # 스케줄 상태 + 수집 현황
.\scripts\collector.ps1 now         # 지금 한 틱 즉시 수집 (창 밖이어도)
```

`install` 한 번이면 그 뒤로는 **평일 07:00에 저절로 시작해 22:00에 저절로
멈춥니다.** 매일 켜고 끌 필요가 없고, 주말·공휴일도 알아서 건너뜁니다.
**VS Code도 터미널도 열어 둘 필요가 없습니다** — 작업 스케줄러가 OS 수준에서
돌리고, `pythonw.exe`라 창도 뜨지 않습니다. 필요한 것은 PC가 켜져 있고
**로그인되어 있는 것**뿐입니다.

> **아침에 PC를 켜는 시각이 그날 데이터의 완전성을 정합니다.** 따라잡기를 껐으므로
> 꺼져 있던 시간의 틱은 그냥 없습니다 — 09:35에 로그인하면 09:40 틱부터 들어오고
> 그날은 `44/49`가 되어 "온전한 날"에서 빠집니다. 온전한 하루가 필요하면 09:00
> 전에 로그인해 두세요.

**각 명령이 데이터에 하는 일**

| 명령 | 스케줄 | 이미 모은 데이터 | 되돌리기 |
| --- | --- | --- | --- |
| `install` | 등록 + 활성 | 그대로 | `uninstall` |
| `pause` | 유지, 비활성 | **손대지 않음** | `resume` |
| `resume` | 다시 활성 | 그대로 | `pause` |
| `uninstall` | 삭제 | **손대지 않음** | `install` |
| `now` | 무관 | 한 틱 추가 | 해당 틱 삭제 |

**데이터를 지우는 명령은 없습니다.** 일시정지·중지 모두 스케줄만 건드립니다.
쌓인 시계열을 지우려면 DB에서 직접 지워야 합니다 — 실수로 날릴 일이 없습니다.

창·간격을 바꾸려면 인자를 주고 다시 등록합니다(같은 이름이라 덮어씁니다):

```powershell
.\scripts\collector.ps1 install -Window 08:00-20:00 -Interval 15
```

**바꾼 뒤 `status`·`now`는 인자 없이 불러도 새 창을 씁니다** — 등록된 작업의
인자에서 되읽기 때문입니다(1.25.1에서 고쳤습니다. 그 전에는 파라미터 기본값
`09:00-17:00`으로 결측을 세서, 스케줄 줄과 현황 줄이 서로 다른 창을 말했습니다).
`now`도 같은 창을 씁니다. `--force`라 창 밖에서도 받아 오지만 **틱 격자의
기준점이 창 시작 시각**이기 때문입니다(4장) — 09:00과 07:00처럼 간격(10분)의
배수만큼 떨어진 창끼리는 격자가 같지만, `07:05` 같은 창을 섞으면 5분 밀린
슬롯에 저장됩니다.

**`status` 출력**

```text
  스케줄   : 활성 · 다음 실행 2026-08-27 14:50
  마지막   : 2026-08-27 14:40 · 성공
PBR 재고 수집 현황 (창 07:00~22:00 · 간격 10분 · 하루 91틱)
  누적     : 3일 · 133틱
  기간     : 2026-08-25 ~ 2026-08-27
  온전한 날: 0일
             ↳ 실험에 쓸 수 있는 날입니다.

        날짜  틱  기대  결측   상태
2026-08-25 49  91  42   결측
2026-08-26 49  91  42   결측
2026-08-27 35  91  56 수집 중

  최근 로그: 2026-08-27 14:40 · 성공 · 1372곳
```

위 3일이 `결측`인 것은 **창을 넓힌 날 경계** 때문입니다 — 데이터가 빠진 것이
아닙니다(2-B장). **`status`는 등록된 작업에서 창을 되읽습니다**, 파라미터
기본값이 아니라. 옛 창으로 대조하려면 `-Window 09:00-17:00`을 직접 주면 됩니다.

등록 직후에는 `마지막 : 아직 실행 전 — 첫 수집은 다음 실행 시각입니다`가 나옵니다.
작업 스케줄러는 '한 번도 안 돎'을 `1999-11-30` / `코드 267011`
(`SCHED_S_TASK_HAS_NOT_RUN`)로 돌려주는데, **오류가 아니라 정상 상태**라

### 절전은 "깨우지" 말고 "안 자게" 한다

이 PC는 **모던 대기(S0)** 라 절전 중 데스크톱 앱이 억제됩니다. 작업에 "깨우기"를
켜도 10분마다 확실히 도는지 보장할 수 없습니다. 그래서 두 가지로 대응합니다.

1. **`install`·`resume`이 전원 설정을 점검합니다.** **설정을 말없이 바꾸지는
   않습니다** — 사용자 시스템 설정이라 알리는 것까지가 선입니다. 세 갈래로
   나눠 말합니다(1.25.2에서 다듬었습니다 — 그 전에는 *창보다 짧으면* 무조건
   경고해서, 실제로는 안 끊기는 상황에도 겁을 줬습니다):

   | AC 절전 임계 | 반응 |
   | --- | --- |
   | `0` (안 함) | 안내 — 창 내내 깨어 있음 |
   | **틱 간격 이하** | ⚠️ **경고** — 유휴 리셋으로 못 막아 실제로 끊김 |
   | 간격보다 길고 창보다 짧음 | 안내 — 매 틱이 타이머를 되돌려 수집 중엔 안 잠 |

   배터리로 돌고 있으면 그것도 따로 경고합니다.
2. **매 틱이 시스템 유휴 타이머를 리셋합니다**(`SetThreadExecutionState`,
   `ES_SYSTEM_REQUIRED`). 10분마다 리셋되므로 절전 임계값이 10분보다 크면 창 동안
   잠들지 않습니다. **배터리 기본값 10분은 간격과 같아 이것만으로는 못 막습니다.**

> **실사용 한 줄: 평일 07–22시에는 전원 어댑터를 꽂고 뚜껑을 열어두면 됩니다.**
> 화면이 꺼지거나 잠기는 것은 상관없습니다.

### 그 밖에

- **로그인 상태여야 합니다.** 사용자 계정 작업이라 로그오프 상태에서는 돌지
  않습니다. 필요하면 `install -RunWhenLoggedOff`로 넓힙니다(비밀번호를 묻습니다).
- **절전으로 놓친 틱은 결측 로그에도 안 남습니다** (스크립트 자체가 안 돌아서).
  그래서 `status`는 로그가 아니라 **DB의 기대 격자와 대조해** 결측을 셉니다.
- 공휴일 제외는 스케줄러가 아니라 **스크립트 가드**가 합니다(4장).

## 11. 두 번째 PC가 휴일을 맡는다 (2026-08-27, 1.25.0·1.25.4)

| 바뀌는 것 | **없습니다** | — |

프로파일을 같은 축으로 비교**하기 위해서입니다 — [TODO.md](../기록/TODO.md) 1-4가
요구하는 것이 정확히 그 비교입니다.

### 11-1. 겹쳐도 안전한 이유

**평일/휴일로 나눠 맡으면 애초에 겹치지 않습니다.** 아래는 그래도 겹쳤을 때
(예: B를 `-IncludeHolidays`로 걸었거나, 한쪽에서 `now`를 눌렀을 때) 무엇이
일어나는지입니다.

두 PC 모두 `tick_of()`가 시각을 같은 격자로 반올림하므로(4장), A의 09:10과 B의
09:10은 **같은 키** `(observed_at, station_id)`가 됩니다. 합칠 때 행이 두 배가
되거나 격자가 어긋나지 않습니다.

**겹치면 먼저 수집한 것을 남깁니다** (사용자 결정, 2026-08-27). `merge_stock.py`가
`INSERT OR IGNORE`를 쓰므로 **로컬에 이미 있는 틱은 건드리지 않습니다.**

> ⚠️ **수집기 본체와 정반대입니다** — `save_stock_snapshot()`은 `INSERT OR REPLACE`라
> 나중 값이 이깁니다. 의도한 차이입니다: 수집기는 *같은 PC가 같은 틱을 다시 받아온*
> 경우(재실행 멱등)라 새 값이 맞고, 병합은 *다른 PC가 이미 잰 값을 나중에 들고 온*
> 경우입니다. 한쪽 규칙을 다른 쪽에 옮겨 붙이면 A PC 값이 조용히 B PC 값으로
> 바뀝니다 — 회귀 테스트가 이걸 고정합니다
> (`test_이미_있는_틱은_덮어쓰지_않는다`).
>
> `fetched_at`으로 실제 선후를 가리지 않는 이유는 **두 PC의 시계가 몇 초씩
> 어긋나기 때문**입니다. 겹치는 구간은 같은 API의 같은 값이라 실질 차이도 없습니다.

### 11-2. 요일 옵션 세 가지

| 옵션 | 평일 | 휴일 | 쓰는 곳 |
| --- | --- | --- | --- |
| (없음) | ✅ | ❌ | **A PC** — 지금까지의 동작 |
| `--include-holidays` | ✅ | ✅ | 한 대로 전부 모을 때 |
| **`--holidays-only`** | ❌ | ✅ | **B PC** — 휴일만 맡는다 |

셋 다 **창 가드는 그대로 지킵니다.** `--force`와 다른 점이 여기입니다 —
`--force`는 창까지 풀어 아무 시각에나 틱이 들어오지만, 요일 옵션은 **어느 날에
받아올지만** 정합니다. 격자 대조가 데이터의 값어치라 창은 살아 있어야 합니다
(`test_휴일만_수집도_창_가드는_지킨다`).

**가드가 두 겹이라 둘 다 맞춰야 합니다.** 하나만 바꾸면 깨워도 안 모으거나
(스크립트가 거름), 안 깨웁니다(트리거가 없음). PowerShell 스위치가 양쪽을
동시에 겁니다.

| 층 | 평일 수집 | `-IncludeHolidays` | **`-HolidaysOnly`** |
| --- | --- | --- | --- |
| 트리거 요일 | 월–금 (`62`) | 7일 (`127`) | **7일 (`127`)** |
| 스크립트 요일 가드 | 휴일이면 종료 | 통과 | **평일이면 종료** |

> ⚠️ **`-HolidaysOnly`인데 트리거가 7일인 것이 핵심입니다.** 토·일만 걸면
> **공휴일을 통째로 놓칩니다** — 어린이날은 화요일이라 요일 트리거로는 잡히지
> 않습니다. 그래서 **7일을 깨우고 평일을 스크립트가 거릅니다.**
> `test_휴일만_수집은_주말과_공휴일을_모두_잡는다`가 이걸 고정합니다.

`--include-holidays`와 `--holidays-only`는 **함께 쓸 수 없습니다** — argparse가
상호 배타로 막고, PowerShell도 등록 전에 막습니다.

**이것은 관측을 남기는 범위지 분석의 `--day-type`이 아닙니다.** 평일과 휴일을
섞어 통계를 내지 말라는 규약은 그대로입니다 — 거를 때는
`db.load_stock_history(day_type="weekday")`가 `observed_at`에서 갈라냅니다(3장).

### 11-3. B PC 준비

git은 **코드만** 나릅니다. `data/`·`.env`는 `.gitignore`에 있어 따라오지 않습니다.

```powershell
git clone https://github.com/movinggeol/PBR-PublicBicycleRelocation-.git
cd PBR-PublicBicycleRelocation-
py -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
```

그다음 **`.env`를 손으로 만듭니다** — `TASHU_API_KEY` 한 줄이면 수집기는 돕니다
(`.env.example` 참고). **DB는 옮기지 않아도 됩니다.** 없으면 첫 틱에서
`db.session()`이 스키마째 새로 만듭니다.

```powershell
.\scripts\collector.ps1 install -Window 07:00-22:00 -HolidaysOnly
.\scripts\collector.ps1 status
```

`[등록] PBR재고수집 — 휴일만 07:00-22:00 · 10분 간격`이 나오면 됩니다.

**창을 A와 같은 07:00–22:00으로 두는 이유**는 평일·휴일을 같은 축으로 비교하기
위해서입니다. B PC를 그만큼 못 켜 두면 짧게 잡아도 됩니다 — 다만 그러면 휴일은
그 창만큼만 관측되므로, 평일과 나란히 놓고 비교할 수 있는 구간이 줄어듭니다.

**시험해 보려면** 휴일을 기다리지 않아도 됩니다. `now`는 `--force`라 요일·창과
무관하게 한 틱을 받아 옵니다.

```powershell
.\scripts\collector.ps1 now      # 지금 한 틱 — 평일에도 동작
```

### 11-4. 합치기 — `tools/merge_stock.py`

**DB는 git으로 못 옮깁니다.** `data/`가 `.gitignore`에 있고 파일이 1GB를 넘습니다
(GitHub 상한은 100MB). USB·클라우드 드라이브로 파일을 나른 뒤 합칩니다.

```powershell
python tools\merge_stock.py D:\B_PC\재고이력\ --dry-run   # 무엇이 들어올지 먼저
python tools\merge_stock.py D:\B_PC\재고이력\             # 합치기
python tools\collect_stock.py --status                    # 확인
```

**옮길 것은 DB가 아니라 일별 CSV입니다** — 하루 1.8MB이고 `--status`가 세는 결측도
병합 후 DB 기준으로 다시 계산됩니다.

| 원천 | 크기 | 마스터(이름·좌표) |
| --- | --- | --- |
| `data/raw_data/재고이력/` 폴더 | 하루 ~1.8MB | **없음** |
| `data/bike_system.db` | 1GB+ | 있음 |

**CSV에는 재고만 있습니다.** B PC만 관측한 날짜가 있으면 그날 마스터가 A PC에
없게 되므로, 병합기가 `⚠ 이름·좌표가 없는 날`로 알려줍니다. 그런 날이 나오면 B의
DB 파일로 한 번 더 합치면 채워집니다(같은 명령에 경로만 `.db`로).

`collect_log.csv`는 이름이 달라 `stock_*.csv` glob에서 자연히 빠집니다 — 형식이
다르므로 섞이면 안 됩니다.

**병합은 원본을 건드리지 않습니다.** 옮겨온 DB는 읽기 전용(`mode=ro`)으로 엽니다.
`--dry-run`으로 먼저 날짜별 틱 수를 보고 결정하세요.

### 11-5. 남는 일

병합은 **손으로 부르는 명령**입니다. 자동 동기화는 넣지 않았습니다 — 두 PC가
같은 DB를 동시에 쓰면 SQLite 잠금이 걸리고, 어느 쪽이 정본인지 흐려집니다.
**분석 직전에 한 번 합치는 것**으로 충분합니다.
