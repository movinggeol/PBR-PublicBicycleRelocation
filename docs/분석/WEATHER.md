# 날씨 — 어떤 API를 받고, 그것이 무엇을 설명하는가

> 2026-08-25 작성 (버전 1.20.1). 수정안 9번 "기상청에서 **어떤** API를 받으면 되는지"에
> 대한 답과, 받은 자료로 실제 측정한 결과입니다.
>
> **결론 먼저**: 과거 자료는 **기상자료개방포털 CSV**(키 불필요), 실시간은 **API 허브의
> `kma_sfctm2`**(키 필요, 이미 열려 있음)입니다. 기간을 한 번에 주는 `kma_sfctm3`는
> **활용신청이 더 필요합니다**(현재 403). 그리고 날씨는 붙일 값어치가 있습니다 —
> **비 오는 날 순수요 예측 오차가 40% 줄어듭니다.**

---

## 1. 어떤 API를 받으면 되는가

기상청은 창구가 두 개이고, **둘의 쓰임이 다릅니다.** 하나로 다 되지 않습니다.

| | 기상자료개방포털 | 기상청 API 허브 |
| --- | --- | --- |
| 주소 | https://data.kma.go.kr | https://apihub.kma.go.kr |
| 키 | **필요 없음** | 필요 (`.env`의 `APIHUN_KMA_TYPE01_KEY`) |
| 받는 방식 | 화면에서 기간을 골라 CSV 내려받기 | HTTP 호출 |
| 한 번에 | **몇 년치도 한 파일로** | **한 시각씩** (기간 조회는 아래 참고) |
| 쓰는 곳 | 과거 자료 — 학습·측정·백테스트 | 오늘 자료 — 실시간 대조·계획 당일 |

### 1-1. 과거 자료 — 포털에서 CSV로 받는다

    기후통계분석·자료 → 종관기상관측(ASOS) → [시간] 자료
      지점 : 대전 (지점번호 133)
      기간 : 대여이력이 있는 범위 (지금은 2025-01-01 ~ 2026-07-31)
      요소 : 기온 · 강수량 · 풍속 · 습도 · 적설
      → CSV 다운로드 → data/raw_data/날씨/ 에 저장

**API로 받지 마십시오.** 1년치가 8,760시간이고 API 허브는 한 시각씩 주므로 호출이
8,760번이 됩니다. 포털은 같은 것을 한 파일로 줍니다. `weather.fetch_range()`에
48시간 상한을 둔 것도 이 실수를 막기 위해서입니다.

### 1-2. 실시간 — API 허브의 `kma_sfctm2`

    https://apihub.kma.go.kr/api/typ01/url/kma_sfctm2.php
      ?tm=202511030900   관측 시각 (KST, 생략하면 가장 최근)
      &stn=133           대전
      &help=0            1로 주면 컬럼 설명이 함께 옵니다
      &authKey=...       .env의 APIHUN_KMA_TYPE01_KEY

**지금 키로 열려 있는 것은 이것 하나입니다.** 2026-08-25에 확인했습니다.

| 엔드포인트 | 무엇 | 상태 |
| --- | --- | --- |
| `kma_sfctm2.php` | 지상관측 시간자료, **한 시각** | ✅ 열림 |
| `kma_sfctm3.php` | 지상관측 시간자료, **기간(tm1~tm2)** | ❌ 403 "활용신청이 필요한 API" |
| `kma_sfcdd.php` / `kma_sfcdd3.php` | 지상관측 **일자료** | ❌ 403 |
| `awsh.php` | 방재기상관측(AWS) 시간자료 | ❌ 403 |

`kma_sfctm2`에 `tm1`·`tm2`를 넣어도 **기간으로 동작하지 않습니다** — 인자를 무시하고
현재 시각 한 줄을 돌려줍니다(실측). 기간이 필요하면 활용신청을 하십시오.

**응답의 `-9`는 대부분 '비가 안 왔다'는 뜻입니다.** 포털 CSV가 빈칸으로 주는 자리를
API는 `-9`로 줍니다. 실측으로 확인했습니다 — 비가 오던 시각을 조회하면 실제 강수량이
오고(2026-07-05 05시 9.4mm, CSV와 일치), 안 오던 시각은 시간·일강수가 모두 `-9`였습니다.
그래서 `-9`를 무조건 '모름'으로 읽으면 여름 내내 '모름'만 보게 됩니다. 다만 **겨울
(11~3월)의 3의 배수가 아닌 시각**은 진짜로 자료가 없는 것이라 구분해야 합니다.

> **활용신청을 하시겠다면**: API 허브 로그인 → 상단 `API 목록` → 해당 API의
> `활용신청` 버튼. 승인되면 같은 키로 열립니다. 신청 전에도 `fetch_range()`가
> 시각별 호출을 묶어 주므로 **하루치(24회)까지는 지금도 받을 수 있습니다.**

### 1-3. 예보는 아직 안 받았다

위 둘은 모두 **관측**입니다. 계획은 하루 앞서 세우므로 운영에 쓰려면 **예보**가
필요합니다(4장). 예보는 또 다른 API(`동네예보` 계열)이고 역시 활용신청 대상입니다.
**아직 신청·검증하지 않았습니다.**

## 2. 받은 자료 — 검증 결과

`data/raw_data/날씨/기상자료 (2025년).csv`, `기상자료 (2026년).csv`
(대전 133, CP949, 2025-01-01 00시 ~ 2026-07-31 23시, **13,848시간**)

| 항목 | 결과 |
| --- | --- |
| 간격 | 정시 1시간, 빠진 시각 **0** |
| 기온 | -12.9 ~ 36.5 °C — 정상 범위 |
| 강수 | 0 ~ 41.8 mm/시 — 정상 (호우 시 이 정도까지 옵니다) |
| 풍속 | 0 ~ 8.0 m/s |
| 습도 | 8 ~ 99 % |
| 결측 | 기온·풍속·습도 **0건**. 강수·적설의 빈칸은 결측이 아니라 "안 왔다" |
| 대여이력과 겹침 | 25년 01월 ~ 26년 03월 — **순수요가 있는 12개 기간 전부** |

**받은 자료는 그대로 쓸 수 있습니다.** 다만 읽을 때 두 가지를 반드시 지켜야 합니다.

### 2-1. 빈칸의 뜻이 컬럼마다 다르다

- **강수·적설의 빈칸 = 0** (안 왔다). 이걸 결측으로 지우면 13,848시간 중 강수 기록이
  있는 1,555시간만 남습니다 — 자료의 89%가 사라집니다. 가장 흔한 실수입니다.
- **기온·습도·풍속의 빈칸 = 진짜 결측** (장비 문제 등). 0으로 채우면 한여름 정오가
  영하가 됩니다. 앞뒤 시각으로 잇습니다.

### 2-2. 겨울 강수는 **3시간 누적**이다 (놓치기 쉽습니다)

기상청 규약입니다 — *"11월~익년 3월까지는 3시간 강수량(3,6,…24시 이외는 자료없음),
4~10월은 1시간 강수량"*. 실제로 확인했습니다.

| 달 | 강수 기록이 3의 배수 시각에 있는 비율 |
| --- | --- |
| 1·2·3·12월 | **100%** |
| 11월 | 85% (초순에 시간 단위 구간이 섞여 있습니다) |
| 4~10월 | 32~35% (= 우연히 그 시각인 것뿐) |

그대로 두면 **5시간 창 밖에서 온 비가 창 안으로 딸려 들어옵니다.** `_05_10`(05~09시)에
06시 값(03~06시 누적)이 통째로 들어가는 식입니다. 그래서 `weather.py`는 **겨울이고,
3의 배수 시각이고, 앞 두 시각이 빈칸일 때만** 그 값을 세 시간에 고르게 나눕니다.
세 조건을 모두 보는 이유는 11월처럼 두 방식이 섞인 달에서 멀쩡한 1시간 값을 쪼개지
않기 위해서입니다.

## 3. 읽는 코드 — `weather.py` 하나

**타슈를 `tashu.py` 하나로 부르는 것과 같은 이유입니다.** 파일과 API가 각자 컬럼과
결측 규칙을 정하면, 학습이 본 '비'와 화면이 보여 주는 '비'가 다른 것을 가리킵니다.

```python
import weather

hourly = weather.load_hourly()                 # 디렉터리 안의 CSV를 모두 이어 붙인다
window = weather.window_frame(hourly, "_05_10")  # 5시간 창 단위로 접는다
now    = weather.fetch_hour()                  # 지금 관측값 (API 허브)
```

| | 규약 |
| --- | --- |
| 컬럼 | `time`, `temp`, `rain`, `wind`, `humid`, `snow` |
| 창 접기 | 강수 **합** · 기온/풍속/습도 **평균** · 적설 **최대**(쌓인 높이라 더하면 안 됩니다) |
| 자정을 넘긴 창 | `_20_05`의 새벽 4시는 **전날 밤**으로 묶습니다 |
| 자료가 없으면 | 빈 표를 돌려줍니다 — **날씨는 있으면 좋고 없어도 되는 입력**입니다 |
| 경로 | `PBR_WEATHER_FILE` (파일이든 디렉터리든 됩니다. 기본 `data/raw_data/날씨`) |
| 관측소 | 대전 133 **한 곳**을 도시 전체에 씁니다 (대여소별로 쪼개지 않습니다) |

테스트는 `tests/test_weather.py` 24개가 위 규약과 화면 동작을 지킵니다.

## 4. 측정 — 날씨가 순수요를 설명하는가

재현: `python experiments/weather_impact.py`

붙이기 전에 재는 것이 이 저장소의 규칙입니다. 이유가 있습니다 — **날씨가 흔드는 것은
이용량이고, 이 파이프라인이 맞혀야 하는 것은 순수요(반납 − 대여)입니다.** 비가 와서
대여와 반납이 함께 반토막 나면 이용량은 급감해도 순수요는 그대로일 수 있습니다.
그러면 날씨를 넣어도 계획은 안 바뀝니다.

### ① 날씨는 이용량을 크게 흔든다

비 온 날(창 강수 ≥ 1mm)의 이용량은 **-58 ~ -78%**. 예상대로입니다.

### ② 그것이 순수요까지 온다

비 온 날의 재배치 필요량(Σ|순수요|)은 **-45 ~ -61%**. 전달됩니다.

### ③ 도시 총량 — 표본 밖 설명력 (5겹 교차검증)

지금 파이프라인이 쓰는 정보(**달 수준 + 평일/휴일 구분**)를 베이스라인으로 두고,
그 위에 날씨가 무엇을 보태는지 봤습니다.

| 시간대 | 구분 | 달 수준만 | + 날씨 | 보탠 몫 |
| --- | --- | ---: | ---: | ---: |
| `_05_10` | 평일 | 0.519 | 0.729 | **+0.210** |
| `_05_10` | 휴일 | 0.245 | 0.634 | **+0.389** |
| `_10_15` | 평일 | 0.350 | 0.804 | **+0.454** |
| `_10_15` | 휴일 | 0.260 | 0.772 | **+0.513** |
| `_15_20` | 평일 | 0.414 | 0.792 | **+0.377** |
| `_15_20` | 휴일 | 0.276 | 0.807 | **+0.532** |
| **평균** | | **0.344** | **0.756** | **+0.412** |

채택 문턱(+0.15)을 여섯 칸 모두에서 넘습니다. 설명력의 대부분은 **강수**가 냅니다
(기온은 오후 시간대에서만 의미 있게 기여합니다).

### ④ 작업 대상 대여소 — 진짜 판정

**도시 총량이 설명된다고 대여소별 예측이 그만큼 좋아지지는 않습니다.** 전체 평균으로
재서 정반대 결론을 낸 적이 있어([EXPERIMENTS.md](EXPERIMENTS.md) 2장), 이 저장소의
채택 기준을 그대로 적용했습니다 — **작업 대상만(`|mu| > 2`) · 평일/휴일 따로 ·
직전 달로만 학습 · 계절 보정(14일)을 켠 베이스라인과 비교**.

붙이는 방식은 계절 배율(`season_ratio`)과 똑같이 잡았습니다. 대여소별로 날씨를 나누지
않고 **도시 하나의 하루 배율**을 `mu`에 곱합니다.

| 시간대 | 구분 | MAE (현행) | MAE (+날씨) | 전체 | 비 온 날 | 맑은 날 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `_05_10` | 평일 | 2.723 | 2.622 | +3.6% | **+36.0%** | +0.1% |
| `_05_10` | 휴일 | 2.483 | 2.400 | +2.9% | **+44.1%** | -1.7% |
| `_10_15` | 평일 | 4.111 | 3.827 | +6.7% | **+46.6%** | +1.5% |
| `_10_15` | 휴일 | 4.488 | 4.279 | +4.1% | **+38.1%** | +1.0% |
| `_15_20` | 평일 | 3.628 | 3.468 | +4.4% | **+30.4%** | +0.9% |
| `_15_20` | 휴일 | 5.268 | 5.034 | +3.7% | **+51.2%** | +0.5% |

검증 달 51건 중 **45건에서 개선**. 그런데 평균 +4.3%라는 숫자는 성격을 감춥니다.

> **날씨는 매일 조금씩 좋아지는 개선이 아닙니다.**
> 비 오는 날(전체의 10%)에 **오차가 40% 줄고**, 나머지 90%의 날에는
> 사실상 아무 일도 일어나지 않습니다(+0.4%).

이것이 이 측정의 핵심입니다. 지금 파이프라인은 **비 오는 날 크게 빗나가고 있고**,
그 날들만 고치는 처방이 날씨입니다.

## 4-1. 머신러닝으로 붙여 봤다 — 아직 전면 교체는 아니다

사용자 질문: "머신러닝 예측 알고리즘을 도입할 수 있을까?" 이 저장소에는 이미 분위수
회귀 하네스가 있고(`demand_model.py`, HistGradientBoosting), 1.15.3에서 채택을
되돌린 뒤 **다음 시도(날씨)를 위해 남겨 둔** 상태였습니다. 그래서 날씨를 피처로 넣고
같은 채택 기준(`experiments/quantile_model_eval.py`)으로 다시 판정했습니다.

재현: `python experiments/quantile_model_eval.py --holdout "26년 03월" --quantile 0.97`

| 검증 달 | 모델 | 커버리지 (목표 95%) | 95%에서 벗어난 정도 | 과잉 |
| --- | --- | ---: | ---: | ---: |
| 26년 03월 | 기준 `mu + z·sigma` | 94.1% | 0.9%p | 7.74대 |
| | 분위수 0.97, **날씨 없이** | 94.4% | 0.6%p | 8.10대 |
| | 분위수 0.97, **날씨 포함** | 94.8% | **0.2%p** | 8.08대 |
| | 분위수 0.95, 날씨 포함 | 92.6% | 2.4%p | 7.13대 |

**날씨는 모델을 낫게 합니다**(0.6%p → 0.2%p). 그런데 여전히 **베이스라인을 명확히
이기지는 못합니다** — 커버리지를 얻는 대신 과잉이 7.74 → 8.08대로 늘어, 1.15.2에서
채택했다가 되돌린 것과 같은 **맞바꿈**입니다.

### 왜 커버리지로는 날씨의 이득이 안 보이는가

**비 오는 날의 손실은 결품이 아니라 과잉이기 때문입니다.** 비가 오면 필요량이
절반으로 줄어드는데 계획은 그대로이므로, 계획은 수요를 **덮기는 덮되 과하게 덮습니다.**
커버리지(덮었는가)는 멀쩡해 보이고 낭비만 늘어납니다. 갈라 보면 분명합니다.

| 검증 달 | | 커버리지 (기준 → 모델) | 과잉 (기준 → 모델) |
| --- | --- | --- | --- |
| 26년 03월 | **비 온 날** (1,499건) | 95.0% → 94.7% | **7.71 → 6.45대** |
| | 맑은 날 (14,211건) | 94.8% → 95.1% | 7.51 → 8.20대 |
| 25년 11월 | **비 온 날** (387건) | 94.3% → 96.6% | **8.34 → 5.55대** |
| | 맑은 날 (12,551건) | 97.2% → 97.4% | 8.24 → 8.85대 |

두 검증 달에서 같은 모양이 나옵니다 — **비 오는 날엔 확실히 낫고(과잉 -16~-33%),
맑은 날엔 조금 나쁩니다.** 전면 교체하면 90%인 맑은 날의 손해가 이득을 상쇄합니다.

### 그래서 권하는 것

**모델을 통째로 바꾸는 것보다 날씨 보정만 얹는 쪽이 낫습니다.** ④에서 잰 도시 배율
방식은 비 오는 날 오차를 40% 줄이면서 **맑은 날에는 중립(+0.4%)** 입니다. 추정기를
바꾸는 것이 아니라 정보를 하나 더 넣는 것뿐이라, 맑은 날 성질이 변하지 않습니다.

머신러닝 쪽은 **하네스를 이번 작업으로 갖춰 뒀습니다**(날씨 피처가 `FEATURES`에 있고,
학습·예측이 `add_weather()` 하나를 거칩니다). 표본이 더 쌓이거나 대여소 특성 피처가
붙으면 재판정은 명령 한 줄입니다.

## 5. 붙일 때 — 설계와 남은 결정

### 제안하는 방식: 계절 배율과 같은 자리, 같은 모양

```
target_qty = mu · (계절 배율) · (날씨 배율) + z · sigma · (…)
                                  ↑ 새로 붙는 것
```

- 도시 전체에 **하나의 배율**. 대여소별로 쪼개지 않습니다 — 관측소가 대전에 하나뿐이고,
  며칠치로 나누면 잡음만 커진다는 것은 계절 보정에서 이미 겪었습니다.
- 붙이는 자리는 **`demand_model.build_features()` 하나**입니다. 학습과 예측이 반드시
  같은 함수를 거쳐야 합니다(한쪽만 배율을 곱하면 조용히 틀립니다 — 테스트가 지킵니다).
- 배율은 0.2~2.0으로 자릅니다. 외삽으로 음수가 나오면 계획의 방향이 뒤집힙니다.

### 결정이 필요한 것 ①: 관측인가 예보인가

측정에 쓴 것은 **관측값**입니다. 계획은 하루 앞서 세우므로 운영에서는 그 자리에
**예보**가 들어가고, **예보 오차만큼 위 숫자는 줄어듭니다.** 강수 유무 예보는 비교적
잘 맞으므로 개선의 상당 부분은 남을 것으로 보이지만, **그것도 재 봐야 압니다.**

- 예보를 쓰려면: 동네예보 API 활용신청 → `weather.py`에 예보 클라이언트 추가 →
  예보 기준으로 ④를 다시 측정
- 관측만 쓰려면: 계획을 **당일 아침**에 세우는 운영에서는 직전 시각 관측이 곧 예보
  구실을 합니다(`_10_15`·`_15_20` 회차에 해당). `_05_10`은 전날 밤 관측뿐입니다.

### 결정이 필요한 것 ②: 얼마나 자동으로 반영할 것인가 → **2번으로 정했다 (1.20.2)**

작업지시서 규칙과 같은 문제입니다. 비 예보에 따라 **계획량을 자동으로 줄이면**,
예보가 빗나갔을 때 결품이 납니다. 후보:

1. **자동 반영** — `target_qty`에 배율을 곱한다 (측정한 그대로)
2. **알림만** — 계획은 그대로 두고 "오늘 비 예보, 실제 필요량은 계획의 60% 수준"을
   화면에 띄운다 (기사가 판단)
3. **문턱** — 강수 확률·강수량이 큰 날에만 반영한다

지금 저장소의 성향(작업지시서는 **판정만 하고 계획을 바꾸지 않는다**)에는 2번이
가깝습니다. 다만 재배치는 하루 전에 짜는 일이라 1번의 이득이 더 큽니다.

**사용자 결정(2026-08-25): 2번.** 계획을 세우는 화면에 지금 날씨를 띄우고, 계획량은
건드리지 않습니다. ①(예보)은 활용신청을 하기로 했고, 열리면 '지금 관측' 자리에
'오늘 예보'가 들어갑니다. 그때 ④를 예보 기준으로 다시 재고 나서 1번(자동 반영)을
다시 논의합니다.

### 화면에 어떻게 나오는가 (1.20.2)

실행 폼(`/`) 위에 한 줄이 붙습니다.

| 상태 | 화면 |
| --- | --- |
| 비가 오는 중 | **경고 상자** — "지금 비가 오고 있습니다 · 시간당 9.4mm · 23.1℃"와 함께 *"비 오는 날 실제 재배치 필요량은 평소의 40~55% 수준이었습니다"* |
| 지금은 그쳤지만 오늘 비가 왔음 | 같은 상자 (일강수 `rain_day`로 판단) |
| 비 안 옴 | 한 줄로 조용히 — "지금 비는 오지 않습니다 · 32.3℃ · 바람 1.9m/s" |
| 겨울의 3시간 사이 시각 | "지금 강수 여부를 알 수 없습니다" + 왜 그런지 |
| API 실패·키 없음 | **접습니다.** 날씨는 있으면 좋고 없어도 되는 정보입니다 |

두 가지를 지켰습니다.

- **화면을 그리는 요청 안에서 API를 부르지 않습니다.** 기상청이 느리면 실행 폼 자체가
  늦게 뜹니다. 브라우저가 화면을 띄운 뒤 `/api/weather`를 따로 부르고, 응답은 10분
  캐시합니다(관측은 정시마다 갱신되므로 더 자주 부를 이유가 없습니다).
- **'비'의 정의가 한 곳입니다** (`weather.RAIN_MM`). 학습이 본 '비'와 화면이 말하는
  '비'가 다른 것을 가리키면 안 됩니다.

## 6. 한계 — 인용할 때 함께 밝힐 것

1. **관측값으로 잰 숫자다.** 운영에는 예보가 들어가고 그만큼 줄어듭니다.
2. **관측소가 한 곳이다.** 대전 133의 값을 도시 전체에 씁니다. 국지성 호우는
   대여소마다 다르게 오지만 나눌 근거가 없습니다.
3. **비 온 날 표본이 적다.** 창 강수 ≥ 1mm인 날이 시간대별로 9~24일입니다.
   "비 오는 날 40% 개선"은 그 표본에서 나온 값입니다.
4. **눈은 재지 못했다.** 2025~26년 대전의 적설 기록은 350시간뿐이고, 대부분 이용량이
   낮은 겨울 새벽입니다. 별도 항으로 넣지 않았습니다.
5. **설명력의 대부분은 강수가 낸다.** 기온은 오후 창(`_10_15`·`_15_20`)에서만
   의미 있게 보태고(+0.11~0.19), 아침 창(`_05_10`)에서는 거의 0입니다(+0.003~0.02).
   풍속은 어디서도 눈에 띄지 않습니다. 변수를 더 늘리는 방향은 값이 적어 보입니다.
