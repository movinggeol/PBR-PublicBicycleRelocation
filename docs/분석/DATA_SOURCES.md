## 2. 계절은 어디에 들어가나 — 사용자 물음 *"계절 데이터는 어떻게 사용하고 있니?"*

**한 줄 답: 설계에는 두 군데 있는데, 지금 운영에서는 둘 다 꺼져 있다.**

| 장치 | 설계 | 지금 실제로 |
| --- | --- | --- |
| **계절 보정(warmup)** | 계획 대상 달의 **첫 14일 실적**으로 도시 전체 배율 하나를 구해 mu · sigma에 곱한다. 계절이 바뀌는 달(2월 → 3월 수요 1.5배)에 지난달 통계가 못 따라오는 것을 막는다 — 전환 달 커버리지 88.7 → 94.7%(3장) | 🔴 **한 번도 안 걸렸다.** 계획 대상 달의 대여이력이 없다 — 공개가 반년 단위로 늦어 2026-08 이후분은 2027년 초에 올라온다(THESIS ⑤). 8~10월 웹 실행 로그 9건이 모두 *"계절 보정 건너뜀"* 이다 |
| **날씨** | 계절 배율과 같은 자리에 날씨 배율을 곱하는 안(WEATHER 5장) | 계획량에는 넣지 않고 화면 알림만 한다(사용자 결정) |
| (학습 창) | 쓰는 달은 **보유한 가장 최근 달**(`latest_period()`) | 그래서 8~10월 계획은 **5~7개월 묵은 3월 통계를 배율 없이** 썼다. 안내 문구는 그것을 *"지난달 통계"* 라고 불렀다 — 1.26.328에서 *"26년 03월 통계 … 계획 대상 달보다 7개월 앞"* 으로 바로잡았다 |

**기온 · 날씨 추세 같은 계절성은 지금 계획에 들어가 있지 않다** — 들어가는 것은 3월 한 달의 대여소별 평균과 흩어짐뿐이다.

사용자가 제안한 *"작년의 이번 달 근처 1~2달을 비율로 참고"* 는 그 빈자리를 메우는 안이다. 같은 제안을 08-28에 쟀을 때(DEMAND_DISTRIBUTION
6-C)는 **직전 달이 손에 있다**고 놓고 견줘 졌다(작년 같은 달이 MAE 15% 나쁨). 지금 처지(가장 최근 달이 5~7개월 묵음)로 다시 잰 것이
[EXPERIMENTS 50장](EXPERIMENTS.md)이다 — 결과는 2-1절.

### 2-1. 50장 결과 — 작년 같은 철로 바꾸지 않는다 (2026-10-07)

| 물음 | 답 |
| --- | --- |
| 가장 최근 달이 5~7개월 묵어도 작년 같은 철보다 맞나 (대여이력 백테스트) | **맞다.** 공개 지연 1~7개월 모두 가장 최근 달이 이겼다 — 판정 칸 24칸 0승 24패, 작년 같은 철 × 성장 배율의 MAE가 6.2% 컸다(대상 달이 26년 1~3월뿐 — 겨울→봄에 한한 말) |
| 이번 가을 관측에서는 | 작년 같은 철 × 성장 배율이 4.2% 더 맞았다(평일 70회차 중 44승 5패). 그 몫은 **수준**(가을 이용이 3월보다 많다)이라, 3월 모양에 작년 계절 변화만 곱해도 같았다. 휴일은 오히려 졌다 |
| 계획이 나아지나 | **아니다.** 수준을 키우면 배송 대상이 33% 늘어, 같은 수의 재고 적은 대여소를 고르는 규칙 대비 이득이 사라졌다(3시간 +2.8 → −2.6%p) |

그래서 계획은 계속 **가장 최근 한 달**만 쓰고, 18개월은 실험 전용으로 남는다. 계절이 계획에 닿는 길은 여전히 계절 보정(warmup)뿐인데,
대여이력이 반년 늦게 올라오는 한 걸리지 않는다 — 실행 로그가 이제 그것을 바로 말한다(1.26.328).

## 3. 대여이력의 열 — 무엇을 읽고 무엇을 안 읽나

공개 파일은 19열이다. **DB(`rental_history`)에는 12열만 적재된다**(`db.RENTAL_COLUMNS`) — 나머지 7열(대여 · 반납의 구 · 동 ·
주소, 반납 대여소명)은 적재할 때부터 버린다. 파이프라인이 읽는 열은 단계마다 정해 두었다(`db.read_rental_source(columns=…)`).

| 열 | 어디서 쓰나 | 계획에 닿나 |
| --- | --- | --- |
| 대여일시 · 반납일시 · 대여_대여소ID · 반납_대여소ID | `raw_to_net.py` → 순수요 | ✅ 계획의 전부 |
| 대여_대여소명 · 대여_X/Y좌표 | `api_to_info.py` → 대여소 정보(이름 · 좌표 보조), 공식 통계 대조(`survey_crosscheck.py`) | 이름 · 좌표는 API가 정본 |
| 이용시간(분) · 이용거리(km) | `api_to_info.py`가 대여소별 **합계만** 낸다 — 웹 *자료* 화면의 대여소 정보 표 | ❌ 계획 무관. 예전 IQR 깎기가 이 두 열로 긴 이용을 지워 대여 기록을 달마다 ~~14~16%~~ 12~16% 깎았다(순수요는 그 기록에서 나온다)(42장 — 지금은 걸지 않는다. 2026-10-08 점검: [DECISIONS 6-1](DECISIONS.md)의 DB ÷ 원본 행 수가 달마다 0.837~0.879, 곧 12.1~16.3% 빠짐이다) |
| 자전거번호 · 반납_X/Y좌표 | 실험만 — 공사 재배치 복원(`rebalance_trace.py`, 44장), 고장 수거(`broken_collect.py`, 34장), 자전거 회전(`bike_turnover.py`) | ❌ |
| 대여 · 반납의 구 · 동 · 대여소주소, 반납_대여소명 (7열) | **DB에 적재하지 않는다** — 어디서도 읽지 않는다 | ❌ |

## 5. 데이터가 계획에 들어가는 길 (요약)

```
타슈 API ─ 재고 · 거치대 · 좌표 ──────────────┐
대여이력(가장 최근 한 달) → 순수요 → mu · sigma ─┼→ 목표 재고 → rebal_qty → 군집(K-Medoids) → ILP → VRP(TMAP 이동시간 식) → 작업지시서
공휴일 → 평일 · 휴일 중 한쪽만 ──────────────────┘
재고이력 ─────────────────────────────────────────→ (평가만) 결품 실측 · 사후 판정 · 다음 회차 예상
날씨 ─────────────────────────────────────────────→ (알림만) 실행 폼 위 예보
```
