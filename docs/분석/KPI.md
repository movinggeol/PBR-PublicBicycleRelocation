## 2. 먼저 짚어야 할 문제 — 지금 지표는 "계획"이지 "결과"가 아닙니다

`improvement_rate`가 어떻게 만들어지는지 따라가 보면 문제가 드러납니다.

```text
target_qty  ← 수요 통계(mu, sigma)로 계산한 목표 재고
rebal_qty   ← target_qty − stock  (tanh 완화, 정수화, 상위 N개 컷)
new_stock   ← stock + rebal_qty
improvement ← |stock − target| − |new_stock − target|
```

`rebal_qty`가 `target − stock`에서 파생되므로, **개선률은 "계획이 자기가 세운 목표를
얼마나 채웠는가"를 잽니다.** 이용자가 실제로 자전거를 탈 수 있었는지와는 다른 얘기입니다.

- 계획대로 완전히 옮기면 개선률은 100%에 수렴합니다.
- 100%가 안 나오는 이유는 tanh 완화·정수화·Pick/Drop 총량 맞추기 컷 때문이지,
  현실의 수요가 빗나가서가 아닙니다.
- 즉 **목표 재고(`target_qty`)가 틀렸다면 개선률이 높아도 의미가 없습니다.**

README의 "평균 불균형 개선 약 70%"도 이 성격의 수치입니다. 대외적으로 쓸 때는
**"계획 달성률"**임을 밝히거나, 아래 3-B의 실측 지표를 함께 제시하는 것이 정확합니다.

**결론: KPI를 계획 지표와 실측 지표로 나누고, 실측 쪽을 새로 만들어야 합니다.**

## 3. 제안하는 KPI 체계

### A. 계획 지표 — 최적화가 의도대로 작동했나 ✅ 구현됨

| 지표 | 정의 | 상태 |
| --- | --- | --- |
| 불균형 개선률 | `improvement / bf_imbalance` 평균 | ✅ |
| Pick/Drop별 개선률 | 작업 유형별 평균 | ✅ |
| 목표 달성 대여소 비율 | `af_imbalance ≤ 1`인 대여소 비율 | 🟡 계산 가능 |
| 미처리 작업량 | 후보에 올랐으나 계획에서 빠진 수량 | 🟡 계산 가능 |

`improvement_rate` 하나만 보면 착시가 생기므로, **미처리 작업량**을 함께 봐야 합니다.
상위 50개 컷과 Pick/Drop 총량 맞추기에서 잘려나간 대여소가 얼마나 되는지가
"계획이 얼마나 욕심을 줄였는지"를 보여줍니다.

### B. 실측 지표 — 이용자가 실제로 자전거를 탈 수 있었나 ✅ 결품 시뮬레이션 구현됨

DB에 `rental_history`가 들어왔으므로(DB_PLAN 4단계) **이제 계산할 수 있습니다.**

| 지표 | 정의 | 상태 |
| --- | --- | --- |
| **결품 시간** | 재고가 0인 시간 (재배치 전후 비교) | ✅ `stockout_hours_before/after` — **VRP가 실제로 옮긴 양 기준**(1.18.4) |
| 계획 기준 결품 | 계획량이 전부 집행됐다고 본 값 | ✅ `stockout_hours_plan` — 집행 값과의 차이가 **계획과 집행의 격차** |
| 포화 시간 비율 | 재고 = 거치대 수인 시간 비율 | 🔴 반납 실패 측정 |
| 수요 충족률 | 실제 대여 성사 건수 / 잠재 수요 | 🔴 기회손실 규모 |
| 재배치 대여소 적중률 | 재배치한 대여소에서 실제 대여가 늘었나 | 🔴 대상 선정 검증 |

재고 시계열이 없어도 **순수요로 궤적을 복원**할 수 있습니다.

```text
stock(t) = clip(stock(0) + Σ(반납 − 대여), 0, parking_lot)
결품 시간 = stock(t) == 0 인 시간대 수
```

`rental_history`에서 시간대별 대여·반납을 집계하면 그대로 나옵니다. 재배치 전
`stock(0)`과 재배치 후 `stock(0) + rebal_qty`로 각각 돌려 비교하면 **"재배치로
결품 시간이 몇 시간 줄었는가"** 라는, 계획이 아닌 결과에 가까운 지표가 됩니다.

> 주의: 이것도 시뮬레이션이지 실측은 아닙니다. 진짜 실측은 재배치를 실제 집행한 뒤
> 다음 기간의 대여 이력을 관측해야 합니다. 다만 지금 데이터로 갈 수 있는 가장 먼 지점입니다.

#### 첫 실측 결과 (25년 11월, 87곳 × 20일)

| 회차 | 결품 시간(전) | 결품 시간(후) | 감소 | 개선 / 악화 |
| --- | --- | --- | --- | --- |
| `_05_10` | 2.30h | **0.50h** | −1.80h | 50곳 / **0곳** |
| `_10_15` | 2.00h | 0.28h | −1.71h | 50곳 / 0곳 |
| `_15_20` | 1.79h | 0.34h | −1.45h | 50곳 / 0곳 |

대여소 한 곳이 하루 평균 겪는 결품 시간입니다(5시간 창 기준).
**Pick 대여소에서 결품이 늘어난 경우가 한 건도 없었습니다.** 회수가 부작용을 낳지
않았다는 뜻이라 확인해 봤더니 근거가 분명했습니다.

| | Pick 대여소 (37곳) | Drop 대여소 (50곳) |
| --- | --- | --- |
| 재고(중앙값) | 25대 → 회수 후 16대 | **0대** |
| 5시간 누적 순수요 | **−0.7대** (반납이 더 많음) | +4.3대 |
| 결과 | 바닥날 일이 없음 | 결품 발생 → 공급으로 해소 |

**Drop 대여소의 재고 중앙값이 0대**라는 게 핵심입니다 — 절반 이상이 완전히 비어
있었고, 결품이 거의 전부 여기서 났습니다. 재배치 효과가 큰 이유이기도 합니다.

#### 이 수치를 읽을 때의 한계

- **시뮬레이션입니다.** 재배치를 실제 집행하고 관측한 값이 아닙니다.
- **시점이 다릅니다.** 초기 재고는 TASHU API의 현재 스냅샷인데 순수요는 25년 11월
  20일치입니다. "지금 재고로 그때 수요를 겪으면"이라는 가상 시나리오이며,
  `target_qty` 계산도 같은 구조입니다.
- **결품 시간의 하한입니다.** 재고를 0에서 자르므로(없는 자전거는 빌릴 수 없음)
  못 빌린 수요는 사라집니다. 실제 불편은 이보다 클 수 있습니다.
- **5시간 동안 아무도 채우지 않는다고 가정**합니다. 회차 중간의 추가 보충은 없습니다.

### C. 운영 지표 — 현장에서 실행 가능한가 ✅ 구현됨 (1.19.3)

| 지표 | 정의 | 상태 |
| --- | --- | --- |
| 총 이동거리 (km) | 클러스터 합계 | ✅ `route_summary` |
| 클러스터별 총 소요시간 (분) | 이동 + 작업 | ✅ `route_summary` |
| **시간 예산 준수율** | 소요시간 ≤ 목표(120분)인 회차 작업 비율 | ✅ `/vehicles`·step4 |
| 차량당 처리 대수 | 처리대수 / 클러스터 | ✅ `route_summary` |
| **차량 부하 편차** | 차량별 누적 작업시간의 최대 − 최소 | ✅ `/vehicles` |
| **차량 가동률** | 출동한 차량 / 보유 21대 | ✅ `/vehicles` |
| 공차 이동 비율 | 적재 0인 구간의 이동거리 비율 | ✅ `empty_distance_ratio` (1.19.3) |
| depot 복귀 횟수 | `action = 'return'` 건수 | ✅ `depot_returns` (1.19.3) |

차량 부하 편차와 가동률은 [FLEET.md](../구현/FLEET.md)의 로테이션이 제대로 도는지 보는 지표입니다.
편차가 계속 벌어지면 배정 규칙이나 회차 구성을 손봐야 한다는 신호입니다.

**시간 예산 준수율이 가장 중요합니다.** [메모.md](../기록/메모.md)의 트러블슈팅 기록에
"수요 예측이 5시간짜리인데 작업에 4시간이 걸리면 의미가 없다"는 문제가 적혀 있습니다.
`TIME_BUDGET_MINUTES`(기본 120분) 기준으로 step4 콘솔과 `/vehicles` 화면에 표시됩니다.

**실측 준수율은 78~85%입니다**(`_05_10`에는 196분짜리 회차도 있었습니다). 원인을
44개 군집으로 재 보니 소요시간을 지배하는 것은 대여소 수(r=0.80)나 처리 대수(0.78)가
아니라 **이동 거리(r=0.966)** 였고, 초과 군집은 전부 45~56km로 정상(30km)보다
지리적으로 흩어져 있었습니다.

기본값은 여전히 **점검 기준일 뿐 제약이 아닙니다.** 다만 1.21.6에서 **제약으로 걸
수 있게** 했습니다 — `--enforce-time-budget`(또는 `PBR_ENFORCE_TIME_BUDGET=1`)를 켜면
VRP가 예산을 넘기는 작업 앞에서 멈추고 depot으로 돌아옵니다.

| | 현행(점검만) | 예산 강제 |
| --- | --- | --- |
| 초과 회차 | 4건 | **0건** |
| 최장 소요 | 196.3분 | **116.8분** |
| 미집행 | 0대 | 25대 (계획의 3.2%) |
| **결품 시간** | — | **+0.011h (40초)** |

**초과가 전부 사라지는 대가가 결품 40초**입니다. 판정을 미집행 대수가 아니라 결품으로
한 것이 요점입니다 — "3.2%를 못 옮긴다"만 보면 나빠 보이지만 이용자가 겪는 것은
40초입니다. 재현: `experiments/baseline/budget_enforce.py`.

⚠️ **기본은 꺼 두었습니다.** 계획의 성격이 바뀌는 변경이고(못 옮기는 대수가 생깁니다),
기본값이 조용히 바뀌면 지난 실행과 비교가 성립하지 않습니다.

### D. 효율 지표 — 투입 대비 산출 ✅ 구현됨 (1.19.3)

| 지표 | 정의 | 의미 |
| --- | --- | --- |
| **km당 개선량** | `Σ improvement / 총 이동거리` | 1km 움직여 불균형 몇 대를 줄였나 |
| 분당 처리 대수 | `처리대수 / 총소요시간` | 작업 밀도 (`bikes_per_minute`) |
| 이동시간 비율 | `총이동시간 / 총소요시간` | 낮을수록 좋음 (`travel_time_ratio`) |

기존 두 축(효과·비용)을 하나로 묶어주는 지표라, **알고리즘을 바꿨을 때 좋아졌는지**
판단하는 데 가장 유용합니다. 예: VRP를 OR-Tools로 바꾸면 km당 개선량이 올라가야 합니다.

### E. 모델·데이터 품질 지표 ✅ 화면까지 연결됨 (1.19.3)

| 지표 | 정의 | 상태 |
| --- | --- | --- |
| **수요 예측 오차** | 실제 순수요 vs `mu` (MAE/RMSE) | ✅ `tools/backtest_demand.py` |
| 클러스터 균형도 | `max\|balance\|`, `mean\|balance\|` | 🟡 step1이 이미 출력 |
| ILP 최적성 갭 | CBC `gapRel` 실제 달성값 | 🟡 solver에서 추출 가능 |
| 단계별 실행 시간 | step0~4 각각 | ✅ run_pipeline이 찍는다 (1.19.0) |
| 대여소 커버리지 | 분석 대상 / 전체 대여소 | ✅ `station_coverage` (1.19.3) |

**수요 예측 오차가 A~D 전부의 전제입니다.** 1.19.3부터 백테스트 결과가
`demand_backtest` 테이블에 쌓이고 `/kpi`의 '수요 예측은 얼마나 맞나' 절에
나옵니다. 그전에는 콘솔에만 찍혀서, 실행할 때마다 사람이 기억해야 했습니다.
**기준선(늘 0이라고 예측)을 못 이기는 시간대는 화면에서 붉게 표시됩니다** —
그 시간대의 목표 재고는 근거가 약하다는 뜻입니다.
 `target_qty`가 `mu`와 `sigma`에서 나오므로,
`mu`가 틀리면 그 위의 모든 지표가 허수입니다.

```powershell
python tools/backtest_demand.py                    # 전 시간대
python tools/backtest_demand.py --duration _05_10  # 하나만
```

한 달로 `mu`를 만들고 **다음 달** 실제 순수요를 얼마나 맞히는지 잽니다
(2025-04 ~ 2026-03의 연속 월 9쌍, 대여소 1,369곳).

### 백테스트 결과 — 세 가지가 드러났습니다

| 시간대 | MAE | 기준선(0 예측) | 개선 | 커버리지 | 95%에 필요한 z |
| --- | --- | --- | --- | --- | --- |
| `_05_10` | 1.29 | 1.66 | **+22.5%** | 91.7% | 2.07 |
| `_10_15` | 1.14 | 1.14 | **−0.2%** ⚠ | 92.7% | 1.98 |
| `_15_20` | 1.57 | 1.77 | +11.0% | 92.7% | 1.96 |
| `_20_05` | 1.44 | 1.53 | +6.0% | 92.8% | 1.94 |

**1. 출근 시간대에서만 예측이 확실히 쓸모 있어 보입니다.** `_05_10`은 기준선 대비
22.5% 정확한데 `_10_15`는 −0.2%로 "순수요 0"이라고 찍는 것과 차이가 없습니다.

> ⚠️ **이 해석은 뒤에 뒤집혔습니다.** 위 표의 MAE는 **전체 1,369곳 평균**인데,
> 파이프라인이 실제로 손대는 곳은 `|rebal_qty| > 2`인 일부뿐입니다.
> 작업 대상만 놓고 다시 재면 `_10_15`의 `mu`도 오차를 **40.2%** 줄입니다.
> `_10_15`는 대여소의 72.8%가 `|mu| < 0.5`라, 손대지도 않는 그 대여소들이
> 전체 평균을 지배했던 것입니다.
> → 자세한 내용과 재현은 [EXPERIMENTS.md](EXPERIMENTS.md) 2장.
>
> **예측 정확도는 작업 대상 대여소에서 재야 합니다.** 전체 평균은 파이프라인이
> 건드리지 않는 대여소에 희석됩니다.

**2. `z = 1.65`가 부족합니다.** 설계 의도는 95% 커버리지인데 실측은 91.7~92.8%입니다.
정규분포를 가정한 값인데 실제 순수요는 꼬리가 두껍습니다.
→ **`z = 1.99`로 변경했습니다** (`project_config.TARGET_Z`). z 스윕 결과 평균
커버리지 92.5% → 94.9%가 되고, 대가는 처리 상한 +30%입니다
([EXPERIMENTS.md](EXPERIMENTS.md) 1장).

**3. 편향은 없습니다.** 모든 시간대에서 ±0.01대 이내 — 평균 자체는 잘 맞습니다.
문제는 평균이 아니라 **분산의 크기를 과소평가**하는 것입니다.

### 계절 전환기가 가장 약합니다

2월로 3월을 예측할 때 커버리지가 86.5~90.2%로 떨어집니다. 대여량이
31만 건 → 55만 건으로 1.8배 뛰는 봄철 급증을 한 달 전 평균이 따라가지 못합니다.

**`z`를 올리는 것만으로는 해결되지 않습니다.** z=2.10까지 올려도 전환 달의
`_05_10`은 90.4%에 머뭅니다. 분석 달 첫 14일 실적으로 배율을 보정하면
z=1.99에서 95.6%까지 회복됩니다 — 근거는 [EXPERIMENTS.md](EXPERIMENTS.md) 3장이고,
구현은 아직 하지 않았습니다([TODO.md](../기록/TODO.md)).

### ⚠️ z가 다른 실행끼리 개선률·목표 도달률을 비교하지 마세요

**개선률**과 **목표 도달률**은 `target_qty`를 분모로 삼습니다. `z`를 올리면 목표
자체가 높아지므로 같은 작업을 해도 두 지표는 낮아집니다. 실제로 z를 1.65 → 1.99로
올렸을 때 결품 시간은 10~27% 줄었는데 개선률과 목표 도달률은 함께 떨어졌습니다.

**성능이 나빠진 것이 아니라 자를 바꾼 것입니다.** `z`나 목표 산출식이 다른 실행끼리는
**결품 시간**으로 비교하세요 — 실제 재고가 0이 되어 빌릴 수 없던 시간이라
목표값과 무관합니다. 실측 대조표는 [EXPERIMENTS.md](EXPERIMENTS.md) 4장에 있습니다.

## 4. 저장 구조 (구현됨)

지표가 `metrics`(대여소 단위)와 `route_summary`(클러스터 단위)에 흩어져 있어
"이번 실행의 요약 숫자 한 줄"을 얻으려면 매번 집계해야 했습니다.

**`kpi_summary` 테이블**로 해결했습니다 — 실행 1건(run_label + duration) = 1행.
step4가 자동으로 채웁니다. 실제 스키마는 [db.py](../../db.py)의 `SCHEMA`에 있고,
아래는 설계 의도를 보여주는 요약입니다.

```sql
CREATE TABLE kpi_summary (
    run_label            TEXT NOT NULL,
    duration             TEXT NOT NULL,
    -- A. 계획
    avg_improvement_rate REAL,
    target_met_ratio     REAL,   -- af_imbalance <= 1 비율
    unhandled_qty        INTEGER,
    -- B. 실측(시뮬레이션)
    stockout_hours_before REAL,
    stockout_hours_after  REAL,      -- 실제로 옮긴 양 기준
    stockout_hours_plan   REAL,      -- 계획량이 전부 집행됐다고 본 값
    -- C. 운영
    total_distance_km    REAL,
    max_cluster_minutes  REAL,
    time_budget_met      REAL,   -- 소요시간 <= 임계값 비율
    vehicles_used        INTEGER,-- 투입 차량 수
    vehicle_load_gap     REAL,   -- 차량 누적 시간 편차(형평성)
    -- D. 효율
    improvement_per_km   REAL,
    -- E. 품질
    demand_mae           REAL,
    cluster_max_imbalance INTEGER,
    computed_at          TEXT NOT NULL,
    PRIMARY KEY (run_label, duration)
);
```

이렇게 두면 **실행 간 비교가 조회 한 번**이 됩니다. DB_PLAN 5단계(실행 이력 비교 화면)가
바로 이 테이블 위에 올라갑니다.

```sql
SELECT run_label, avg_improvement_rate, improvement_per_km, max_cluster_minutes
FROM kpi_summary WHERE duration = '_05_10' ORDER BY run_label;
```

## 5. 대시보드 표시 제안

`/kpi` 화면을 하나 두고 3단으로 구성합니다.

1. **헤드라인 4개** — 개선률 / km당 개선량 / 최장 소요시간 / 결품 시간 감소
   (현재 실행 값 + 직전 실행 대비 증감 화살표)
2. **추세** — `run_label` 축의 꺾은선. 알고리즘을 바꿨을 때 효과를 눈으로 확인
3. **실행 비교 표** — 두 `run_label`을 골라 지표별 차이

지표 하나만 크게 띄우는 것은 피해야 합니다. **개선률은 올리기 쉽고(계획을 욕심내면 됨),
그러면 소요시간이 늘어납니다.** 효과·비용·효율을 나란히 놓아야 트레이드오프가 보입니다.

## 7. 주의사항

- **지표를 목표로 삼으면 지표가 망가집니다.** 개선률만 보면 "쉬운 대여소만 골라
  개선률을 올리는" 왜곡이 생깁니다. 처리한 총량(`처리대수`)과 항상 같이 보세요.
- **평균은 분포를 감춥니다.** 개선률 평균 75%가 "모두 75%"인지 "절반은 100%, 절반은 50%"인지
  구분되지 않습니다. 중앙값·최솟값이나 히스토그램을 함께 두는 편이 낫습니다.
- **시간대(`duration`)별로 따로 봐야 합니다.** 출근(05~10)과 퇴근(15~20)은 수요 구조가
  반대라 섞으면 둘 다 흐려집니다. `kpi_summary`의 PK에 `duration`을 넣은 이유입니다.
- **비교는 같은 조건에서만.** `run_label`이 달라도 원천 데이터 기간(`period`)이 다르면
  개선률 비교는 무의미합니다. 비교 화면에서 `period`를 함께 표시해야 합니다.
- ✅ **결품 지표는 VRP가 실제로 옮긴 양으로 잽니다** (1.18.4). 그전에는
  `stock + rebal_qty`로 계산해 **계획이 100% 집행된다고 가정**했고, 그래서
  편익을 약 13% 과대평가하면서(0.42h 대 0.48h) **방법 간 비교에는 쓸 수 없었습니다** —
  대조군 실험에서 제안 방법·그리디·지리 균등 군집·무재배치의 점수가 **전부 0.42h로
  같았습니다** ([EXPERIMENTS.md](EXPERIMENTS.md) 5장).
  계획 기준 값은 `stockout_hours_plan`으로 함께 남습니다.
  **두 값의 차이가 곧 계획과 집행의 격차**이므로 함께 보세요.
  ⚠️ **1.18.4 이전에 쌓인 `stockout_hours_after`는 계획 기준입니다** — 실행 라벨이
  다른 값을 비교할 때 주의하세요.
- ✅ **소요시간은 depot 복귀까지 포함합니다 (1.19.1).** 그전에는 빠져 있어
  `max_cluster_minutes`와 `time_budget_met`이 낙관적이었습니다 ([TODO.md](../기록/TODO.md) 1-1).
  ⚠️ **1.19.1 이전에 쌓인 값과 섞어서 비교하지 마세요** — 같은 계획이라도
  소요시간이 30%가량 낮게 찍혀 있습니다.

### '목표 도달 비율'은 실행 품질이 아닙니다 (1.19.7)

**헤드라인에서 내렸습니다.** 표에는 그대로 있지만, 이 값이 낮은 것은 대개 계획을
못 지켜서가 아닙니다.

계획량은 격차 그대로가 아니라 `Q·tanh(격차/Q)`로 눌립니다(`Q` = 적재 용량 10대,
[FORMULATION.md](FORMULATION.md) 3장). 그래서 격차별로 이렇게 됩니다.

| 목표까지 격차 | 계획량 | 남는 차이 | 도달? |
| --- | --- | --- | --- |
| 5대 | 4대 | 1 | ✅ |
| 7대 | 6대 | 1 | ✅ |
| 8대 | 6대 | 2 | ❌ |
| 10대 | 7대 | 3 | ❌ |
| 20대 | 9대 | 11 | ❌ |

**도달이 가능한 구간은 격차 4~7대뿐입니다.** 작업 대상 기준(`|rebal_qty| > 2`)과
겹쳐 보면 창이 아주 좁습니다. 실측(25년 11월)에서 격차는 **중앙값 5~10대,
최대 58대**였고, `_05_10`의 도달률 6%는 대부분 여기서 나옵니다 — 실행이 나빠서가
아닙니다.

그래서 헤드라인에는 **`reachable_ratio`(한 번에 닿는 범위)** 를 대신 둡니다.
목표까지 벌어진 양이 적재 용량 안이라 **한 번 방문으로 해결할 수 있었던** 대여소
비율입니다. 낮으면 "애초에 한 회차로는 못 푸는 일감이 많다"는 뜻이고, 그건 계획의
잘못이 아니라 **문제의 크기**입니다. `gap_median`·`gap_max`도 함께 기록합니다.

> **`tanh`가 옳은지는 아직 실험한 적이 없습니다.** `z`·`γ`와 달리 근거 기록이
> 없는 관행값입니다. `clip(±Q)`으로 바꾸면 격차 10대까지 한 번에 메울 수 있게
> 되지만 대여소당 작업량이 늘어 시간 예산을 압박합니다 — 재실험 과제입니다
> ([TODO.md](../기록/TODO.md)).

### Pick 쪽 결품이 조금 느는 것은 정상입니다 (1.19.6)

재고를 빼내는 곳이니 당연하고, `mu`가 크게 음수인 대여소는 `target_qty`가 0으로
잘려 거의 다 실어 갑니다. 자전거가 다시 흘러드니 맞는 판단이지만, 그 대여소가
유난히 붐빈 하루에 결품이 한두 시간 생깁니다 — `z`가 허용한 꼬리입니다.

실측(26년 03월 `_05_10`): **Pick +1h 대 Drop −2915h = 0.03%**, 악화 1곳.
step4는 이 몫이 `PICK_HARM_WARN_SHARE`(5%)를 넘을 때만 경고합니다. 넘지 않아도
몫은 늘 찍으므로 판단 근거는 남습니다.

**따라서 결품 합계가 이 재배치의 성적입니다.** Pick 쪽 숫자만 떼어 "이 계획이
어떤 대여소를 나쁘게 했다"고 읽으면 안 됩니다.

- 하루는 요일·날씨 효과를 가르지 못합니다.

### 후속 검증 — 'pick 후보가 비어 있을 것'이라는 걱정은 틀렸다 (1.21.9)

아래 '재고 0이 48.8%'를 보고 **"빼 올 자전거가 없는 것 아닌가"** 를 의심했는데,
재 보니 아니었다(`experiments/structure/pick_feasibility.py`).

| 시간대 | pick 후보 | 계획 재고 | 실측 재고 | **재고 0** | 계획대로 뺄 수 있는 후보 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `_05_10` | 42곳 | 19.0 | 18.0 | **0%** | 98% |
| `_10_15` | 32곳 | 24.0 | 21.0 | **0%** | 97% |
| `_15_20` | 41곳 | 21.0 | 18.0 | **0%** | 90% |

못 채우는 양은 **934대 중 33대(3.5%)** 다.

**왜 48.8%와 다른가**: 그 숫자는 **전체 1,372곳**의 것이고, `pick` 후보는
**재고가 남아도는 곳만 골라낸 집합**이다(`rebal_qty < 0` = 여기 넘친다).
그러니 그중에 빈 대여소가 있을 리 없다. **전체 평균을 부분집합에 적용한 오독**이었다
— 이 저장소가 반복해 겪은 함정과 같은 종류다([RETROSPECTIVE](../기록/RETROSPECTIVE.md) 4장 ⑥).

**그래도 남는 것 둘**:

- `_15_20`만 유독 약하다(90%, 하루 종일 88% 언저리). 퇴근 시간대라 저녁으로 갈수록
  빠져나가기 때문으로 보인다. 이 회차만 여유를 더 둘 근거가 될 수 있다.
- 3.5%는 작지만 **ILP가 pick·drop을 짝지어 놨으므로 drop도 같은 만큼 못 채운다** —
  실제 손실은 두 배로 봐야 한다.

### 덤으로 드러난 것 — 평시 재고가 매우 낮다

관측 50,764건 중 **48.8%가 재고 0**이었고, 1,372곳 중 **1,009곳이 하루 중 한 번은
비었으며 261곳은 내내 0**이었습니다. 작업 대상 대여소만 봐도 시간의 39.5%가 0입니다.

이 숫자는 재배치 계획의 전제를 다시 보게 합니다 — **빼 올 자전거가 있는 대여소가
생각보다 적을 수 있습니다.** `pick` 후보가 실제로 존재하는지는 수집 데이터가 더
쌓이면 따로 재야 합니다.

## 8. 결품 시간은 논리적으로 방어되는가 (2026-08-28, 수정안 37)

> *"꽤 민감하며 논리적으로 공격받을 만한 지표이다. (…) 이 데이터 조사를 멈추면
> 사라지는 설득력이라고 생각이 든다."*

맞는 지적입니다. **공격 지점을 전부 재서 적어 둡니다** — 심사에서 나올 질문을
미리 답해 두는 것이 이 절의 목적입니다.

### 지표가 실제로 무엇을 세는가

```text
stock(t+1) = clip(stock(t) - net(t), 0, 거치대 수)
결품 시간   = stock <= 0 인 시각의 개수
```

`_05_10`은 5시간 창이므로 **대여소·일당 최대 5.0h**입니다. 0.55h는 *"하루 5시간
중 33분이 결품"* 이라는 뜻입니다.

### 공격 지점 넷 — 크기를 재 두었습니다

**① 초기 재고 스냅샷에 크게 흔들린다 (가장 큼)**

재고는 **실행 시각의 한 순간**입니다. ±3대만 달라져도:

| 초기 재고 | 재배치 전 | 후 | **개선량** |
| --- | --- | --- | --- |
| −3대 | 2.449 | 0.713 | **1.735** |
| **±0 (현행)** | 2.003 | 0.549 | **1.454** |
| +3대 | 0.787 | 0.328 | **0.459** |

**개선량이 3.8배 흔들립니다.** 스냅샷 시각이 몇 시간만 어긋나도 값이 달라집니다.

**② 재배치를 언제 반영하느냐**

현행은 창의 **첫 시각에 전량** 더합니다. 실제 작업은 회차 내내 순차로 일어납니다.

| 반영 시각 | 결품 |
| --- | --- |
| **05시 (현행)** | **1.324h** |
| 07시 | 1.542h |
| 09시 | 1.687h |

**27% 차이입니다. 현행이 가장 낙관적입니다.**

**③ 못 빌린 수요가 사라진다**

`clip(lower=0)`이라 재고 0에서 더 빠지지 않습니다. 대기 수요가 다음 시간으로
넘어가지 않으므로 **결품을 낮춰 잡습니다.**

**④ 시간 안의 분포를 모른다**

시간마다 `net_HH`를 한 번에 빼므로 **한 시간 안의 짧은 결품**을 놓칩니다.

> ③④는 둘 다 **같은 방향**입니다 — 실제 결품은 이 값보다 큽니다.
> **그래서 이 지표는 하한(lower bound)입니다.** 이렇게 쓰면 ③④는 공격이
> 아니라 **보수적 추정**이라는 근거가 됩니다.

### 관측으로 그 격차를 쟀습니다

10분 간격 재고 관측과 맞대어 봤습니다 (`observed_stockout.py --save`).

| 회차 | 복원(step4) | 실측(관측) | **보정비** | 근거 |
| --- | --- | --- | --- | --- |
| `_10_15` | 1.73h | 2.01h | **1.16배** | 3일·681곳 |

**예상한 방향과 일치합니다** — 복원이 16% 낮춰 잡고 있었습니다.
③④의 진단이 맞았다는 증거입니다.

### ⚠️ "수집을 멈추면 설득력이 사라진다"에 대한 답

**보정 계수를 DB에 남깁니다**(`stockout_calibration` 표).

| 무엇이 | 수집이 멈추면 |
| --- | --- |
| 관측 자료(`stock_history`) | 더 쌓이지 않는다 |
| **보정 계수** | **표에 남는다** ✅ |

계수와 함께 **언제·며칠치로·어느 창에서 쟀는지**를 적어 두므로, 나중에도
*"3일 관측으로 얻은 1.16배"* 라고 밝히며 인용할 수 있습니다.
**덮어쓰지 않고 쌓으므로** 관측이 늘면 추세가 보입니다.

⚠️ **계수를 파이프라인이 자동으로 곱하지는 않습니다.** 3일치로 그럴 근거가
없습니다. 지금은 **화면에 함께 띄워 하한임을 밝히는** 단계입니다.

### 논문에 쓸 문장

> *"결품 시간은 순수요로 복원한 재고 궤적에서 재고가 0인 시각을 센 값이다.
> 재고 0에서 미충족 수요를 이월하지 않고, 시간 내 분포를 균등으로 보므로
> **실제 결품의 하한**이다. 10분 간격 관측과 대조한 결과 실측이 복원의 1.16배였고
> (3일·681개소), 이는 하한이라는 성질과 일치한다. 초기 재고 스냅샷에 민감하여
> ±3대 변동 시 개선량이 0.46~1.74h로 달라지므로, 절대값보다 **동일 조건에서의
> 방법 간 비교**에 쓰는 것이 타당하다."*

**마지막 문장이 핵심입니다.** 이 지표의 값어치는 절대 수치가 아니라
**같은 자로 여러 방법을 견주는 것**에 있습니다 — 대조군 비교(EXPERIMENTS.md 5장)가
바로 그 용법입니다.
