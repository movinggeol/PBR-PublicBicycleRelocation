# 차량 운용 — 로테이션과 형평성

> 2026-08-10 도입. 보유 차량 21대를 하루 여러 회차에 나눠 투입하고,
> 차량별 작업량을 기록해 부하가 한쪽으로 쏠리지 않게 합니다.

## 운영 모델

```text
보유 차량        21대
하루 재배치      약 3회차  (예: 05~10 / 10~15 / 15~20)
회차당 투입      약 10대 (상한)
나머지 차량      다음 회차 담당
```

한 회차에 전 차량을 투입하지 않습니다. 일부가 나가고 나머지는 다음 회차를 맡는
**교대 방식**입니다. 그래서 필요한 것이 두 가지입니다.

1. **로테이션** — 같은 차량이 계속 나가지 않게
2. **기록** — 누가 얼마나 일했는지 남겨서 형평성을 확인

## 이전 상태의 문제

`VEHICLE_TOTAL = 21`은 선언만 되어 있고 **어디서도 읽지 않았습니다.** 실제로는
"클러스터 1개 = 차량 1대"로 돌았고, 클러스터 수는 `ceil(대상 대여소 / 7)`로 정해졌습니다.

즉 **차량 대수가 제약이 아니라 결과**였습니다. 두 방향 모두 문제였습니다.

- 대상이 적으면 21대 중 5~6대만 쓰고 나머지는 놀았습니다.
- 대상을 늘리면 21대를 넘는 계획이 **아무 경고 없이** 만들어졌습니다.

## 지금 구조

```text
step1  클러스터 수 K = min(ceil(N / 7), VEHICLES_PER_ROUND)
         └ 회차당 투입 가능 대수를 넘지 않음. 상한에 걸리면 클러스터가 커짐

step2  vrp.py 가 클러스터별 작업량(대여소 수·대수·거리·소요시간) 산출
         └ db.assign_vehicles() 로 실제 차량 배정
         └ vehicle_assignment 테이블에 기록

웹     /vehicles 에서 누적 부하와 회차별 배정 이력 확인
```

### 로테이션 규칙

`db.assign_vehicles()`가 두 단계로 정합니다.

1. **누적 소요시간이 적은 차량부터 뽑습니다** (동률이면 출동 횟수 → 차량 ID 순).
   직전 회차에 나간 차량은 누적이 늘어 뒤로 밀리므로 자연스럽게 교대가 됩니다.
2. **뽑은 차량 중 가장 한가한 쪽에 가장 무거운 클러스터를 줍니다.**
   한 회차 안에서도, 회차를 거듭해도 부하가 고르게 수렴합니다.

별도의 순번표를 두지 않고 **누적 기록만으로** 로테이션이 나오게 한 이유는,
차량이 정비로 빠지거나 회차 수가 바뀌어도 규칙이 그대로 성립하기 때문입니다.

같은 회차를 다시 계산할 때는 그 회차의 기존 배정을 누적에서 빼고 계산하므로
**재실행해도 같은 결과**가 나옵니다.

### 실제 동작 예 (합성 데이터, 하루 3회차)

```text
회차 _05_10 (3대)          회차 _10_15 (2대)          회차 _15_20 (2대)
  V01  36대  76.7분          V04  36대  127.2분         V06  36대  94.2분
  V02  36대  66.8분          V05  18대   65.1분         V07  18대  67.9분
  V03  36대  59.3분
```

회차마다 다른 차량이 나갑니다. `V04`가 127분으로 목표(120분)를 넘었는데,
이런 초과를 눈에 보이게 하는 것이 기록의 목적입니다.

## 데이터 구조

### `vehicle` — 차량 마스터

| 컬럼 | 설명 |
| --- | --- |
| `vehicle_id` | `V01` ~ `V21` |
| `active` | 0이면 배정 제외 (정비 등) |
| `note` | 비고 |

정비로 차량이 빠지면 `active = 0`으로 두면 됩니다. 배정에서 자동으로 제외됩니다.

```sql
UPDATE vehicle SET active = 0, note = '정비 입고' WHERE vehicle_id = 'V07';
```

### `vehicle_assignment` — 회차별 배정과 작업량

| 컬럼 | 설명 |
| --- | --- |
| `run_label`, `duration` | 어느 실행의 어느 회차인가 |
| `vehicle_id`, `cluster` | 어느 차량이 어느 군집을 맡았나 |
| `stations`, `bikes` | 방문 대여소 수, **실제로 옮긴 자전거 수** |
| `distance_km`, `minutes` | 이동거리, 소요시간(이동 + 작업) |

> `bikes`는 pick 기준으로 셉니다. 한 대는 실리고 내려지므로 pick·drop의 `qty`를
> 모두 더하면 2배가 됩니다(ILP 계획 대수와 어긋남). 반면 **작업시간은 싣기·내리기가
> 각각 드는 게 맞으므로** `work_sec`는 두 동작을 모두 반영합니다.

이 테이블이 **형평성 추적의 원장**입니다. 로테이션도 이 누적을 보고 정합니다.

## 웹에서 보기

`/vehicles` 화면에서 확인합니다.

- **투입 현황** — 출동한 차량 수 / 미출동 대수
- **형평성** — 누적 작업시간의 최소·최대·편차 (편차가 작을수록 고르게 나뉜 것)
- **차량별 누적** — 출동 횟수, 처리 대수, 누적 거리·시간, 최근 작업
- **회차별 배정 이력** — 실행을 골라서 조회

API로도 제공합니다.

```
GET /api/vehicles                                  # 차량별 누적
GET /api/vehicles/assignments?vehicle_id=V01       # 특정 차량 이력
GET /api/vehicles/assignments?run_label=...        # 특정 실행 배정
```

## 함께 고친 것 — 한쪽 후보만 있는 회차

3회차 운용을 시험하다 **기존 버그**를 발견했습니다. Pick 후보만 있고 Drop 후보가
없는 시간대(모든 대여소가 과잉이라 받아줄 곳이 없는 경우)에 클러스터 수가 0이 되어
K-Medoids가 크래시했습니다.

하루 여러 회차를 돌리면 실제로 생기는 상황이라, 이제 **크래시 대신 건너뜁니다.**
step1이 건너뛰면 step2·step4도 입력이 없는 것을 보고 함께 건너뜁니다.

```text
[건너뜀] _10_15: 재배치 대상이 없습니다 (Pick 또는 Drop 후보가 없어 옮길 곳이 없음)
```

## 시간 예산

**한 회차의 작업이 끝나야 하는 시한**입니다. `target_qty`가 특정 시간 창(예: 05~10시)의
수요를 전제로 계산되므로, 작업이 늦어지면 자전거가 **필요했던 시각이 지난 뒤**에
도착합니다. 계획은 100% 달성했는데 이용자는 못 타는 상황이 되는 것입니다.

| 작업 완료 | 계획이 유효한 시간 |
| --- | --- |
| 07시 (2시간 소요) | 07~10시, 3시간 |
| 09시 (4시간 소요) | 09~10시, 1시간 |

기본값은 `TIME_BUDGET_MINUTES = 120`분이며 `PBR_TIME_BUDGET_MINUTES`로 바꿉니다.
[메모.txt](메모.txt)의 트러블슈팅 기록("1~2시간 이내 완료가 목표")에서 온 값입니다.

### 지금은 제약이 아니라 점검 기준입니다

초과해도 계획이 수정되지는 않고, **눈에 보이게만** 합니다.

- `vrp.py` — 초과 클러스터에 `⚠ 시간 예산 초과` 표시 + 요약 경고
- `imbalance.py` — 경로 요약에 준수율 출력
- `/vehicles` — 준수율 카드와 초과 행 강조

### 왜 초과가 생기나 — 이동시간이 80%입니다

실측한 시간 구성입니다.

```text
V01  총 92.0분 = 이동 74.0분 + 작업 18.0분   (이동 80%)
V02  총 89.5분 = 이동 73.5분 + 작업 16.0분   (이동 82%)
V03  총 76.2분 = 이동 59.2분 + 작업 17.0분   (이동 78%)
```

**소요시간의 70~80%가 이동입니다.** 이 비율이면 120분으로 처리 가능한 건 약 23대이고,
나머지 시간은 길에서 씁니다.

근본 원인은 **step1의 클러스터링이 시간을 모른다**는 데 있습니다. 목적함수가
`α·balance² + β·size분산 + γ·거리합`이라 시간 항이 없어서, 대여소 6곳이지만
서로 멀리 떨어진 클러스터가 만들어질 수 있습니다.

따라서 **작업량을 줄이는 것보다 지리적으로 좁게 묶는 편이 시간 단축에 효과적**입니다.
거리 가중치 `γ`를 올리는 것만으로도 개선될 여지가 있습니다.

## 남은 과제

- **차량이 여러 클러스터를 순차 처리** — 지금은 회차당 차량 1대 = 클러스터 1개입니다.
  40분짜리 클러스터를 끝낸 차량이 다른 클러스터로 넘어가지 못합니다.
- **시간 예산을 실제 제약으로** — 위처럼 표시만 할 뿐 계획을 바꾸지는 않습니다.
  방법은 ① 거리 가중치 `γ` 상향 ② 클러스터링 후 초과분을 쪼개는 반복 루프
  ③ 클러스터당 작업량 상한. 이동 비중이 80%이므로 ①이 가장 직접적입니다.
- **`VEHICLES_PER_ROUND = 10`의 근거** — 사용자 운용 계획에 따른 값입니다.
  적재 용량 10대는 대전교통공사 확인값이지만([버전관리.txt](버전관리.txt) 1.0.1),
  회차당 투입 대수는 현장 확인이 필요합니다.
- **작업자 배정** — 차량과 작업자가 1:1인지, 교대 근무는 어떻게 되는지 미반영.
