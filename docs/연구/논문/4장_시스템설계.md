# 제4장 시스템 설계

이 장은 제3장의 모형을 실제로 계산하는 시스템의 구조를 설명한다. 4.1절에서 전체 흐름을,
4.2절에서 사용한 자료를, 4.3절에서 단계별 처리를 다룬다. 4.4절은 저장소, 4.5절은 차량 운용
규칙, 4.6절은 웹 대시보드, 4.7절은 재현성과 검증을 다룬다.

## 4.1 전체 구조

시스템은 원천 자료 수집부터 재배치 계획, 지도 시각화, 성과 평가까지를 하나의 흐름으로 잇는
파이프라인이다([그림 4-1]).

![그림 4-1](../초안/그림/그림4-1_파이프라인.png)

[그림 4-1] 시스템 파이프라인 구조

파이프라인은 다섯 단계로 이루어진다. 0단계는 자료를 수집하고 순수요와 목표 재고를 계산한다.
1단계는 작업 대상을 고르고 군집화한다. 2단계는 군집마다 물량을 배분하고 방문 순서를 정한다.
3단계는 경로를 지도에 표시하고, 4단계는 재배치 전후의 지표를 계산한다. 각 단계는 앞 단계의
산출물을 입력으로 받아 독립적으로 실행할 수 있으며, 실행을 구분하는 식별자(실행 라벨)와
시간대를 공통 인자로 공유한다. 전체 실행은 하나의 실행 스크립트가 이 순서를 통제한다.

구현 언어는 Python이며, 군집화에는 K-Medoids(FasterPAM), 정수선형계획에는 PuLP와 CBC
솔버, 지도 표시에는 Folium, 웹 대시보드에는 FastAPI와 Jinja2, 저장소에는 SQLite를 썼다.

## 4.3 단계별 처리

0단계 : 수집과 전처리

공개 API로 대여소별 현재 재고와 거치대 수, 좌표를 조회하고, 월별
대여이력을 병합하여 대여소 정보를 통합한다. 이어서 대여소별·시각별 순수요를 대여 건수와 반납
건수의 차이로 집계하고, 식 (3.2)~(3.5)로 목표 재고와 재배치량을 계산한다.

1단계 : 선정과 군집화

식 (3.6)으로 수거·배송 후보를 고르고, 식 (3.7)로 군집 수를 정한 뒤
K-Medoids와 식 (3.8)의 조정으로 차량별 담당 구역을 만든다.

2단계 : 최적화

군집마다 식 (3.9)의 정수선형계획으로 옮길 대수를 정하고, 식 (3.10)의
그리디 규칙으로 방문 순서를 만든다. 결과에는 구간별 거리, 이동시간, 작업시간, 누적 소요시간,
배정된 차량이 함께 기록된다.

3단계 : 지도 시각화

경로와 수거·배송 지점, 군집을 지도에 표시한다. 지도에는 상용 경로 안내
API로 받은 실도로 경로를 그리며, 계획 계산 자체에는 식 (3.12)의 추정 이동시간을 쓴다([그림 4-4]).

4단계 : 성과 평가

식 (3.13)으로 재배치 전후의 결품 시간과 포화 시간을 계산하고, 군집별
이동거리와 소요시간을 집계하여 성과 지표로 저장한다.

![그림 4-4](../초안/그림/그림4-4_경로지도.png)

[그림 4-4] 경로 지도 출력의 예 (2026년 8월 11일 실행, 2025년 11월 통계, 05~10시). 선은 상용 경로 안내 API로 받은
실도로 경로이고 색은 차량(군집)이며, 원 안의 수는 방문 순서이다. 방문 표식을 누르면 군집, 대여소, 방문 순서, 작업

## 4.4 데이터 저장소

시스템은 산출물을 CSV 파일과 SQLite 데이터베이스에 함께 기록한다. 전환 과정의 설계로서 CSV를
기준 산출물로 두고, 데이터베이스 기록이 실패해도 경고만 남기고 계산을 계속한다. 저장소 도입이
계획 산출 자체를 막아서는 안 되기 때문이다.

데이터베이스는 20개 테이블로 구성된다. 설계의 핵심은 테이블 구조보다 한 행이 무엇에
속하는가라는 범위(scope)의 구분이다(<표 4-2>).

<표 4-2> 테이블의 범위 구분

| 범위 | 구분 키 | 해당 자료의 예 |
| --- | --- | --- |
| 실행 | 실행 라벨 | 계획 시점의 재고, 대여소 정보 |
| 실행과 회차 | 실행 라벨, 시간대 | 작업 대상, 물량 배분, 경로, 성과 지표 |
| 기간 | 자료 기간(월) | 순수요, 대여이력 |
| 관측 시각 | 관측 시각 | 관측 재고 시계열 |
| 전역 | 없음 | 차량 |

순수요를 실행이 아니라 기간의 범위에 둔 것이 중요한 판단이다. 순수요는 과거 대여이력에서만
계산되므로 언제 분석하든 같은 값이기 때문이다. 외래키는 선언하지 않았고, 대신 복합 기본키와
범위별로 먼저 지우고 다시 넣는 방식으로 같은 실행을 반복해도 결과가 겹치지 않게 하였다.

## 4.5 차량 운용

운영기관에 문의한 결과 재배치 차량은 21대이며 한 번에 모두 투입하지 않고 조를 나누어 운용한다
(대전교통공사 타슈 관제센터 담당자, 유선 문의, 2025년 9월 6일). 시스템은 이 운용 방식 위에 본 연구의 회차 구조를 얹기 위해
차량 배정 계층을 따로 둔다. 회차당 투입 대수는 고정값이 아니라 식 (3.7)의 추정 작업량이 정하며,
실데이터에서 12~16대였다<!--A:EXP 5-G-->. 따라서 보유 21대 안에서 교대 여유가 있다.

배정은 두 단계 규칙으로 이루어진다. 먼저 누적 작업시간이 적은 차량부터 그 회차에 필요한
대수만큼 뽑고, 뽑힌 차량 가운데 누적이 적은 차량일수록 작업량이 무거운 군집을 맡긴다. 별도의
순번표 없이 누적 기록만으로 교대가 이루어지므로, 차량이 정비로 빠지거나 회차 수가 바뀌어도
규칙이 그대로 성립한다.

이 규칙을 결원 상황에서 시험하였다. 결원을 0, 1, 3, 5, 6, 7, 9대로 늘려 12회차를 연속 실행한
결과, 가용 차량 16대(결원 5대)까지는 모든 회차의 배정이 성립하였고, 15대부터는 필요 대수가
16인 회차에서 배정이 실패하였다<!--A:EXP 25-->. 다만 결원이 끝난 뒤 차량별 누적 작업시간의
표준편차가 오히려 벌어져(결원 5대 기준 12회차 끝에 54분), 결원 중의 최댓값 아래로 돌아온 것은 복구 뒤
7회차째였다<!--A:EXP 25-->([그림 4-5]). 12회차 시험에서는 복구 뒤가 6회차뿐이어서 이 회복이 관측되지 않았고,
회차를 늘려 다시 재어 확인하였다. 결원 동안 누적이 멈춰 있던 차량이 복귀 직후 연이어 배정되기 때문이며,
단기 형평성은 보장하지 못한다.

![그림 4-5](../초안/그림/그림4-5_결원_형평성.png)

[그림 4-5] 결원 규모별 차량 누적 작업시간 편차의 추이(왼쪽)와 배정이 실패한 회차 수(오른쪽). 1~6회차에 결원이 들고
7회차에 복구된다. 부하는 군집당 60~100분의 합성 값이고, 회차마다 필요한 대수는 12, 14, 16대를 돌며, 값은 난수 씨앗
다섯 개의 평균이다. 왼쪽은 복구 뒤의 회복을 보이려고 12회차 시험을 14회차까지 늘려 그렸다.<!--A:EXP 25-->

차량 대수 21은 문서화된 제원이 아니라 담당자의 구두 답변이며, 공개 자료로 교차 확인되지
않는다(제8장).

## 4.6 웹 대시보드

파이프라인 실행과 결과 열람을 위해 서버 렌더링 방식의 웹 대시보드를 구현하였다. 주요 화면은
<표 4-3>과 같다.

<표 4-3> 웹 대시보드의 주요 화면

| 화면 | 기능 |
| --- | --- |
| 실행 | 기간, 시간대, 요일 구분, 차량 대수를 지정해 파이프라인을 백그라운드로 실행 |
| 성과 지표 | 실행별 지표와 직전 실행 대비 증감을 표와 그래프로 제시 |
| 차량 운용 | 차량별 누적 작업량, 형평성, 회차 배정 이력 |
| 작업지시서 | 차량별 방문 순서와 수량을 인쇄 가능한 형태로 제공 |
| 실시간 재고 대조 | 출발 직전에 계획 대상 대여소만 다시 조회하여 집행 가능 여부를 판정 |
| 지도·자료 | 단계별 지도와 산출 자료의 열람·내려받기 |

![그림 4-9](../초안/그림/그림4-9_실시간대조.png)

[그림 4-9] 실시간 재고 대조 화면 (2026년 8월 11일 실행의 05~10시 계획을 2026년 9월 18일 15시 52분의 재고와 대조,
차량 한 대). 계획 대상 86곳 가운데 47곳은 그대로 집행할 수 있고, 36곳은 수량 조정이 필요하며, 3곳은 집행할 수
없다고 판정하였다. 음영 행이 계획과 다른 재고가 발견된 곳이다.

파이프라인 계산은 수 분이 걸리므로 웹 요청 안에서 직접 실행하지 않고 별도 프로세스로
실행한다. 설계에서 일관되게 지킨 원칙은 화면이 판정만 하고 계획을 자동으로 바꾸지 않는다는
것이다. 실시간 재고 대조가 계획과 다른 재고를 발견하거나, 비가 와서 실제 필요량이 줄어든다는
사실을 알리더라도 계획량은 바꾸지 않는다. 자동 보정을 넣으면 기사가 손에 든 작업지시서와 화면의
숫자가 어긋나기 때문이다.

대시보드는 인증 없이 로컬에서만 띄우는 것을 전제로 하므로, 운영 환경에 배포하려면 인증과 권한
관리가 먼저 필요하다.

시스템은 900개가 넘는 자동화 테스트로 검증한다. 합성 자료로 파이프라인 전 구간을 실행하는

남겨 재고 스냅샷과 기간, 난수 씨앗을 인자로 받으며, 본 논문의 표마다 그 조건을 함께 밝힌다.
API 키와 원천 자료는 공개 저장소에서 제외하였으므로, 재현하려면 각자의 API 키와 자료를 준비해야
한다. 실험별 재현 방법은 부록에 정리한다.
