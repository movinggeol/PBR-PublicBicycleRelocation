    ## Data

### Data Sources

본 프로젝트는 대전광역시 공공자전거(TASHU)의 운영 데이터를 활용하였다.

| 데이터        | 출처             | 수집 방식    |
| ---------- | -------------- | -------- |
| 대여소 정보     | TASHU Open API | REST API |
| 자전거 보유 현황  | TASHU Open API | REST API |
| 대여소 거치대 정보 | 공공데이터포털        | CSV      |
| 대여 이력 데이터  | 공공데이터포털        | CSV      |
| 대여소 좌표 정보  | 공공데이터포털        | CSV      |

### Data Collection Pipeline

데이터 수집 및 처리 과정은 다음과 같다.

```text
TASHU API
      │
      ▼
Raw Data Collection
      │
      ▼
Data Cleaning
      │
      ▼
Net Demand Calculation
      │
      ▼
Target Quantity Calculation
      │
      ▼
Pick / Drop Selection
      │
      ▼
Optimization Dataset
```

### ETL Process

#### Extract

* TASHU Open API 데이터 수집
* 공공데이터포털 CSV 데이터 수집

#### Transform

* 대여소 정보 통합
* 중복 데이터 제거
* 결측 데이터 제거
* 순수요(Net Demand) 계산
* 목표 재고(Target Quantity) 계산
* 재배치 수량(Rebalancing Quantity) 계산

#### Load

* 분석용 CSV 데이터셋 저장
* ILP/VRP 입력 데이터 생성

DB -> 현재는 csv 기반인데, 대규모가 처리 힘들 테니 DB로 가야 한다는 것은 정해짐.
그런데 어떤 걸 왜 쓸지를 고민해봐야 함.
NoSQL이라고 말했는데, 시계열 데이터를 다룰 수 있는 DB를 고려해봐야 할 것 같다 함.



'''
markdown### 1. 시계열 DBMS(TSDB) 개요 및 종류
- **개요:** 시간 흐름에 따라 생성되는 데이터(센서, 로그, 거래 등)를 고속 저장/조회하는 DB.
- **종류:** InfluxDB(모니터링 특화), TimescaleDB(PostgreSQL 기반 SQL 활용), Machbase(국내 고성능 TSDB), kdb+(금융권 초고속 DB).

### 2. 자전거 대여소 데이터(60만 건, 5개 데이터) 관리 전략
- **현재 데이터 상황:** (60만 행, 10개 컬럼) 규모의 CSV 파일 총 5개.
  1) 대여이력 (시계열)
  2) 대여소 정보 (마스터)
  3) 대여소별 작업량
  4) 대여소별 재고 이동
  5) 방문 순서
- **추천 DB:** **SQLite**
- **구조 제안:** 5개의 CSV를 각각 다른 파일로 만들지 않고, `bike_system.db`라는 단 하나의 SQLite DB 파일 내부에 5개의 테이블(Table)로 통합 관리. (SQL JOIN 연산 및 이식성 극대화)

### 3. SQLite가 로컬 파일임에도 완전한 'DB'로 작동하는 기술적 이유
1) **B-Tree 구조 및 인덱스(Index):** CSV처럼 처음부터 끝까지 다 읽는(Full Scan) 방식이 아니라, 인덱스를 통해 60만 건 중 원하는 1건을 단 3~4번 만에 핀포인트로 찾아냄.
2) **페이지(Page) 단위 입출력:** 파일 전체를 메모리(RAM)에 올리지 않고, 데이터가 포함된 작은 블록(보통 4KB)만 로드하여 메모리 사용량을 최소화함.
3) **바이너리 인코딩(압축):** 텍스트(String) 형식인 CSV와 달리 데이터를 컴퓨터가 이해하는 이진수(Binary)로 변환/압축 저장하여 디스크 용량을 아끼고 연산 속도를 높임.
4) **ACID 트랜잭션 보장:** WAL(Write-Ahead Logging) 기법을 사용해 데이터 쓰기 중 프로그램이 꺼져도 파일이 깨지지 않고 안전하게 복구(Rollback)됨.
5) **표준 SQL 지원:** 대형 서버 DB와 동일한 SQL 문법을 지원하여 복잡한 데이터 결합(JOIN) 및 시계열 데이터 가공이 가능함.

### 4. 파이썬 기반 테이블 생성 및 최적화 스크립트 예시
import sqlite3

conn = sqlite3.connect("bike_system.db")
cursor = conn.cursor()

# 5개 테이블 생성 (대여이력, 대여소 정보, 작업량, 재고이동, 방문순서)
cursor.execute('''
CREATE TABLE IF NOT EXISTS rental_history (
    history_id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT NOT NULL, bike_id TEXT NOT NULL,
    start_station_id TEXT NOT NULL, end_station_id TEXT, user_id TEXT NOT NULL
)''')

cursor.execute('''
CREATE TABLE IF NOT EXISTS station_info (
    station_id TEXT PRIMARY KEY, station_name TEXT NOT NULL,
    latitude REAL, longitude REAL, capacity INTEGER
)''')

cursor.execute('''
CREATE TABLE IF NOT EXISTS station_workload (
    work_date TEXT NOT NULL, station_id TEXT NOT NULL,
    total_rentals INTEGER DEFAULT 0, total_returns INTEGER DEFAULT 0,
    PRIMARY KEY (work_date, station_id)
)''')

cursor.execute('''
CREATE TABLE IF NOT EXISTS inventory_movement (
    movement_id INTEGER PRIMARY KEY AUTOINCREMENT, move_timestamp TEXT NOT NULL,
    from_station_id TEXT, to_station_id TEXT, bike_count INTEGER NOT NULL, truck_id TEXT
)''')

cursor.execute('''
CREATE TABLE IF NOT EXISTS visit_sequence (
    route_id TEXT NOT NULL, sequence_order INTEGER NOT NULL,
    station_id TEXT NOT NULL, estimated_arrival TEXT,
    PRIMARY KEY (route_id, sequence_order)
)''')

# 시계열 인덱스 추가로 조회 성능 극대화
cursor.execute('CREATE INDEX IF NOT EXISTS idx_rental_time ON rental_history(timestamp)')
conn.commit()

    issue -> branch -> commit -> pull request ->review -> merge(메인으로 머지)

    이슈를 메인에서 고친 후 커밋하면, 다른 오류가 발생할 수 있고, 이로 인해 전체 서비스가 정지될 수 있음

    있어야 하는 것 : 상황(어떤 문제가 보였는가), 영향(사용자는 무엇을 못 하는가), 
                    목표(무엇을 바꾸면 되는가), 완료 기준(어떤 상태면 닫을 수 있는가), 검증 방법(어떻게 확인할 것인가)

트러블슈팅은 면접 답변의 재료다.
Situation 상황, Task 과제, Action 활동, Result 결과

Situation
            최종 작업 계획의 예상 현실성 없이 과한 시간이 계산된다.
            (ex : 수요 예측을 다음 5시간 동안 하는데, 이전 작업이 4시간 소요된다.)
Task
            수요 예측 시점부터 5시간 동안의 예측이기에, 
            최대한 빨리 작업을 마쳐야 하며 1~2시간 이내에 재배치 작업을 완료하는 것이 목표이다.
            상황처럼 긴 시간이 소요된다면 예측 시간 동안 사용될 대수를 충족하지 못한다.
Action
            "각 작업자마다 방문 노드 수가 너무 과하게 책정되었다"고 판단된다.
            작업자별로 부여되는 노드수를 줄인다.
Result
            매 작업마다 과한 작업량을 계획하는 것은 현실성이 없다는 것을 알았다.
            모든 작업을 할 수 없는 경우엔 우선순위가 높은 작업을 우선적으로 처리해야 한다.
